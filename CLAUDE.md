# Claude Code Project Guidelines

## Project Overview

**webrun-vcs** is a pure-TypeScript Git implementation (read/write) organized as a pnpm monorepo.

Key packages: `vcs-core` (objects, refs, packfiles), `vcs-working-tree` (index, checkout, worktree), `vcs-commands` (porcelain API), `vcs-transport` (fetch/push protocols), `vcs-transport-lfs`/`vcs-transport-xet` (large objects), `vcs-store-*` (storage backends), `vcs-workspace` (file sync plus versioning).

Tech stack: TypeScript, Node.js 24, pnpm 10 workspaces (via corepack), Vitest (testing), Biome 2 (lint + format), Rolldown (bundling). Internal dependencies use `workspace:^`; external ones use the pnpm catalog (`catalog:`) in `pnpm-workspace.yaml`.

## General Behavior

Do not over-analyze or over-explore before acting. When the task is clear, start implementation immediately. Ask for clarification only when genuinely ambiguous.

## File Operations

When creating notes or documents, always confirm the target directory/path with the user before writing. Never assume the output location.

## Conventions

### Naming
All files and folders use **kebab-case**: `my-component.ts`, `utils/date-formatter.ts`

**[Full Guide](.claude/code/naming-conventions.md)**

### Portable APIs only
Library and app code (`packages/*/src`, `apps/*/*/src`) uses only APIs that exist in browsers and on servers: files through `FilesApi`, Web Streams, Web Crypto, `fetch`. No `node:*` imports (Biome `noNodejsModules` is an error there); tests may use Node (to drive native git, for example). On Node, get a `FilesApi` from `createNodeFilesApi` (`@statewalker/vcs-utils-node/files`). Every file operation goes through the `FilesApi`, symlinks included (`lstat`/`readlink`/`symlink` in its `PosixFilesApi` contract), so a composite or simulated FilesApi (`createSymlinkFilesApi`, `createMountedFilesApi`) works everywhere. The one exception to the no-`node:*` rule is the Node FilesApi itself in `packages/vcs-utils-node/src/files` (`posix-node-files-api.ts`, `replace-file.ts`). `git-host-environment.ts` may import `node:os` but not `node:fs`: it reads files through a FilesApi. The Biome overrides in `biome.json` list exactly these files, so any other `node:fs` use fails lint.

### Module Structure
Folder-based exports with wildcard re-exports. Import from `index.js`, use `.js` extensions.

```typescript
// ❌ import { foo } from "../delta/specific-file.js";
```

## Code Quality / Post-Edit Checks

## Testing

When editing existing test files, NEVER overwrite/replace the entire file. Always append or surgically insert new tests alongside existing ones.

When working from checklist/epic documents, complete ALL items listed — do not skip or forget items. Before reporting done, re-read the checklist and verify every item is addressed.

## Common Pitfalls

- **Import extensions**: Always use `.js` in imports, never `.ts` or extensionless
- **`git-cli-sandbox`**: `apps/demos/git-cli-sandbox/` is stale — ignore its test failures
- **`split()` limit**: `"a b".split(" ", 2)` gives `["a","b"]` not `["a","b c"]` — use `indexOf` + `slice`
- **Refs vs Checkout**: `CommitCommand` uses `history.refs`, not `checkout.head`
- **Apps are built without type checking**: vite builds `apps/*` even when they use removed APIs. After changing a package API, run `pnpm -r typecheck` (it covers the apps) and grep `apps/` for the old names.
- **Workspace cycles**: `vcs-core` depends on `vcs-utils-node`, and `vcs-testing` on `vcs-core`, so `vcs-utils`/`vcs-utils-node` must not depend on `vcs-testing` (not even as a devDependency): pnpm then builds in the wrong order and CI fails on missing declarations. Put such tests in a store package.
- **git's read-only files in tests**: git writes commit-graph files, packs and idx files mode 0444; tests run as root locally but CI does not, so a test that corrupts or rewrites one `chmodSync(path, 0o644)` first (else EACCES on CI). Check with `setpriv --reuid=65534 --regid=65534 --clear-groups env HOME=<tmp> TMPDIR=<tmp> node ../../node_modules/vitest/vitest.mjs run <test> --configLoader runner` (a world-writable temp dir, not the scratchpad)
- **`toEqual` on large byte arrays**: Vitest `toEqual` on `Uint8Array`s of hundreds of KB or more takes seconds and has caused CI timeouts; compare the bytes directly (length plus a loop, or `Buffer.equals` in tests)
- **Native git in tests**: CI has no `user.name`/`user.email`; pass `GIT_AUTHOR_*`/`GIT_COMMITTER_*` in the env of every git call, and fix both `GIT_AUTHOR_DATE` and `GIT_COMMITTER_DATE` when two repositories must produce the same commit ids
- **git versions differ**: CI runs a newer git (2.5x) than the sandbox (2.43); oracle tests that compare bytes with native git must pin config that changed defaults (e.g. `transfer.advertiseObjectInfo`) or normalise version-dependent lines
- **git 3.0 (`breakingChanges`)**: `GitHostEnvironment.breakingChanges` (`createNodeGitHostEnvironment({ breakingChanges: true })`) asks for a git built with `WITH_BREAKING_CHANGES` (`Documentation/BreakingChanges.adoc`); off, ours is git 2.5x. Its twins are `tests/*-git3-native.test.ts`, run against `$GIT3` (`tests/native-git3.ts`: `git3Binary()`, `nativeGit3Env()`; the `git3-oracle.yml` workflow builds git master with the flag) and skipped without it. Build one locally with `make WITH_BREAKING_CHANGES=YesPlease NO_GETTEXT=YesPlease NO_TCLTK=YesPlease NO_PERL=YesPlease NO_PYTHON=YesPlease NO_CURL=YesPlease prefix=<dir> install` and `GIT3=<dir>/bin/git`. Such a build creates reftable repositories on `main` but still SHA-1 objects (`read_repository_format` gives a new repository `GIT_HASH_SHA1_LEGACY`): follow the oracle, not BreakingChanges.adoc. What the switch changes: `init`'s initial branch (`defaultInitialBranch`: `init.defaultBranch` from the protected config, else `master`, `main` with the switch; `InitResult.hints` is git's advice), `safe.bareRepository`'s default (`explicit`), `core.commentChar=auto` refused in `checkConfigOnLoad` (`checkAutoCommentChar`, git's advice per config file). Grafts stay (the oracle still honours `info/grafts`). Legacy remotes: off, a remote the configuration gives no URL is read from `$GIT_COMMON_DIR/remotes/<name>` then `branches/<name>` (`loadLegacyRemote`, vcs-commands `legacy-remotes.ts`: remote.c's `read_remotes_file`/`read_branches_file`, `<url>[#<branch>]` fetching `refs/heads/<branch>:refs/heads/<name>`, pushing `HEAD:refs/heads/<branch>`, the branch `init.defaultBranch` else `master` with the hint, tags always followed: transport `TagMode` `auto-always`), its refspecs added after the configuration's; commands load it where git calls `remote_get` (fetch, pull, push, ls-remote, `@{upstream}`/`@{push}`, `remote rename`) and every `RemoteConfigStore` of the working copy then sees it (`isConfigured`, `legacyOrigin`; `configuredNames` stays config-only, as `for_each_remote`); 2.5x's deprecation warning goes to `FetchResult.messages`/`PushResult.warnings`/`RemoteRenameResult.warnings` (2.43 has none), `remote rename <n> <n>` migrates it (`migrate_file`) and another new name fails as `git_config_rename_section` (exit 1). With the switch on both files are never read (git 3.0); twins `tests/legacy-remotes-native.test.ts`
- **`GIT_CONFIG_GLOBAL=/dev/null` is read-only**: `nativeGitEnv` and most test environments point `GIT_CONFIG_GLOBAL` at `/dev/null`; a `git config --global` (or `git lfs install`, which writes global config) under it locks and renames a regular file over `/dev/null`, breaking every later process on the machine. A test that writes global config sets `GIT_CONFIG_GLOBAL` (or `HOME` with it unset) to a temp file; never run such a command by hand in that environment either. Check `ls -l /dev/null` still shows a character device
- **Background maintenance in native git**: git 2.5x runs `git maintenance run --auto --detach` after `commit` and similar commands; the detached process changes `.git/objects` while a test copies or reads the repository (CI fails with ENOENT). Set `maintenance.auto=false` and `gc.auto=0` (e.g. `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n`, as `nativeGitEnv` in vcs-commands tests does); a local `git push ../bare.git` starts receive-pack with `local_repo_env` cleared (`GIT_CONFIG_COUNT` too), so set them in the receiving repository's own config (`receive.autogc=false` as well) when a test copies it afterwards
- **Commit identities**: every commit/tag-creating command resolves its author and committer through `resolveAuthorIdent`/`resolveCommitterIdent` (vcs-commands `git-ident.ts`, git's `ident.c` order). Native-twin tests pass the same `GIT_AUTHOR_*`/`GIT_COMMITTER_*` to native git and, through `createNodeGitHostEnvironment({ env })`, to ours, instead of `setAuthor`/`setCommitter`
- **Signing is refused**: no signer exists yet (statewalker-root#283), so every request to sign (`setSign`/`setSigningKey`, `commit.gpgSign`; tag `setSigned`/`setSigningKey`, `tag.gpgSign`, `tag.forceSignAnnotated`; push `setSigned`, `push.gpgSign`) fails where git's `commit_tree`/`build_tag_object`/`generate_push_cert` would sign, with git's lines for a gpg that fails without output (`signing.ts`: `signRequestOf`, `refuseCommitSigning`, `SigningFailedError`): the state git leaves stays (MERGE_HEAD, CHERRY_PICK_HEAD, a stopped or rescheduled rebase pick, `rebase-apply`). Twins give native git a `gpg.program` that exits 1 (`tests/signing-refused-native.test.ts`)
- **Merge-family twins**: `merge`/`cherry-pick`/`revert`/`rebase`/`pull` native tests build both twins with `buildHistory` (`tests/merge-native-scenarios.ts`) and compare `snapshot(..., normalizeState)` (`tests/merge-native-helpers.ts`); `normalizeState` evens out what 2.43 and 2.5x write differently in `rebase-merge/` (todo `# ` subjects, `message`). A refused `git merge` runs `restore_state` (reset --hard + `stash apply --index`), which leaves AUTO_MERGE and rewrites dirty files through smudge
- **`connection: close` in test HTTP servers**: Node 22's undici 6 asserts (`Parser.finish`, `!this.paused`) when the server closes the socket while the body consumer pauses on the final chunk; test servers keep connections alive and end them in `close()` (`closeAllConnections`)
- **Gitea oracle**: `GITEA=1 pnpm --filter @statewalker/vcs-testing-gitea test` runs a real Gitea (test infra; Node APIs allowed in that package via a biome override)
- **Sorted directory listings**: Node `fs.readdir`, and so FilesApi `list`, returns names sorted, so git behaviour that depends on filesystem order (readdir order of loose objects, reflogs) cannot be reproduced; tests sort such output
- **`git fsck` in 2.5x**: it runs `git refs verify` unless given `--no-references` (`FsckCommand` matches `fsck --no-references`), and dies under `--connectivity-only` on a corrupt packed object
- **Missing files in memory**: `createInMemoryFilesApi().read()` of a missing path yields no bytes instead of failing with ENOENT, so `tryReadFile` returns an empty array there; check `stats(path)?.kind === "file"` first when a missing file must read as absent
- **Commit-graphs and replace refs**: `git commit-graph write` disables replace refs and writes a graph anyway; `git gc` (in-process, replace refs on) writes none, and readers ignore a graph while `refs/replace/` has refs (`commitGraphCompatible`)
- **Bloom statistics differ by version**: git 2.5x asks a root commit's changed-path filter (`rev_same_tree_as_empty`), 2.43 does not, so trace2 `bloom/statistics` of one `git log -- <path>` differ by one check per root reached (`log-path-native.test.ts` allows for it)
- **Benchmarking**: measure the built bundles (`dist/`), not sources through tsx: its `keepNames` wraps every function in `__name` and skews profiles of hot closures. `node scripts/bench-porcelain.mjs <work-dir>` builds a wide and a long-history repository with native git and times status, commit -a, log -p and log --stat against it (median of fresh processes)
- **Benchmark noise**: the sandbox VM varies by 10 to 15% between runs of the same build; compare two builds interleaved (A, B, B, A...) over 11 or more fresh processes, with the CPU time (`process.cpuUsage()`) beside the wall time, and keep a copy of the baseline's `packages/*/{dist,package.json,node_modules}` (relative pnpm links) to run it from. A change that does not beat that noise is dropped. A cold status's fixed cost is mostly the lstat syscalls (about 3 µs each in a fresh process, half that warm) and JIT warm-up: lstat without BigInt (`bigint: false`, exact seconds but not nanoseconds) and a directory cache in `lstatMany` measured no gain; git verifies the index trailer only in fsck (`verify_index_checksum`), so reads skip the hash, and nothing on a read-only path should call `crypto.getRandomValues` (its first call loads the runtime's crypto, several ms) Commit walks are bound by object reads (pack lookup, inflate, delta), not commit parsing: `commitFromBytes` (one native `TextDecoder` pass) costs about 1 µs per commit and a byte-by-byte JavaScript header parser is slower (`String.fromCharCode.apply` over subarrays)
- **Attribute lookups outside an operation**: a `Worktree.attributes`/conversion lookup made outside `Worktree.batch` opens a scope of its own, re-reading the configuration, `info/attributes` and every `.gitattributes` on the way, once per path. A command that prints or converts many paths runs inside one batch (`git log` and `DiffCommand.callBytes`/`callDiffstat` do); `git diff A B` of 200 files spent about a fifth of its time there
- **FilesApi Proxies inside `Worktree.batch`**: `FileWorktree.batch` runs over `files.withLstatCache()`, a new `PosixNodeFilesApi` of the same root, so a test Proxy around the FilesApi (one refusing `move`/`remove`, or counting `read`s) sees nothing a batched command does unless it wraps `withLstatCache` too. Attribute-read counting tests (`diff-one-operation`, `commands-one-operation`) therefore count only the reads made outside an operation; `mv` and `rm` stay unbatched (their failure-injection twins rely on the Proxy, and they hash only files whose stat changed)
- **FilesApi reads in hot paths**: every `read` call resolves and lstats its path; on Node a range of at most 64 KiB is read synchronously, a longer one through libuv's thread pool (several round trips, idle time in profiles). Per-entry pack reads go through cached windows of at most 64 KiB (`PackedEntry.data()`, index-pack's `WindowReader`), never `files.read` per entry. `node scripts/bench-clone.mjs <dir>` times a clone's stages (pack generation, index-pack, checkout, end to end) against native git without bitmaps
- **Small typed arrays in hot paths**: `new Uint8Array(n)`/`new Int32Array(n)` above 64 bytes gets a backing store outside the heap (1–3 µs each, more than a small diff's loops); per-object or per-diff buffers come from `allocBytes`/`allocInt32` (vcs-utils `streams/`, slab views) or a reused scratch buffer. On Node, `fs.promises.lstat` with any concurrency is about ten times slower than `lstatSync` in a loop, so stat passes stay synchronous
- **Type and size checks of packed objects**: `objectHeader`, `hasObjectOfType` (typed stores' `has`), `Blobs.size` and write-pack's planning read entry headers (`GitObjects.header`/`objectType`, git's `oid_object_info`) and fall back to `get` only when those answer undefined; never check a type or size through `get` in a loop (it applies the whole delta chain). A wrapper of `GitObjects` may pass `header`/`objectType` through only if they answer for nothing its `get` would not return. index-pack inflates a stream whole in one pass when it lies in the chunk at hand (`inflateWholeInChunk`); keep the streaming path as the fallback that reports errors. Benchmarks that build branches with native git under a fixed `GIT_COMMITTER_DATE` give them the oldest date, and date-ordered walks (merge bases, upload-pack's commit walk) then read the whole history, in native git too: date such commits after their parents
- **FIFO/LRU eviction with `Map`**: `map.keys().next()` skips every slot deleted since the table was rebuilt, so evicting one entry per insert costs microseconds; use `OrderedMap` (vcs-utils) for caches that evict
- **Funcname patterns**: `diff.<driver>.xfuncname`/`funcname` and the builtin driver patterns are POSIX regexes; run them through `compilePosixRegex` (vcs-utils `regex/`), never a JavaScript `RegExp` (different semantics, catastrophic backtracking)
- **Tree modes**: the tree store reads modes canonical (`canonTreeMode`, git's `canon_mode`: a 100664 entry reads as 100644). Code that re-encodes a stored tree or must see the stored modes (fsck, serialization, sync) reads `trees.raw` and decodes it with `decodeTreeBytes(raw)`
- **Cache-tree after an index change**: a cache-tree written with the index must describe the resulting index. Build it from a tree only when the index equals that tree (`primeCacheTree`, as git's `prime_cache_tree`); otherwise invalidate every path where the index differs (`invalidateCacheTreeAgainstIndex`). `writeTree` reuses valid nodes, so a stale one silently drops staged changes from commits. `IndexFile` diffs the entries every cache-tree describes with the ones it writes: the one read or written (`TREE`) and a pending one from `setCacheTree` alike (the staging records the entries at set time), invalidating each path that changed since, so code that edits entries after (or without) setting a cache-tree needs no invalidation of its own; set a tree computed for the final entries after the edits (`rewriteIndex(..., { cacheTree })`), or the diff throws its valid nodes away. Intent-to-add entries are in no tree, skip-worktree or not (`update_one`); tests check a cache-tree with `verifyCacheTree`
- **Faking racy-git in fixtures**: `utimes` sets mtime but never ctime, and git (no `USE_NSEC`) compares ctime seconds under the default `core.trustctime=true`, so a fixture that dates files and the index to fake a racily clean entry still races the real clock through ctime under load (a stat mismatch skips the size-0 smudge in native git and ours alike); set `core.trustctime=false` in such fixtures
- **Ref values are checked**: every ref store refuses a direct value that is not a full lowercase hex object id (`isRefObjectId`, reason `invalid-object-id` in `planRefBatch`); a symbolic ref (HEAD at a branch) is written with `setSymbolic`, never `set("HEAD", "refs/heads/x")`, and test fixtures use real ids, not fakes. Commands that take a revision name resolve it before writing refs (as `rebase().setUpstream("main")` does now)
- **Path checkouts**: `checkout -- <paths>`, `restore` and `reset -- <paths>` share `checkout-paths.ts` / `read_from_tree` (builtin/checkout.c `checkout_paths`, builtin/reset.c) with full pathspecs through `pathspec.ts`; a path checkout that names nothing or hits an unmerged path writes nothing. git 2.43 stops a glob-looking element at an index entry of exactly that name (`x*y.txt`), 2.5x keeps matching: native twins of such elements are 2.5x-only
- **Unborn index**: with no `.git/index` (`clone --no-checkout`, `worktree add --no-checkout`) `isIndexUnborn(staging)` is true (no entries, update time 0: only Git/File stagings, never memory/KV/SQL); checkout/switch and two-tree `read-tree -m` then run git's `initial_checkout` (every target entry written, untracked files in the way still refused), everything else reads it as an empty index (status: HEAD's files staged as deleted). A switch naming no target leaves it unborn: `switch -c <new>`, `switch --detach`, and only the exact `git checkout -b <new>` (`setOnlyMergeOnSwitchingBranches`; `checkout -q -b <new>` merges). Never write an empty index where git writes none (a no-op `sparse-checkout set` there), or the next checkout stages deletions
- **Split and sparse indexes**: `IndexFile` reads a split index (`link`: `sharedindex.<id>` in the git directory, checksum checked, freshened on read, merged as `merge_base_index`) and a sparse index (`sdir`: each sparse directory expanded from its tree, the `TREE` extension turned into the full index's) itself, so a staging always holds the whole, merged, expanded index; any other lowercase extension is still refused (`UnsupportedIndexExtensionError`). Writes follow `write_locked_index` and `convert_to_sparse` through the staging's `IndexHost` (`setIndexHost`; commands install `indexHostOf` once per staging: `core.splitIndex`, `splitIndex.maxPercentChange`/`sharedIndexExpire`, `core.sharedRepository`, `index.sparse` with cone patterns, the trees); without a host a split index stays split and nothing is collapsed, and `FileStagingStore` expands a sparse index from the repository's own trees (`defaultTrees`). Which entries stay shared is git's `ce->index` kept beside the entry objects (`split-index.ts`): a new object at a path takes the previous entry's place (replacement when its data changed), except in an unpack-trees write (`markIndexUpdate(staging, { workdir: true })`: checkout, reset, merge, stash's reset) where a changed object or mode deletes the shared entry, and paths `markReaddedEntries` names (`git apply`'s remove-and-add). A sparse index read is re-collapsed into the same directories while they qualify (git's sparse-aware commands keep it collapsed, its cache-tree as edited); otherwise a full conversion stores the cache-tree's trees first (`storeCacheTree`, `WRITE_TREE_MISSING_OK`). An index written several times where git writes once ends up with extra shared indexes and other replacements: `withOneIndexWrite("last", body, { holdWrites: true })` holds them (`Staging.holdWrites`) and writes once (a whole-tree reset; never a body that reads the index back between its writes, as `reset -p` does). A status that only splits or unsplits still writes (`IndexFile.wantsRewrite`). gc and fsck read indexes through `readIndexFileEntries`. git 2.5x prints the `advice.sparseIndexExpanded` hint when sparse-checkout expands a sparse index (`--no-sparse-index`, non-cone patterns), 2.43 does not. Twins of index-writing commands compare stat-free structure (`ls-files`-like entries, link bitmaps, shared entries) across copies, or run both in one directory restoring `.git/index` and `sharedindex.*` between them for byte equality
- **Index trailers and corrupt indexes**: only fsck hashes an index (`verifyChecksum`, git's `verify_index_checksum`), so `parseIndexFile` bounds-checks every count, entry, name and varint itself and refuses corrupt bytes with `IndexCorruptError` (git's stderr `lines`, exit 128; fsck returns them as its death). `index.skipHash` (default `feature.manyFiles`) writes a null trailer (`IndexSettings.skipHash`); stagings tell such files apart by `indexFileIdentity` (`skiphash:` plus the content's SHA-1), never by the trailer, and a new shared index stays hashed (git's `sharedindex.0000…` loses the entries)
- **Index flags**: one-way whole-tree index reads (reset, `checkout -f`, autostash) pass `readTree(..., { keepMatching })` so skip-worktree and assume-unchanged entries keep their flags, as git's `oneway_merge`; flagged entries are checked by stat only (`flaggedEntryDiffers`, `entryNotUptodate`), never by content
- **`FilesApi.move` returns false**: it reports failure by returning `false` (the Node FilesApi swallows the errno) instead of throwing; every caller must check the result, or code that then cleans up the source (as `mv` prunes empty source directories) deletes data after a failed move
- **Index lock across a commit**: `commit --only` and `commit -a` hold `staging.lockIndex()` from before they edit the index until HEAD has moved (git's `index_lock`); while it is held write through the lock (`write()`, then `commit()`/`rollback()`), never `staging.write()` (it fails with `IndexLockedError`), and give an `AddCommand` run inside it `setWriteIndex(false)`
- **Adding index entries**: stage paths through `IndexAdder` (vcs-commands `index-adder.ts`, git's `add_to_index`): it drops the stage-0 entries a new one clashes with as a file or directory and invalidates each touched cache-tree path; every `writeTree` refuses such clashes (`verifyTreePaths`) rather than storing a tree with two entries of one name. Code that builds entries itself (reset's `read_from_tree`, `read_tree_some`) drops clashes with `stageZeroClashes` (`has_file_name`/`has_dir_name` compare one stage: conflict stages of a clashing path stay), and every intent-to-add entry it creates stores the empty blob first (`set_object_name_for_intent_to_add_entry`), or native `write-tree`/`status` fail on the index
- **Worktree stat pass**: code that compares many index entries with their files stats them in batches (`withWorktreeEntries` / `getWorktreeEntries`, passing the entry to `compareWithWorktree`), not `getEntry` per path; untracked scans pass `skipFile` (the index's paths) to `walk`. A walk lists through `PosixFilesApi.listKinds` when present, so a FilesApi wrapper that overrides `list` (a test Proxy simulating an unreadable directory) must override `listKinds` too
- **Unreadable directories**: the Node FilesApi's `list` and `listKinds` both throw for a directory they cannot read (EACCES; a missing one lists nothing), and walks report it through `onUnreadable(path, error)`; commands turn that into git's "could not open directory" warning (`unreadableDirectoryWarning`). Tests run as root, which reads any directory: simulate unreadable ones with a FilesApi Proxy (or `vi.mock` of `readdir`), and take the expected lines from native git run as an unprivileged user (`setpriv --reuid=65534`)
- **Sparse checkout in index-writing commands**: a command that writes the index and the worktree together takes `SparseUnpack.start` before it changes anything and follows git's unpack-trees order: its checks and writes skip what `leavesAlone(path)` names (a skip-worktree or new entry staying outside the patterns: never checked for local changes or untracked files, never written or removed), it writes only paths `writes(path)` accepts, unlinks the files `leaving()` decides (verify_uptodate_sparse against the source index, before any write) with its own removals, and once its result is written calls `finish()` (flags, entries coming back into the patterns). Never write a file outside the patterns and remove it afterwards (`switchTrees`, `resetMerge`/`resetKeep`, `restoreWorktreeHard`, checkout and clone do this already). git repeats the patterns' "unrecognized pattern" warnings once per index it builds; ours prints them once per command. Conflicts are passed to `sparse.conflict()`: a conflicted path is written whatever the patterns say only where its source entry was skip-worktree or absent (merge-ort's `record_conflicted_index_entries` checks out a skip-worktree stage-0 entry); one leaving the checkout keeps `CE_WT_REMOVE` and is unlinked, its content left in the stages. `update_sparsity` runs without `o->internal.dir`, so `finish({ preserveIgnored })` treats ignored files as untracked there; elsewhere ask `await worktree.isIgnored(path)`, never a worktree entry's lazy `isIgnored` (it answers before the ignore files are read). - **Reftable repositories**: `extensions.refStorage = reftable` opens; `createGitFilesBackend` gives it a `ReftableRefStore` (vcs-store-files `refs/reftable/`): a lazy reader as git's `reftable/reader.c`. `openReftable` checks only the header, footer CRC and section positions; `getRef` seeks through the ref index (its top level may span several blocks, walked linearly) or the blocks' first keys, then a block's restarts; `refs(prefix)`/`logs(refName)` are generators decoding one block at a time (log blocks inflated one at a time, exactly to their length), keys rebuilt in one scratch buffer; `verify()` walks every block (fsck). Every decoded block, restart and record is bounds-checked (`ReftableFormatError`). SHA-256 repositories use version 2 tables with hash id `s256` (28-byte header, 72-byte footer, 32-byte ids and obj keys; git's `writer_version`: SHA-1 stays version 1): the store, stack reader and writer are told the repository's `objectFormat` (`ReftableRefStoreOptions.objectFormat`, `createReftableStackReader(files, dir, { objectFormat })`, `ReftableWriteOptions.objectFormat`, `openReftable(bytes, name, { objectFormat })`) and refuse a table of another hash as git's merged table does (`ReftableFormatError`, "corrupt reftable file"; native reads then see no refs, writes die `reftable: transaction prepare: corrupt reftable file`); compaction's size overhead is the header less one (23, or 27). obj_id_len (common prefix + 1) has 5 bits: ids sharing 31 bytes would overflow it in git too, so tests use real hashes, never ids that differ only at the end. No budget is relative to the file (`reflog expire` writes tombstones deflated below a byte each): each call gets a `ReftableReadBudget` charging records visited, restart tables checked, names and values materialised and an eighth of inflated bytes against `REFTABLE_READ_CEILING` (256 MiB), and counting the inflated log blocks held at once (one per iterator) against `REFTABLE_HELD_CEILING` (128 MiB) (a log block may exceed the header's block size: JGit writes them twice its ref block size). `createReftableStackReader` re-reads `tables.list` each call (a listed table gone or read short, a concurrent compaction's, reloads the list while it changed, as `reftable_stack_reload_maybe_reuse`: back-off, 3 s once past 3 tries; unchanged, `ReftableFormatError`), refuses a name listed twice, update-index ranges that do not ascend (git's stack writer) and tables holding more than `REFTABLE_STACK_BYTES_CEILING` (512 MiB); its view merges lazily (lookups newest table first, listings and reflogs a binary heap as git's pq.c, `logHeads` decoding only the records no newer table hides); `getReflog` re-walks per call. Its own refs (HEAD, root refs, `refs/bisect/` ...) live in `<common>/worktrees/<id>/reftable` for a linked worktree (`GitLinkedWorktrees.refsOf`); `.git/HEAD` is a stub never read; FETCH_HEAD/MERGE_HEAD stay files. An index's lower levels come before its root (the footer's position), so sections are found by walking blocks, not from the footer alone. Writes (`ReftableRefStore` over `createReftableStackWriter`, `refs/reftable-backend.c`): one transaction per write, `tables.list.lock` taken (`reftable.lockTimeout`, 100 ms) before the plan is checked (`planRefBatch`; a root ref alone, no reflog), the hook told `preparing` (as asked) before the lock, `prepared` under it, `committed` after the list is renamed, `aborted` on a refusal (rolled back); one table per stack changed (a linked worktree's own refs go to its stack), refs at the next update index, reflog lines at it (own lines, `RefCommand.reflog`, at the indexes after it, git's `max_index`), a deleted ref's log one tombstone per entry; a no-op of HEAD's branch still logs HEAD (git does). `writeReftable` is `reftable/writer.c` byte for byte (padding dropped before the log section and at the end, an index from four blocks, obj blocks only with a ref index, every key without a shared prefix a restart) except the deflate of log blocks: pako (zlib 1.2.8) at level 9 picks other back references than the system's zlib 1.3, so twins compare log blocks inflated (`normalizedTable`). After each addition the stack compacts geometrically (`suggestCompactionSegment`, sizes less 23, `reftable.geometricFactor`; `$GIT_TEST_REFTABLE_AUTOCOMPACTION=false` off), table locks taken newest first, best effort, the merged table written as a `.temp.*` file and renamed to its `.ref` name only under the relocked list (a `.ref` file appears only while `tables.list.lock` is held, so no clean, ours or git's, can take it for stale); `packRefs`/`optimize`/gc compact all and remove unlisted tables (`clean`, under the lock). A transaction over two stacks commits them in git's order (the stack of the ref asked for first), rolls back the rest when one fails, and reports a partial apply (`ReftablePartialCommitError`). Reflog expiry and `deleteReflogEntry` go through `expireReflog` (one table rewriting the whole log, an existence marker when empty, `--updateref` peeled, no hook), so gc's `expireReflogs` uses it on reftable; reachability (gc, repack, prune), reflog expiry and fsck read reflogs and worktree refs through `reflogNames`/`worktreeRefs`/`getReflog`, never `logs/`, from `repositoryStore()` whichever worktree runs them (fsck reads a linked worktree's HEAD as `worktrees/<id>/HEAD` there, never its stub file) (a linked worktree's store would miss the main worktree's HEAD, `refs/bisect/` and HEAD reflog). New repositories: `InitCommand.setRefFormat`, `$GIT_DEFAULT_REF_FORMAT`, `init.defaultRefFormat` (`feature.experimental`), git 3.0's `breakingChanges` default (`defaultRefFormat`); `.git/HEAD` (`ref: refs/heads/.invalid`) and `.git/refs/heads` (a file) are stubs, as git writes them, and `worktree add` writes the same stubs in the admin directory and HEAD into the worktree's stack. A reftable rename logs a deletion (new id null) and a creation: `getReflog` keeps both, as git's ref store counts them; `reflog show` hides the null one. - **SHA-256 repositories (T3a, T3b, T3c, T3d)**: the object format belongs to the store (`GitObjects.objectFormat`, `History.objectFormat`, `Blobs.objectFormat` (worktrees hash with it by default), `objectFormatOf(holder)`, `GitCommand.objectFormat`; vcs-utils `ObjectFormat`: raw/hex lengths, `nullId`, `emptyTreeId`, `emptyBlobId`, `signatureHeader`, `createHasher`): never hard-code 40/20, `"0".repeat(40)` or `EMPTY_TREE_ID` in code a SHA-256 repository reaches; raw tree parsers take an id length (`decodeTreeBytes({ idLength })`, `TreeEntryCursor(bytes, idLength)`, fsck's `IdShape`), ref stores check values with `isRefObjectId(value, format)` (SHA-1 by default). What has no SHA-256 path yet throws `UnsupportedObjectFormatError` (`assertSha1ObjectFormat`); SHA-256 reftables are supported (statewalker-root#280, see Reftable repositories; `init` writes `objectformat` before `refstorage` under `[extensions]`, as git). Transports (T3d) carry the facade's `objectFormat` (`formatOf(repository)`, vcs-transport `protocol/object-format.ts`): servers append `object-format=sha256` to v0 capabilities (before `agent=`; a SHA-1 repository's v0 advertisement keeps its bytes, git's clients assume SHA-1 without one) and name the hash in v2 (`v2ObjectFormatCapabilities`), an empty repository's `capabilities^{}` id is the format's null id; they refuse another client hash (v2 serve.c `mismatched object format: server <s>; client <c>`, receive-pack `error: unsupported object format '<c>'`) and read ids, shallow lines and the raw pack (`readRawPack(hashSize)`: REF_DELTA bases, trailer) in the repository's width. Clients read the advertisement in the server's format, echo it in ls-refs (ls-remote across formats succeeds, as git) and refuse fetch/push across formats as git (`checkObjectFormat` in `fetchPack`, send-pack after pre-push; `ObjectFormatMismatchError`). Compare null ids with `isNullId`/`isNullObjectId`, never `=== ZERO_OID` (vcs-transport's `ZERO_OID` is SHA-1's). A clone takes the remote's hash (`FetchClientOptions.onRemoteObjectFormat`): an empty destination of another format is reopened (`LinkedWorktrees.reopenWithObjectFormat`, `CloneResult.workingCopy`, adopted by `Git.clone()`) and the clone runs again; a hand-built `MemoryWorkingCopy` without `worktrees` cannot be reopened, so clone twins open ours through `openGitLinkedWorktrees`. Readers take the pack order from it (`PackFile.loadReverseIndex`, under `pack.readReverseIndex`) only when its positions follow the idx's offsets: git trusts any well-formed file (a swapped row makes native `repack -b` die with `bad offset for revindex`), ours computes the order instead. fsck checks it as `verify_reverse_indices` (`verifyReverseIndexFile`): 2.5x per source after the packs (object bit, not with `--connectivity-only`), 2.43 after the commit-graph and before the bitmaps (bit 0100, `--connectivity-only` too).
- **gc expires reflogs first**: `gc()` runs `git reflog expire --all` (`expireReflogs`: `gc.reflogExpire` 90 days, `gc.reflogExpireUnreachable` 30 days against the ref's tip (a HEAD's: every ref's), `gc.<pattern>.reflogExpire*` by wildmatch, `refs/stash` never unless a pattern names it, linked worktrees' logs as `worktrees/<id>/...`) before it lists what is reachable, unless both settings are `never` (`gcExpiresReflogs`). Tests whose reflog entries carry fixed 2023 dates (`1700000000`) and rely on them as roots pass `expireReflogs: false`, as native twins pass `-c gc.reflogExpire=never`. Twins date entries relative to the clock (`GIT_COMMITTER_DATE` of `now - n days`) and keep config cutoffs off the entries' exact ages (both gcs read their own clock). As git, pseudo-refs (`ORIG_HEAD`, `FETCH_HEAD`, `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `MERGE_AUTOSTASH`) are no roots (`rev-list --all` never lists them): what only they name is cruft, gone with `--prune=now`; prune (and `FileGcStrategy`) keeps what `rebase-apply/`/`rebase-merge/` `autostash`/`orig-head` name (2.44+'s `add_rebase_files`, `ReachabilityRoots.rebaseFiles`; not under 2.43 compatibility). Reflog expiry rewrites every reflog it reads as `files_reflog_expire` (each kept line `<tz>\t<message>`, a tab even before an empty message; a last line without its newline dropped)
- **Cruft packs in gc**: `gc()` follows `git gc` (`gc.cruftPacks`, default true): `repack({ cruft, cruftExpiration, maxCruftSize })` puts the unreachable objects of the replaced packs and the unreachable loose objects into a cruft pack (`writeCruftPacks`, `.mtimes` through `installPack({ mtimes })`, before the `.idx`), each with the newest time of its copies (loose mtime, pack mtime, an old cruft pack's `.mtimes`); with an expiration (`gc.pruneExpire`, read from the config when `pruneExpireMs` is not given) only objects strictly newer than it, plus what they reach outside the staying packs (kept with the expiration as time), as pack-objects' `enumerate_and_traverse_cruft_objects`. `--prune=now` (`pruneExpireMs: 0`) writes none (git's `repack -a`); `gc.cruftPacks=false` keeps the old `repack -A` path (objects loosened). Either way the loose prune keeps what a younger unreachable object reaches (git prune's `mark_recent`). `gc.maxCruftSize` splits by estimated entry sizes (min 1 MiB, as git); a pack over the limit is split again. Tests about loosened objects pass `cruftPacks: false`; cruft twins pin `gc.pruneExpire` to a number of seconds (both gcs then expire at one instant) and copy fixtures with `cp -a` (file times are the objects' times). Ours keeps the objects an unknown pack (installed during the walk) holds out of the cruft pack (git would copy those reached by the traversal)
- **`git.gc()` is git gc**: `GarbageCollectCommand` over a files repository (`history.packs`, `hooks.commonGitFile`) runs the store's `gc()` with its own pack-refs (`packRefsStep`, the reference-transaction hook) and `worktree prune` (`beforeObjects`/`afterObjects`): git 2.43 runs `worktree prune` and `rerere gc` (`rerereGc`, vcs-store-files `rerere-gc.ts`) after the repack and prune, 2.56 and master before them (`GcOptions.compatibility`, from the hook runner), so what only a pruned worktree reached is packed under 2.43 and cruft under 2.56. The repack is `-d -l` with `--cruft`/`-A`/`-a`, `--keep-pack` (`RepackOptions.keepPacks`: `--keep-largest-pack`, `gc.bigPackThreshold`; kept whatever `packKeptObjects` says), `-f --depth --window` (`--aggressive`, `gc.aggressiveDepth`/`Window`), and `--auto`'s incremental `repack -d -l --no-write-bitmap-index` unless there are more than `gc.autoPackLimit` packs (git's half-the-memory check for keeping the largest pack is not made: none is kept without a threshold); then `update-server-info` (`updateServerInfo`, which `repack()` runs too: `info/refs`, `objects/info/packs`, whose new packs git orders by pointer, so twins compare it as a count), prune (recent loose and recent packed objects, a cruft pack's by `.mtimes`, seed the walk that keeps old ones; `prune_shallow` drops shallow commits nothing reached; `tmp_*` expire with the prune expiry), `clean_pack_garbage` (a lone `.idx` and its siblings) and the commit-graph. `pack-refs` writes `packed-refs` even with nothing to pack. Twins: `tests/gc-native-twins*.test.ts` (`gcTwins` in `gc-native-twins-support.ts`: `cp -a` twins with worktree and alternates paths rewritten, compared whole twice: loose ids, packs by kind with cruft `.mtimes` (`EXPIRATION` for objects kept at the cutoff, which each gc computes from its own clock; before the second round both twins' packs written by the first are dated a day back alike, since a cruft pack dates objects found in a pack by the pack's mtime), `.keep`/`.promisor`/`.rev`/`.bitmap`, packed-refs, refs, reflogs, worktree admin files, `rr-cache`, `shallow`, commit-graph bytes, temporaries; native fsck --strict, `commit-graph verify` and `--test-bitmap` give ours what they give native's result). Native gc there gets `-c gc.reflogExpire=90.days.ago -c gc.reflogExpireUnreachable=30.days.ago` (2.56.x's swap); run them with 2.43 and 2.56.1 on `PATH`, and with a 3.0 build add `GIT_DEFAULT_REF_FORMAT=files` (bare twins pass `GIT_DIR`: `safe.bareRepository=explicit`). Deliberate divergences: a `.pack` without its `.idx` is removed after an hour (git leaves it); `-A`'s loosened objects get the current time (git gives them the pack's), so they outlive git's by up to the pack's age; `packed-refs.new` and quarantine directories are swept as before
- **gc under concurrent writers**: `gc()` locks as git's `lock_repo_for_gc` (`acquireGcLock`: `gc.pid.lock` exclusive, then `gc.pid` = `<pid> <host>` from `GitHostEnvironment.gcProcess`, `0 unknown` without; held while younger than 12 hours and of another host or a running pid, `force` overrides; a held `gc.pid.lock` is never taken over), so native gc and ours refuse each other with git's messages. Ours walks once before the repack where git's prune is a separate process walking again, so the prune re-walks when the refs moved, and both the prune (`gc()` and `FileGcStrategy.prune`) and the repack's pack removal re-stat right before unlinking (a write that found the object stored freshened it). Interleavings are tested deterministically (`tests/gc-concurrency.test.ts`: FilesApi proxies triggering on the move onto `objects/info/packs`, which marks the repack's end; note Node FilesApi paths reach a proxy with a leading `/`), native gc is paused by a `git` wrapper first on `GIT_EXEC_PATH` waiting before its `pack-refs`/`prune` children (`tests/gc-concurrency-native.test.ts`), and `tests/gc-crash.git.test.ts` kills gc at every mutating FilesApi call and checks native `fsck --strict`
- **Pack bitmaps**: `.bitmap` bits are pack order (`PackFile.packOrder()`, offsets sorted, or the `.rev`), entry positions and the name-hash cache idx order. `writePackBitmap` is byte-identical to git's for the same pack only when the listing matches: commits of one date stay in traversal order (glibc's qsort is a stable merge sort), a tag's name hash is its `tag` header (the revision walk names peeled tags so), a tree or blob's that of its first listed path (`packNameHash` hashes the path's bytes, `encodeGitPath` for non-ASCII, skipping only git's isspace bytes 9, 10, 13, 32), a tree or blob a ref names that of "" (git's pending objects, listed after the commits and before their trees; `listObjects({ tipPaths })` names the index's entries and cache-tree nodes as `--indexed-objects` does) (our `walkTree` yields a tree's blobs before its subtrees, git recurses in entry order: identical blobs at two paths can hash differently). 2.5x sorts entries oldest first, 2.43 newest first (`compatibility`); twins pick it from `git --version` and use distinct commit dates. `bitmapWalk` gives exactly reach(wants) minus reach(haves); the plain walk marks only the trees of edge commits (uninteresting parents of listed commits) and tree haves uninteresting, as git's, and may list more, so compare served packs by inclusion, or without haves. With haves none of which (tags peeled) is in the bitmapped pack, `listObjects` walks instead, as git's classic `prepare_bitmap_walk`. `pack.preferBitmapTips` gets a `/` appended in 2.5x, not in 2.43 (`isPreferredBitmapTip`). A bitmap the new pack cannot close fails the repack (`BitmapWriteError`, git's warning plus `fatal: failed to write bitmap index`) before anything is replaced, the new pack removed. `repack.packKeptObjects` defaults to whether a bitmap is asked for. `exportPack` leaves bitmaps out for shallow receivers and thin packs with haves (thin bases come from the walk's boundary). fsck checks bitmap checksums per source in 2.5x (object bit), at the very end in 2.43 (exit bit 0200, `--connectivity-only` too). A bitmap with a wrong trailer or pack checksum is refused on open (git checks only in fsck), and so is one whose bit size or runs exceed the pack's object count (crafted files in served repositories); readers mask bits at or above the count
- **Multi-pack-indexes**: native git reads a midx-covered pack only through `objects/pack/multi-pack-index` (or 2.5x's `multi-pack-index.d/` chain), so every code path that deletes packs clears a midx naming them first (`clearMultiPackIndexNaming`, git's `repack_remove_redundant_pack`: the midx, its `multi-pack-index-*.bitmap`/`.rev`, and the chain unless an incremental layer was written); repack and `PackSet.remove` do, and `repack({ writeMidx })` writes the new midx (`--stdin-packs`, the new pack preferred) before removing anything. A midx naming a missing pack makes native fsck and `multi-pack-index verify` fail ("failed to load pack in position N") and native writes refuse to reuse it, while reads still find objects in packs outside it. `encodeMultiPackIndex` is byte-identical to git's only with git's discovery order: an existing valid midx's packs first (its entries count as mtime 0, so copies in other packs win), then the directory's `.idx` in readdir order (`listKinds({ readdirOrder: true })`), duplicates going to the preferred pack, then the newest mtime (seconds), then that order; 2.43 writes `RIDX` alone, 2.44+ `RIDX` and `BTMP`. Both versions leave an up-to-date midx unwritten (removing its bitmap without `--bitmap`); 2.43 exits 1 where 2.5x exits 255. A midx bitmap is a pack bitmap whose "pack" is the midx (`multiPackIndexBitmapPack`: checksum, `RIDX` order, midx positions), commits from a walk over every ref (peeled, commits only), every name hash 0 (`writePackBitmap({ nameTags: false })`); the pack set prefers it over pack bitmaps and refuses one whose header names another midx. Lookups ask a valid midx first only from three packs on (one pack reads 25% slower through it, thirty packs 2-3 times faster); a midx git refuses, a checksum mismatch (git trusts it and loses objects; ours falls back), or a stale one is not used (`PackSet.midxErrors`). fsck runs `multi-pack-index verify` per source in 2.5x (after the source's packs, object bit; a fatal load refusal dies 128), last in 2.43 (bit 040, `--connectivity-only` too), and checks the midx bitmap's checksum before the packs'. Tests that overwrite git's midx bitmaps or chain layers chmod them first (mode 0444). Deliberate divergences for safety: `multiPackIndexExpire` checks the checksum and that every pack still selecting objects opens before its first unlink (git unlinks the zero-count packs first, so with a midx naming a deleted pack it deletes the only copies left: we refuse with `error: could not load pack N`, also under 2.43, which says nothing), and a write reusing a midx whose pack is gone fails as 2.5x (`could not load pack N`) under 2.43 too (2.43 exits 0 and keeps the stale midx). Crafted midxes (served repositories): PNAM names must be `pack-<hex>.idx` (git joins `../` names into paths), chains are capped (`MAX_MIDX_CHAIN_LAYERS`, `MAX_MIDX_CHAIN_BYTES`) and walked in loops, `RIDX`/`BTMP` are checked before a midx bitmap is used, and a pack-int-id out of range (`badPackIntId`) makes the pack set ignore the midx while verify prints git's `fatal: bad pack-int-id: N (M total packs)` (exit 128); fsck dies (128) where git reads that object through the midx (2.5x: a ref tip at the snapshot; the walk's trees, or every non-blob with `--connectivity-only`), else only the verify child fails (2.43 bit 040, 2.5x object bit). `midx.version` (1 or 2, 2.5x) sets the version byte; 2.43 ignores the key and dies on a version 2 file
- **Partial clone filters (serving)**: upload-pack offers `filter` only with `uploadpack.allowFilter` (default off; `UploadPackFilterPolicy` from `explicitServerSettingsFromConfig`, also `uploadpackfilter.allow`/`.<choice>.allow`/`.tree.maxDepth`, read in config order); allow-list refusals go out as `ERR filter '<choice>' not supported` / `tree filter allows max depth N, but got M`, an unparsable spec or a second `filter` line ends the connection with no packet (git dies), and v0 needs the `filter` capability on the first want. `listObjects({ filter })` (vcs-core `pack/object-filter/`) follows list-objects.c exactly: wants and what their tags peel to are user given and always sent, except a want tree that is also a listed commit's root tree (do_traverse marks it `NOT_USER_GIVEN` first: git's walk omits it, its bitmap keeps it, so do ours); trees are walked entry by entry in tree order (never `walkTree`'s blobs-first order), since `tree:<depth>`, `sparse:oid` and `combine:` (each sub-filter with its own seen set) answer by order. Bitmaps apply only `canFilterBitmap` filters. `sparse:oid=<blob-ish>` is resolved by the facade (id, ref, `<rev>:<path>`) and parsed by `createRepositoryFacade({ sparseFilterPatterns: sparseFilterMatcher })`; a bad one fails the pack as pack-objects dies (`PackObjectsError`: `fatal:` on band 2, the abort with its NUL on band 3). A client whose server takes no filter gets git's warning and a full check. upload-pack serves a want of any object id it has in v2 (a lazy fetch's wants). Twins compare `rev-list --objects --all --missing=print` of native `clone --filter` from ours and from http-backend (`tests/serve-filter-native.test.ts`)
- **Partial clones (client)**: `fetchFromConnection({ filter })` keeps the pack and writes `pack-<id>.promisor` through the FilesApi (`markPromisorPack`; the sought refs, HEAD first on clone, for a kept pack, empty over smart HTTP v0 as remote-curl's fetch-pack writes it), and walks the new tips as `rev-list --exclude-promisor-objects` allowing absent objects only of the kinds the filter omits (`filterPromises`; a deepening fetch too): stricter than git, which trusts tips found in a promisor pack. `CloneCommand.setFilter` and `FetchCommand.setFilter` (partial_clone_register: `core.repositoryformatversion=1`, `remote.<name>.promisor`, `.partialclonefilter`; no `extensions.partialClone`, in 2.43 and 2.5x alike); a later fetch from a promisor remote uses its `partialclonefilter` (fetch_one_setup_partial), `setRefetch` is `--refetch` (no haves, every tip wanted; git's auto-maintenance hint after it is not run). `core.maxTreeDepth` (default 2048) bounds every `listObjects` tree walk, gc's too
- **Lazy fetch**: the files backend wraps its objects with `withLazyFetch` (`GitObjects.promisor`, vcs-core `object-promisor.ts`): `get`/`getNow`/`getRaw` of an absent id ask the installed `PromisorFetcher` once and read again (odb.c's single retry); `has` never fetches (`odb_has_object` without `FETCH_PROMISOR`), so code that checks `has` before reading an object a partial clone may lack must ask `blobs.mayFetch?.()` (tree-restore's planner) or read instead. Every `GitCommand` installs `createPromisorFetcher` (vcs-commands `promisor-remote.ts`) unless one is set; clone/fetch/pull/push (`TransportCommand`) install one from their own transports, credentials, headers and timeout for the length of their call (`aroundEntryPoints`) and put the previous one back, and library users set a store's for later commands with `installPromisorFetcher(workingCopy, { transports, credentials })`: promisor remotes in promisor_remote_init's order, each fetched as git's child `fetch <remote> --filter=blob:none --stdin` (`fetchPromisedObjects`: no ls-refs, no haves, kept promisor pack whose `.promisor` names `<id> <id>` only when kept by size), `could not fetch <id> from promisor remote` (`PromisorFetchError`, which the typed stores pass through) for a promisor object every remote failed; a fetch must bring every wanted id (else its quarantine is discarded and git's `fatal: bad revision '<id>'` / `error: <url> did not send all necessary objects` precede the death), and a read still absent after a fetch that succeeded throws `PromisorFetchError`, never a silent miss. The lazy fetch runs `fetch.fsckObjects`/`transfer.fsckObjects` as `--fsck-objects` (objects, not links) and, like every promisor-pack import (filtered fetch/clone too), git 2.48+'s `repack_local_links`: the local objects the received objects link to (commit tree/parents, tag object, subtrees) that are stored outside the promisor packs are walked as `pack-objects --exclude-promisor-objects-best-effort` (a commit in a promisor pack listed but not walked through, present blobs listed; a copy outside the promisor packs counts as outside) into one more promisor pack (`ObjectPromisor.localLinkObjects`, `RepositoryFacade.repackLocalLinks`), so gc keeps a pushed commit the server built on (2.43 has none: native 2.43 gc loses it; ours never does, `PromisorExclusions.roots` walks such objects as roots). `GIT_NO_LAZY_FETCH` (`GitHostEnvironment.noLazyFetch`, 2.45+, not under 2.43 compatibility): single reads fetch nothing, a batch warns `lazy fetching disabled; some objects may not be available` and dies. Batches are one fetch each, where git batches: `writeTreeRestorePlan` (check_updates: checkout, switch, reset, clone, merge results, stash), diff's patch/stat outputs before rename detection (`PREFETCH_FORMATS`, diffcore_std; `log -p` once per commit), `detectRenames({ prefetch })` before basename and inexact matching (status, diff, merge-ort), merge-ort's content merges (`prefetchForContentMerges`); blame and path checkouts fetch per blob, as git. Fetch, clone, fsck, gc, repack, the lazy fetch itself and served/received packs (upload-pack, receive-pack local and served) read through the store's view without lazy fetch (`fetch_if_missing = 0`): `objects.withoutLazyFetch` / `objectsWithoutLazyFetch`, `historyWithoutLazyFetch(history)` for facades, quarantines over it; never a store-wide switch, so a concurrent read elsewhere still fetches. Native git in a test that reads an object our in-process server must lazily send blocks the server under `spawnSync`: use `gitAsync`, or check our store's `has`. gc and repack exclude promisor objects (`promisorExclusions`: promisor-pack objects plus absent objects they name, `listObjects({ excludeObjects })` marking them as revision.c's `mark_uninteresting`), and `repack -a` writes the promisor packs' objects into a new promisor pack with an empty `.promisor` (both versions; `RepackResult.promisorPack`); `repack({ filter })` is `--filter` (the left-out objects in a pack beside it). fsck takes promisor objects as reachable without walking them and never missing (mark_object, check_reachable_object); a promisor pack object it cannot read is git's `fatal: packed object <id> (stored in <pack>) is corrupt`, exit 128 (`PromisorObjectReadError`, read in pack order: 2.5x asks at the walk's first object, 2.43 at its first missing one, else skips). `readRepositoryFormat` counts a remote with only `partialclonefilter` as a promisor remote (promisor_remote_config). Twins count `command=fetch` POSTs through one counting server (`tests/partial-clone-lazy-native.test.ts`)
- **Backfill, sparse-checkout clean, pulls into the void**: `git.backfill()` (`BackfillCommand`, 2.49+) is path-walk.c's walk with backfill's `fill_missing_blobs`: root trees of the walked commits (boundary commits' first, `--include-edges` default on), then paths from a priority queue (blob paths before tree paths, each in byte order, an object listed only at the first path met), each blob path's absent ids added to the batch and fetched (`ObjectPromisor.fetchObjects`, one promisor fetch) once it reaches `--min-batch-size` (default 50000), the rest at the end; `--sparse` (default `core.sparseCheckout`) skips paths outside the cone (non-cone patterns are matched with `includes`, broader than git's MATCHED-only blob check). - **Repository ownership (`safe.directory`)**: `discoverRepository` (vcs-store-files `safety/`) is git's setup discovery with `ensure_valid_ownership` and `safe.bareRepository`; `Worktree.openRepository` checks as `enter_repo` (receive-pack, http-backend, daemon) unless `checkOwnership: false`, which local fetch/ls-remote/`clone --no-local` pass (2.48+'s upload-pack: any owner) while a local push (`withLocalReceivePack`) and a local clone's copy (`checkOwnership({ gitDirOnly })`) check.
