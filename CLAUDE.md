# Claude Code Project Guidelines

## Project Overview

**webrun-vcs** is a pure-TypeScript Git implementation (read/write) organized as a pnpm monorepo.

Key packages: `vcs-core` (objects, refs, packfiles), `vcs-working-tree` (index, checkout, worktree), `vcs-commands` (porcelain API), `vcs-transport` (fetch/push protocols), `vcs-transport-lfs`/`vcs-transport-xet` (large objects), `vcs-store-*` (storage backends), `vcs-workspace` (file sync plus versioning).

Tech stack: TypeScript, Node.js 24, pnpm 10 workspaces (via corepack), Vitest (testing), Biome 2 (lint + format), Rolldown (bundling). Internal dependencies use `workspace:^`; external ones use the pnpm catalog (`catalog:`) in `pnpm-workspace.yaml`.

## General Behavior

Do not over-analyze or over-explore before acting. When the task is clear, start implementation immediately. Ask for clarification only when genuinely ambiguous.

## File Operations

When creating notes or documents, always confirm the target directory/path with the user before writing. Never assume the output location.

## Conventions

### Naming
All files and folders use **kebab-case**: `my-component.ts`, `utils/date-formatter.ts`

**[Full Guide](.claude/code/naming-conventions.md)**

### Portable APIs only
Library and app code (`packages/*/src`, `apps/*/*/src`) uses only APIs that exist in browsers and on servers: files through `FilesApi`, Web Streams, Web Crypto, `fetch`. No `node:*` imports (Biome `noNodejsModules` is an error there); tests may use Node (to drive native git, for example). On Node, get a `FilesApi` from `createNodeFilesApi` (`@statewalker/vcs-utils-node/files`). Every file operation goes through the `FilesApi`, symlinks included (`lstat`/`readlink`/`symlink` in its `PosixFilesApi` contract), so a composite or simulated FilesApi (`createSymlinkFilesApi`, `createMountedFilesApi`) works everywhere. The one exception to the no-`node:*` rule is the Node FilesApi itself in `packages/vcs-utils-node/src/files` (`posix-node-files-api.ts`, `replace-file.ts`). `git-host-environment.ts` may import `node:os` but not `node:fs`: it reads files through a FilesApi. The Biome overrides in `biome.json` list exactly these files, so any other `node:fs` use fails lint.

### Module Structure
Folder-based exports with wildcard re-exports. Import from `index.js`, use `.js` extensions.

```typescript

// ❌ import { foo } from "../delta/specific-file.js";
```

## Code Quality / Post-Edit Checks

After any refactoring or multi-file edit, run `tsc --noEmit` and fix ALL TypeScript errors (unused imports, type mismatches, missing extends) before reporting completion.

## Testing

When editing existing test files, NEVER overwrite/replace the entire file. Always append or surgically insert new tests alongside existing ones.

## Task Execution

When working from checklist/epic documents, complete ALL items listed — do not skip or forget items. Before reporting done, re-read the checklist and verify every item is addressed.

### Plan Mode
For multi-file features or architectural changes, start in plan mode. Iterate on the plan before switching to execution. Return to plan mode if implementation diverges significantly.

### Subagents
Use subagents for parallel independent subtasks (e.g., researching multiple packages simultaneously, running tests while editing). Keep the main context focused on the primary task.

When the user asks for structural consistency or formatting conformity in documents, apply it uniformly without arguing — even if some sections seem like they don't need it.

## Common Pitfalls

- **Import extensions**: Always use `.js` in imports, never `.ts` or extensionless
- **`git-cli-sandbox`**: `apps/demos/git-cli-sandbox/` is stale — ignore its test failures
- **`split()` limit**: `"a b".split(" ", 2)` gives `["a","b"]` not `["a","b c"]` — use `indexOf` + `slice`
- **Refs vs Checkout**: `CommitCommand` uses `history.refs`, not `checkout.head`
- **Apps are built without type checking**: vite builds `apps/*` even when they use removed APIs. After changing a package API, run `pnpm -r typecheck` (it covers the apps) and grep `apps/` for the old names.
- **Workspace cycles**: `vcs-core` depends on `vcs-utils-node`, and `vcs-testing` on `vcs-core`, so `vcs-utils`/`vcs-utils-node` must not depend on `vcs-testing` (not even as a devDependency): pnpm then builds in the wrong order and CI fails on missing declarations. Put such tests in a store package.
- **git's read-only files in tests**: git writes commit-graph files, packs and idx files mode 0444; tests run as root locally but CI does not, so a test that corrupts or rewrites one `chmodSync(path, 0o644)` first (else EACCES on CI). Check with `setpriv --reuid=65534 --regid=65534 --clear-groups env HOME=<tmp> TMPDIR=<tmp> node ../../node_modules/vitest/vitest.mjs run <test> --configLoader runner` (a world-writable temp dir, not the scratchpad)
- **`toEqual` on large byte arrays**: Vitest `toEqual` on `Uint8Array`s of hundreds of KB or more takes seconds and has caused CI timeouts; compare the bytes directly (length plus a loop, or `Buffer.equals` in tests)
- **Native git in tests**: CI has no `user.name`/`user.email`; pass `GIT_AUTHOR_*`/`GIT_COMMITTER_*` in the env of every git call, and fix both `GIT_AUTHOR_DATE` and `GIT_COMMITTER_DATE` when two repositories must produce the same commit ids
- **git versions differ**: CI runs a newer git (2.5x) than the sandbox (2.43); oracle tests that compare bytes with native git must pin config that changed defaults (e.g. `transfer.advertiseObjectInfo`) or normalise version-dependent lines
- **`GIT_CONFIG_GLOBAL=/dev/null` is read-only**: `nativeGitEnv` and most test environments point `GIT_CONFIG_GLOBAL` at `/dev/null`; a `git config --global` (or `git lfs install`, which writes global config) under it locks and renames a regular file over `/dev/null`, breaking every later process on the machine. A test that writes global config sets `GIT_CONFIG_GLOBAL` (or `HOME` with it unset) to a temp file; never run such a command by hand in that environment either. Check `ls -l /dev/null` still shows a character device
- **Background maintenance in native git**: git 2.5x runs `git maintenance run --auto --detach` after `commit` and similar commands; the detached process changes `.git/objects` while a test copies or reads the repository (CI fails with ENOENT). Set `maintenance.auto=false` and `gc.auto=0` (e.g. `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n`, as `nativeGitEnv` in vcs-commands tests does); a local `git push ../bare.git` starts receive-pack with `local_repo_env` cleared (`GIT_CONFIG_COUNT` too), so set them in the receiving repository's own config (`receive.autogc=false` as well) when a test copies it afterwards
- **Commit identities**: every commit/tag-creating command resolves its author and committer through `resolveAuthorIdent`/`resolveCommitterIdent` (vcs-commands `git-ident.ts`, git's `ident.c` order). Native-twin tests pass the same `GIT_AUTHOR_*`/`GIT_COMMITTER_*` to native git and, through `createNodeGitHostEnvironment({ env })`, to ours, instead of `setAuthor`/`setCommitter`
- **Merge-family twins**: `merge`/`cherry-pick`/`revert`/`rebase`/`pull` native tests build both twins with `buildHistory` (`tests/merge-native-scenarios.ts`) and compare `snapshot(..., normalizeState)` (`tests/merge-native-helpers.ts`); `normalizeState` evens out what 2.43 and 2.5x write differently in `rebase-merge/` (todo `# ` subjects, `message`). A refused `git merge` runs `restore_state` (reset --hard + `stash apply --index`), which leaves AUTO_MERGE and rewrites dirty files through smudge
- **`connection: close` in test HTTP servers**: Node 22's undici 6 asserts (`Parser.finish`, `!this.paused`) when the server closes the socket while the body consumer pauses on the final chunk; test servers keep connections alive and end them in `close()` (`closeAllConnections`)
- **Gitea oracle**: `GITEA=1 pnpm --filter @statewalker/vcs-testing-gitea test` runs a real Gitea (test infra; Node APIs allowed in that package via a biome override)
- **Sorted directory listings**: Node `fs.readdir`, and so FilesApi `list`, returns names sorted, so git behaviour that depends on filesystem order (readdir order of loose objects, reflogs) cannot be reproduced; tests sort such output
- **`git fsck` in 2.5x**: it runs `git refs verify` unless given `--no-references` (`FsckCommand` matches `fsck --no-references`), and dies under `--connectivity-only` on a corrupt packed object
- **Missing files in memory**: `createInMemoryFilesApi().read()` of a missing path yields no bytes instead of failing with ENOENT, so `tryReadFile` returns an empty array there; check `stats(path)?.kind === "file"` first when a missing file must read as absent
- **Commit-graphs and replace refs**: `git commit-graph write` disables replace refs and writes a graph anyway; `git gc` (in-process, replace refs on) writes none, and readers ignore a graph while `refs/replace/` has refs (`commitGraphCompatible`)
- **Bloom statistics differ by version**: git 2.5x asks a root commit's changed-path filter (`rev_same_tree_as_empty`), 2.43 does not, so trace2 `bloom/statistics` of one `git log -- <path>` differ by one check per root reached (`log-path-native.test.ts` allows for it)
- **Benchmarking**: measure the built bundles (`dist/`), not sources through tsx: its `keepNames` wraps every function in `__name` and skews profiles of hot closures. `node scripts/bench-porcelain.mjs <work-dir>` builds a wide and a long-history repository with native git and times status, commit -a, log -p and log --stat against it (median of fresh processes)
- **FilesApi reads in hot paths**: every `read` call resolves and lstats its path; on Node a range of at most 64 KiB is read synchronously, a longer one through libuv's thread pool (several round trips, idle time in profiles). Per-entry pack reads go through cached windows of at most 64 KiB (`PackedEntry.data()`, index-pack's `WindowReader`), never `files.read` per entry. `node scripts/bench-clone.mjs <dir>` times a clone's stages (pack generation, index-pack, checkout, end to end) against native git without bitmaps
- **Small typed arrays in hot paths**: `new Uint8Array(n)`/`new Int32Array(n)` above 64 bytes gets a backing store outside the heap (1–3 µs each, more than a small diff's loops); per-object or per-diff buffers come from `allocBytes`/`allocInt32` (vcs-utils `streams/`, slab views) or a reused scratch buffer. On Node, `fs.promises.lstat` with any concurrency is about ten times slower than `lstatSync` in a loop, so stat passes stay synchronous
- **FIFO/LRU eviction with `Map`**: `map.keys().next()` skips every slot deleted since the table was rebuilt, so evicting one entry per insert costs microseconds; use `OrderedMap` (vcs-utils) for caches that evict
- **Funcname patterns**: `diff.<driver>.xfuncname`/`funcname` and the builtin driver patterns are POSIX regexes; run them through `compilePosixRegex` (vcs-utils `regex/`), never a JavaScript `RegExp` (different semantics, catastrophic backtracking)
- **Tree modes**: the tree store reads modes canonical (`canonTreeMode`, git's `canon_mode`: a 100664 entry reads as 100644). Code that re-encodes a stored tree or must see the stored modes (fsck, serialization, sync) reads `trees.raw` and decodes it with `decodeTreeBytes(raw)`
- **Cache-tree after an index change**: a cache-tree written with the index must describe the resulting index. Build it from a tree only when the index equals that tree (`primeCacheTree`, as git's `prime_cache_tree`); otherwise invalidate every path where the index differs (`invalidateCacheTreeAgainstIndex`). `writeTree` reuses valid nodes, so a stale one silently drops staged changes from commits. `IndexFile` diffs the entries every cache-tree describes with the ones it writes: the one read or written (`TREE`) and a pending one from `setCacheTree` alike (the staging records the entries at set time), invalidating each path that changed since, so code that edits entries after (or without) setting a cache-tree needs no invalidation of its own; set a tree computed for the final entries after the edits (`rewriteIndex(..., { cacheTree })`), or the diff throws its valid nodes away. Intent-to-add entries are in no tree, skip-worktree or not (`update_one`); tests check a cache-tree with `verifyCacheTree`
- **Faking racy-git in fixtures**: `utimes` sets mtime but never ctime, and git (no `USE_NSEC`) compares ctime seconds under the default `core.trustctime=true`, so a fixture that dates files and the index to fake a racily clean entry still races the real clock through ctime under load (a stat mismatch skips the size-0 smudge in native git and ours alike); set `core.trustctime=false` in such fixtures
- **Ref values are checked**: every ref store refuses a direct value that is not a full lowercase hex object id (`isRefObjectId`, reason `invalid-object-id` in `planRefBatch`); a symbolic ref (HEAD at a branch) is written with `setSymbolic`, never `set("HEAD", "refs/heads/x")`, and test fixtures use real ids, not fakes. Commands that take a revision name resolve it before writing refs (as `rebase().setUpstream("main")` does now)
- **Path checkouts**: `checkout -- <paths>`, `restore` and `reset -- <paths>` share `checkout-paths.ts` / `read_from_tree` (builtin/checkout.c `checkout_paths`, builtin/reset.c) with full pathspecs through `pathspec.ts`; a path checkout that names nothing or hits an unmerged path writes nothing. git 2.43 stops a glob-looking element at an index entry of exactly that name (`x*y.txt`), 2.5x keeps matching: native twins of such elements are 2.5x-only
- **Unborn index**: with no `.git/index` (`clone --no-checkout`, `worktree add --no-checkout`) `isIndexUnborn(staging)` is true (no entries, update time 0: only Git/File stagings, never memory/KV/SQL); checkout/switch and two-tree `read-tree -m` then run git's `initial_checkout` (every target entry written, untracked files in the way still refused), everything else reads it as an empty index (status: HEAD's files staged as deleted). A switch naming no target leaves it unborn: `switch -c <new>`, `switch --detach`, and only the exact `git checkout -b <new>` (`setOnlyMergeOnSwitchingBranches`; `checkout -q -b <new>` merges). Never write an empty index where git writes none (a no-op `sparse-checkout set` there), or the next checkout stages deletions
- **Split and sparse indexes**: `IndexFile` reads a split index (`link`: `sharedindex.<id>` in the git directory, checksum checked, freshened on read, merged as `merge_base_index`) and a sparse index (`sdir`: each sparse directory expanded from its tree, the `TREE` extension turned into the full index's) itself, so a staging always holds the whole, merged, expanded index; any other lowercase extension is still refused (`UnsupportedIndexExtensionError`). Writes follow `write_locked_index` and `convert_to_sparse` through the staging's `IndexHost` (`setIndexHost`; commands install `indexHostOf` once per staging: `core.splitIndex`, `splitIndex.maxPercentChange`/`sharedIndexExpire`, `core.sharedRepository`, `index.sparse` with cone patterns, the trees); without a host a split index stays split and nothing is collapsed, and `FileStagingStore` expands a sparse index from the repository's own trees (`defaultTrees`). Which entries stay shared is git's `ce->index` kept beside the entry objects (`split-index.ts`): a new object at a path takes the previous entry's place (replacement when its data changed), except in an unpack-trees write (`markIndexUpdate(staging, { workdir: true })`: checkout, reset, merge, stash's reset) where a changed object or mode deletes the shared entry, and paths `markReaddedEntries` names (`git apply`'s remove-and-add). A sparse index read is re-collapsed into the same directories while they qualify (git's sparse-aware commands keep it collapsed, its cache-tree as edited); otherwise a full conversion stores the cache-tree's trees first (`storeCacheTree`, `WRITE_TREE_MISSING_OK`). An index written several times where git writes once ends up with extra shared indexes and other replacements: `withOneIndexWrite("last", body, { holdWrites: true })` holds them (`Staging.holdWrites`) and writes once (a whole-tree reset; never a body that reads the index back between its writes, as `reset -p` does). A status that only splits or unsplits still writes (`IndexFile.wantsRewrite`). gc and fsck read indexes through `readIndexFileEntries`. git 2.5x prints the `advice.sparseIndexExpanded` hint when sparse-checkout expands a sparse index (`--no-sparse-index`, non-cone patterns), 2.43 does not. Twins of index-writing commands compare stat-free structure (`ls-files`-like entries, link bitmaps, shared entries) across copies, or run both in one directory restoring `.git/index` and `sharedindex.*` between them for byte equality
- **Index flags**: one-way whole-tree index reads (reset, `checkout -f`, autostash) pass `readTree(..., { keepMatching })` so skip-worktree and assume-unchanged entries keep their flags, as git's `oneway_merge`; flagged entries are checked by stat only (`flaggedEntryDiffers`, `entryNotUptodate`), never by content
- **`FilesApi.move` returns false**: it reports failure by returning `false` (the Node FilesApi swallows the errno) instead of throwing; every caller must check the result, or code that then cleans up the source (as `mv` prunes empty source directories) deletes data after a failed move
- **Index lock across a commit**: `commit --only` and `commit -a` hold `staging.lockIndex()` from before they edit the index until HEAD has moved (git's `index_lock`); while it is held write through the lock (`write()`, then `commit()`/`rollback()`), never `staging.write()` (it fails with `IndexLockedError`), and give an `AddCommand` run inside it `setWriteIndex(false)`
- **Adding index entries**: stage paths through `IndexAdder` (vcs-commands `index-adder.ts`, git's `add_to_index`): it drops the stage-0 entries a new one clashes with as a file or directory and invalidates each touched cache-tree path; every `writeTree` refuses such clashes (`verifyTreePaths`) rather than storing a tree with two entries of one name. Code that builds entries itself (reset's `read_from_tree`, `read_tree_some`) drops clashes with `stageZeroClashes` (`has_file_name`/`has_dir_name` compare one stage: conflict stages of a clashing path stay), and every intent-to-add entry it creates stores the empty blob first (`set_object_name_for_intent_to_add_entry`), or native `write-tree`/`status` fail on the index
- **Worktree stat pass**: code that compares many index entries with their files stats them in batches (`withWorktreeEntries` / `getWorktreeEntries`, passing the entry to `compareWithWorktree`), not `getEntry` per path; untracked scans pass `skipFile` (the index's paths) to `walk`. A walk lists through `PosixFilesApi.listKinds` when present, so a FilesApi wrapper that overrides `list` (a test Proxy simulating an unreadable directory) must override `listKinds` too
- **Unreadable directories**: the Node FilesApi's `list` and `listKinds` both throw for a directory they cannot read (EACCES; a missing one lists nothing), and walks report it through `onUnreadable(path, error)`; commands turn that into git's "could not open directory" warning (`unreadableDirectoryWarning`). Tests run as root, which reads any directory: simulate unreadable ones with a FilesApi Proxy (or `vi.mock` of `readdir`), and take the expected lines from native git run as an unprivileged user (`setpriv --reuid=65534`)
- **Sparse checkout in index-writing commands**: a command that writes the index and the worktree together takes `SparseUnpack.start` before it changes anything and follows git's unpack-trees order: its checks and writes skip what `leavesAlone(path)` names (a skip-worktree or new entry staying outside the patterns: never checked for local changes or untracked files, never written or removed), it writes only paths `writes(path)` accepts, unlinks the files `leaving()` decides (verify_uptodate_sparse against the source index, before any write) with its own removals, and once its result is written calls `finish()` (flags, entries coming back into the patterns). Never write a file outside the patterns and remove it afterwards (`switchTrees`, `resetMerge`/`resetKeep`, `restoreWorktreeHard`, checkout and clone do this already). git repeats the patterns' "unrecognized pattern" warnings once per index it builds; ours prints them once per command. Conflicts are passed to `sparse.conflict()`: a conflicted path is written whatever the patterns say only where its source entry was skip-worktree or absent (merge-ort's `record_conflicted_index_entries` checks out a skip-worktree stage-0 entry); one leaving the checkout keeps `CE_WT_REMOVE` and is unlinked, its content left in the stages. `update_sparsity` runs without `o->internal.dir`, so `finish({ preserveIgnored })` treats ignored files as untracked there; elsewhere ask `await worktree.isIgnored(path)`, never a worktree entry's lazy `isIgnored` (it answers before the ignore files are read). A `.gitignore` missing from the worktree is read from its skip-worktree index entry (`setSkipWorktreeIgnoreReader`, git's `read_skip_worktree_file_from_index`)
- **Plumbing trusts the stat data**: `read-tree -m`'s `verify_uptodate` (and `mv`'s refresh) take a file whose stat no longer matches its entry as changed without reading it, so a native-twin test that copies a repository (`cp -a` changes ctime and inode) runs `git update-index -q --refresh` in each copy first; ours compares content there (`entryNotUptodate`) and would pass where unrefreshed git refuses. `setCacheTree(undefined)` drops the `TREE` extension from the next write (read-tree with conflicts writes none)
- **Status untracked modes**: `StatusCommand` defaults to git's `normal` mode (an untracked directory as `dir/`, empty ones hidden); code that needs every untracked file calls `setUntrackedFiles("all")`, and native-twin tests comparing with `git status -uall` must too. `scanUntracked` is dir.c's `read_directory` driven by the dir flags (`wt_status_collect_untracked`). git's normal-mode cache can keep showing `dir/` after the files below it go while the parent's stat stays (the parent's cached name outlives the `check_only` directory): compare a cached status with native git's cached one, not with an uncached run
- **Untracked cache (`UNTR`)**: ours uses and updates it for whole-tree scans without `--ignored` and pathspec, made for the scan's dir flags (0 for `-uall`, 6 for `-unormal`); a cache of other flags is replaced unless it is the configured mode's (`new_untracked_cache_flags`), which is kept untouched. `scanUntracked` (vcs-working-tree) follows dir.c's order, so it lists directories in readdir order (`listKinds(path, { readdirOrder: true })`; plain `readdirSync` sorts) and hashes a `.gitignore` as content plus `\n` unless an up-to-date index entry gives its id. `IndexFile` keeps `UNTR` across entry edits, invalidating the directory of each (path, stage) added or removed. Native-twin tests restore the index bytes and mtime between twins and date changed directories back to a second never used before: two changes in one mtime second are invisible to git's cache too
- **Status text and commit templates**: `StatusCommand.callText` (wt-status.c) and `CommitCommand.callDryRun` / `setEditor` share one formatter (`status-format.ts`); hints follow `determine_whence` (MERGE_HEAD, CHERRY_PICK_HEAD), not the state lines. `git commit` takes `--branch` but no `-b`, and has no `--porcelain=v2` or `--ignored`. git 2.43 writes the scissors line twice in a `--cleanup=scissors -v` template, 2.5x once. An empty config value is false to `parseGitBool`: read a boolean with a default as `value === undefined ? fallback : parseGitBool(value) ?? fallback`, never `parseGitBool(value ?? "")`
- **Nested repositories**: `FileWorktree` walks mark a directory `GITLINK` (and do not enter it) only when its `.git` names a repository (`is_nonbare_repository_dir`, or cannot be checked) and does not resolve to the superproject's own git directory (`treat_directory`'s realpath check); an empty `.git` directory or a gitfile of garbage is walked as any other directory. Code that removes such directories walks with `enterNonRepositoryGitDirs` and removes with `nonRepositoryGitDirs` (as clean and `stash -u` do). Inner `git status` runs mirror git's child flags: `rm` of a submodule `-uall`, `is_submodule_modified` the submodule's own mode (`-uno` when ignoring untracked), `worktree remove` the worktree's own mode
- **Submodule summaries**: `diff --submodule=log|diff`, `status.submoduleSummary` and `SubmoduleSummaryCommand` share `submodule-summary.ts` (submodule.c's header and first-parent left/right walk). Header ids use the superproject's abbreviation, `git submodule summary` the submodule's (`rev-parse --short` run there), else the first 7 digits. Its list is `diff-index --ignore-submodules=dirty`, which overrides `submodule.<name>.ignore` and `diff.ignoreSubmodules` (only `--for-status` skips `ignore=all`), and without `--cached` reports an entry whose submodule HEAD moved even when it is back at the tree's commit. git has no "(not checked out)" line: a submodule not checked out is opened from `.git/modules/<name>`. `format-patch` and plumbing patches ignore `diff.submodule`
- **Hooks**: hooks run only through `GitHostEnvironment.hookRunner` (Node: `createNodeHookRunner` in vcs-utils-node `files/node-hook-runner.ts`, the one file there allowed `node:child_process`); with none set, no hook runs. Commands find and run them through `this.hooks` (`HookSession`, vcs-commands `git-hooks.ts`: `find_hook` over `Worktree.getFiles`, `core.hooksPath`, the `advice.ignoredHook` hint, `GIT_PREFIX`), and a command running another passes `shareHooksOf(this)` so one `getHookOutput()` gathers both. Wired: commit (`commitPrepared`/`runMessageHooks`/`finishCommit`), merge (`mergeCommitHooks`, post-merge in `call`), checkout/switch/restore/clone/worktree add (`runPostCheckoutHook`), rebase (`begin`, `commitOnto`, the end of `processTodo`), the sequencer (`sequencerPrepareMessage`/`sequencerPostCommit`), am (`runAmHook`), push (`runPrePush` via `PushClientOptions.prePush`), the receive side of a local push (`scriptReceiveHooks`/`pushToCheckout` in `local-transport.ts`, with `relayPostReceive`), and `reference-transaction` in the files ref store's `batch` and `remove` of `refs/...` (`FileRefStore.setTransactionHook`, installed by `GitCommand.refsStore` while the command's `call*` runs, the previous hook put back after; the receive side installs the remote's in `withLocalReceivePack`): the root refs git updates in transactions (`isRootRefName`: ORIG_HEAD, CHERRY_PICK_HEAD, ...; AUTO_MERGE marked `only: "2.56"`, 2.43 writes it as a file) run it from `set`/`remove` too, so commands delete them where git does (`OperationState.deleteRef` for git's unconditional deletions: AUTO_MERGE after every commit, reset and branch switch); `setSymbolic` runs it as 2.5x's `refs_update_symref` (`<zero> ref:<target> <ref>`, marked `only: "2.56"`: 2.43 writes symrefs outside transactions); linked-worktree refs run it too (`WorktreeRefs.setTransactionHook` installs it on the worktree's own store and on the repository's, an update through the worktree's HEAD told as `HEAD` in `preparing`; - **Multi-pack-indexes**: native git reads a midx-covered pack only through `objects/pack/multi-pack-index` (or 2.5x's `multi-pack-index.d/` chain), so every code path that deletes packs clears a midx naming them first (`clearMultiPackIndexNaming`, git's `repack_remove_redundant_pack`: the midx, its `multi-pack-index-*.bitmap`/`.rev`, and the chain unless an incremental layer was written); repack and `PackSet.remove` do, and `repack({ writeMidx })` writes the new midx (`--stdin-packs`, the new pack preferred) before removing anything. A midx bitmap is a pack bitmap whose "pack" is the midx (`multiPackIndexBitmapPack`: checksum, `RIDX` order, midx positions), commits from a walk over every ref (peeled, commits only), every name hash 0 (`writePackBitmap({ nameTags: false })`); the pack set prefers it over pack bitmaps and refuses one whose header names another midx. Lookups ask a valid midx first only from three packs on (one pack reads 25% slower through it, thirty packs 2-3 times faster); a midx git refuses, a checksum mismatch (git trusts it and loses objects; ours falls back), or a stale one is not used (`PackSet.midxErrors`). fsck runs `multi-pack-index verify` per source in 2.5x (after the source's packs, object bit; a fatal load refusal dies 128), last in 2.43 (bit 040, `--connectivity-only` too), and checks the midx bitmap's checksum before the packs'. Tests that overwrite git's midx bitmaps or chain layers chmod them first (mode 0444). Deliberate divergences for safety: `multiPackIndexExpire` checks the checksum and that every pack still selecting objects opens before its first unlink (git unlinks the zero-count packs first, so with a midx naming a deleted pack it deletes the only copies left: we refuse with `error: could not load pack N`, also under 2.43, which says nothing), and a write reusing a midx whose pack is gone fails as 2.5x (`could not load pack N`) under 2.43 too (2.43 exits 0 and keeps the stale midx). Crafted midxes (served repositories): PNAM names must be `pack-<hex>.idx` (git joins `../` names into paths), chains are capped (`MAX_MIDX_CHAIN_LAYERS`, `MAX_MIDX_CHAIN_BYTES`) and walked in loops, `RIDX`/`BTMP` are checked before a midx bitmap is used, and a pack-int-id out of range (`badPackIntId`) makes the pack set ignore the midx while verify prints git's `fatal: bad pack-int-id: N (M total packs)` (exit 128); fsck dies (128) where git reads that object through the midx (2.5x: a ref tip at the snapshot; the walk's trees, or every non-blob with `--connectivity-only`), else only the verify child fails (2.43 bit 040, 2.5x object bit). `midx.version` (1 or 2, 2.5x) sets the version byte; 2.43 ignores the key and dies on a version 2 file
- **Partial clone filters (serving)**: upload-pack offers `filter` only with `uploadpack.allowFilter` (default off; `UploadPackFilterPolicy` from `explicitServerSettingsFromConfig`, also `uploadpackfilter.allow`/`.<choice>.allow`/`.tree.maxDepth`, read in config order); allow-list refusals go out as `ERR filter '<choice>' not supported` / `tree filter allows max depth N, but got M`, an unparsable spec or a second `filter` line ends the connection with no packet (git dies), and v0 needs the `filter` capability on the first want. `listObjects({ filter })` (vcs-core `pack/object-filter/`) follows list-objects.c exactly: wants and what their tags peel to are user given and always sent, except a want tree that is also a listed commit's root tree (do_traverse marks it `NOT_USER_GIVEN` first: git's walk omits it, its bitmap keeps it, so do ours); trees are walked entry by entry in tree order (never `walkTree`'s blobs-first order), since `tree:<depth>`, `sparse:oid` and `combine:` (each sub-filter with its own seen set) answer by order. Bitmaps apply only `canFilterBitmap` filters. `sparse:oid=<blob-ish>` is resolved by the facade (id, ref, `<rev>:<path>`) and parsed by `createRepositoryFacade({ sparseFilterPatterns: sparseFilterMatcher })`; a bad one fails the pack as pack-objects dies (`PackObjectsError`: `fatal:` on band 2, the abort with its NUL on band 3). A client whose server takes no filter gets git's warning and a full check. upload-pack serves a want of any object id it has in v2 (a lazy fetch's wants). Twins compare `rev-list --objects --all --missing=print` of native `clone --filter` from ours and from http-backend (`tests/serve-filter-native.test.ts`)
- **Partial clones (client)**: `fetchFromConnection({ filter })` keeps the pack and writes `pack-<id>.promisor` through the FilesApi (`markPromisorPack`; the sought refs, HEAD first on clone, for a kept pack, empty over smart HTTP v0 as remote-curl's fetch-pack writes it), and walks the new tips as `rev-list --exclude-promisor-objects` allowing absent objects only of the kinds the filter omits (`filterPromises`; a deepening fetch too): stricter than git, which trusts tips found in a promisor pack. `CloneCommand.setFilter` and `FetchCommand.setFilter` (partial_clone_register: `core.repositoryformatversion=1`, `remote.<name>.promisor`, `.partialclonefilter`; no `extensions.partialClone`, in 2.43 and 2.5x alike); a later fetch from a promisor remote uses its `partialclonefilter` (fetch_one_setup_partial), `setRefetch` is `--refetch` (no haves, every tip wanted; git's auto-maintenance hint after it is not run). `core.maxTreeDepth` (default 2048) bounds every `listObjects` tree walk, gc's too
- **Lazy fetch**: the files backend wraps its objects with `withLazyFetch` (`GitObjects.promisor`, vcs-core `object-promisor.ts`): `get`/`getNow`/`getRaw` of an absent id ask the installed `PromisorFetcher` once and read again (odb.c's single retry); `has` never fetches (`odb_has_object` without `FETCH_PROMISOR`), so code that checks `has` before reading an object a partial clone may lack must ask `blobs.mayFetch?.()` (tree-restore's planner) or read instead. Every `GitCommand` installs `createPromisorFetcher` (vcs-commands `promisor-remote.ts`) unless one is set; clone/fetch/pull/push (`TransportCommand`) install one from their own transports, credentials, headers and timeout for the length of their call (`aroundEntryPoints`) and put the previous one back, and library users set a store's for later commands with `installPromisorFetcher(workingCopy, { transports, credentials })`: promisor remotes in promisor_remote_init's order, each fetched as git's child `fetch <remote> --filter=blob:none --stdin` (`fetchPromisedObjects`: no ls-refs, no haves, kept promisor pack whose `.promisor` names `<id> <id>` only when kept by size), `could not fetch <id> from promisor remote` (`PromisorFetchError`, which the typed stores pass through) for a promisor object every remote failed; a fetch must bring every wanted id (else its quarantine is discarded and git's `fatal: bad revision '<id>'` / `error: <url> did not send all necessary objects` precede the death), and a read still absent after a fetch that succeeded throws `PromisorFetchError`, never a silent miss. The lazy fetch runs `fetch.fsckObjects`/`transfer.fsckObjects` as `--fsck-objects` (objects, not links) and, like every promisor-pack import (filtered fetch/clone too), git 2.48+'s `repack_local_links`: the local objects the received objects link to (commit tree/parents, tag object, subtrees) that are stored outside the promisor packs are walked as `pack-objects --exclude-promisor-objects-best-effort` (a commit in a promisor pack listed but not walked through, present blobs listed; a copy outside the promisor packs counts as outside) into one more promisor pack (`ObjectPromisor.localLinkObjects`, `RepositoryFacade.repackLocalLinks`), so gc keeps a pushed commit the server built on (2.43 has none: native 2.43 gc loses it; ours never does, `PromisorExclusions.roots` walks such objects as roots). `GIT_NO_LAZY_FETCH` (`GitHostEnvironment.noLazyFetch`, 2.45+, not under 2.43 compatibility): single reads fetch nothing, a batch warns `lazy fetching disabled; some objects may not be available` and dies. Batches are one fetch each, where git batches: `writeTreeRestorePlan` (check_updates: checkout, switch, reset, clone, merge results, stash), diff's patch/stat outputs before rename detection (`PREFETCH_FORMATS`, diffcore_std; `log -p` once per commit), `detectRenames({ prefetch })` before basename and inexact matching (status, diff, merge-ort), merge-ort's content merges (`prefetchForContentMerges`); blame and path checkouts fetch per blob, as git. Fetch, clone, fsck, gc, repack, the lazy fetch itself and served/received packs (upload-pack, receive-pack local and served) read through the store's view without lazy fetch (`fetch_if_missing = 0`): `objects.withoutLazyFetch` / `objectsWithoutLazyFetch`, `historyWithoutLazyFetch(history)` for facades, quarantines over it; never a store-wide switch, so a concurrent read elsewhere still fetches. Native git in a test that reads an object our in-process server must lazily send blocks the server under `spawnSync`: use `gitAsync`, or check our store's `has`. gc and repack exclude promisor objects (`promisorExclusions`: promisor-pack objects plus absent objects they name, `listObjects({ excludeObjects })` marking them as revision.c's `mark_uninteresting`), and `repack -a` writes the promisor packs' objects into a new promisor pack with an empty `.promisor` (both versions; `RepackResult.promisorPack`); `repack({ filter })` is `--filter` (the left-out objects in a pack beside it). fsck takes promisor objects as reachable without walking them and never missing (mark_object, check_reachable_object); a promisor pack object it cannot read is git's `fatal: packed object <id> (stored in <pack>) is corrupt`, exit 128 (`PromisorObjectReadError`, read in pack order: 2.5x asks at the walk's first object, 2.43 at its first missing one, else skips). `readRepositoryFormat` counts a remote with only `partialclonefilter` as a promisor remote (promisor_remote_config). Twins count `command=fetch` POSTs through one counting server (`tests/partial-clone-lazy-native.test.ts`)
- **Backfill, sparse-checkout clean, pulls into the void**: `git.backfill()` (`BackfillCommand`, 2.49+) is path-walk.c's walk with backfill's `fill_missing_blobs`: root trees of the walked commits (boundary commits' first, `--include-edges` default on), then paths from a priority queue (blob paths before tree paths, each in byte order, an object listed only at the first path met), each blob path's absent ids added to the batch and fetched (`ObjectPromisor.fetchObjects`, one promisor fetch) once it reaches `--min-batch-size` (default 50000), the rest at the end; `--sparse` (default `core.sparseCheckout`) skips paths outside the cone (non-cone patterns are matched with `includes`, broader than git's MATCHED-only blob check). Revisions go through `handle_commit`/`setup_pending_objects`: annotated tags peeled (`^v1`, `v1..main` exclude), a tree with a path (`HEAD:dir`) walked from `dir/`, a blob with a path fetched (a missing one first by a lazy fetch of its own, as `parse_object`), a blob by id or through a tag fetched (`/tagged-blobs`), a tree by id or through a tag not walked; `--all`/`--not` and `-- <path>` (history simplified as try_to_simplify_commit, exact pathspecs as path-walk compares them: `dir/` enters `dir` and fetches nothing below it, as git) are supported, other rev-list options and pathspec magic/wildcards refused (exit 128), never ignored. Twins record each request's wants behind http-backend. `sparse-checkout clean` (2.5x) removes, whole, every directory `sparseDirectoriesOf` collapses (convert_to_sparse in memory, whatever `index.sparse` says; unmerged entries, an empty index or non-cone patterns die; nothing at or below a directory holding an intent-to-add entry, whose cache-tree node `update_one` leaves invalid and `convert_to_sparse_rec` never enters, the root excepted; 2.43 lacks that check and collapses such directories, so twins with intent-to-add entries are 2.5x-only; a directory read sparse stays collapsed under such an entry, as git keeps a collapsed index), a sparse directory that is a symbolic link in the worktree passed over (git follows it and empties the directory it points to; ours keeps it, the safer choice), `Removing`/`Would remove` per directory or, with `-v`, per regular file in readdir order; it checks sparse and cone mode before parsing options, then `clean.requireForce`. `pull` on an unborn branch: with rebase and an index file (even one without entries) git dies `Updating an unborn branch with changes added to the index.` before fetching (`--autostash` too); otherwise `pull_into_void` (`MergeCommand.callIntoVoid`: a two-way switch from the empty tree, HEAD's branch created with reflog `initial pull`). `GcOrchestrator` takes `GcRoots.keep` (objects kept unwalked: `FileGcStrategy` passes a partial clone's `promisorExclusions().excluded`, and its `roots` as roots) and walks through `historyWithoutLazyFetch`, so it prunes partial clones as `git gc --prune=now` does for loose objects
- **Repository ownership (`safe.directory`)**: `discoverRepository` (vcs-store-files `safety/`) is git's setup discovery with `ensure_valid_ownership` and `safe.bareRepository`; `Worktree.openRepository` checks as `enter_repo` (receive-pack, http-backend, daemon) unless `checkOwnership: false`, which local fetch/ls-remote/`clone --no-local` pass (2.48+'s upload-pack: any owner) while a local push (`withLocalReceivePack`) and a local clone's copy (`checkOwnership({ gitDirOnly })`) check. Owners come from the FilesApi's `lstat().uid`, the user from `GitHostEnvironment.effectiveUid` (Node: `process.geteuid()`, `effectiveUid: null` turns it off); without either the check passes. `safe.*` is read only from `readProtectedConfig` (system, global, `$GIT_CONFIG_COUNT`/`$GIT_CONFIG_PARAMETERS` as `commandLineConfig`), never the repository's config; it is read without a git directory (`GitConfigOptions.withoutGitDir`: `gitdir:`/`gitdir/i:`/`onbranch:` false, `hasconfig:remote.*.url:` matched against those sources' remote URLs), only once an owner check fails or a bare repository is found, and command-line config git cannot parse is fatal there (`commandLineConfigError`, git's `unable to parse command-line config`). `openRepository` checks before it reads the repository's config or alternates; served refusals answer as git (HTTP 500 as `die_webcgi`, a dropped git:// connection). 2.43 compares `safe.directory` literally (no realpath, `/*`, `.`, warning) and has no implicit bare repositories (`.git`, `.git/worktrees/`, `.git/modules/`: 2.44/2.45); the sandbox's distribution 2.43 also refuses in upload-pack (ls-remote twins are 2.5x-only). Twins use `GIT_TEST_ASSUME_DIFFERENT_OWNER=1` (both honour it, any uid; it hits the native pusher's own repository too, so run it with `GIT_DIR`), and, as root, `setpriv --reuid=65534` against root's fixture with ours at `effectiveUid: 65534`. The 2.56 wrapper in a 0700 scratchpad is unreachable for uid 65534 (git silently falls back to `/usr/bin/git`): copy it to a world-readable directory first. Tests' FileWorktrees get no environment by default (`openOurs(..., worktreeEnvironment)`), so their local remotes are never checked
