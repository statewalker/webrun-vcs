# Claude Code Project Guidelines

## Project Overview

**webrun-vcs** is a pure-TypeScript Git implementation (read/write) organized as a pnpm monorepo.

Key packages: `vcs-core` (objects, refs, packfiles), `vcs-working-tree` (index, checkout, worktree), `vcs-commands` (porcelain API), `vcs-transport` (fetch/push protocols), `vcs-transport-lfs`/`vcs-transport-xet` (large objects), `vcs-store-*` (storage backends), `vcs-workspace` (file sync plus versioning).

Tech stack: TypeScript, Node.js 24, pnpm 10 workspaces (via corepack), Vitest (testing), Biome 2 (lint + format), Rolldown (bundling). Internal dependencies use `workspace:^`; external ones use the pnpm catalog (`catalog:`) in `pnpm-workspace.yaml`.

## General Behavior

Do not over-analyze or over-explore before acting. When the task is clear, start implementation immediately. Ask for clarification only when genuinely ambiguous.

## File Operations

When creating notes or documents, always confirm the target directory/path with the user before writing. Never assume the output location.

## Conventions

### Naming
All files and folders use **kebab-case**: `my-component.ts`, `utils/date-formatter.ts`

**[Full Guide](.claude/code/naming-conventions.md)**

### Portable APIs only
Library and app code (`packages/*/src`, `apps/*/*/src`) uses only APIs that exist in browsers and on servers: files through `FilesApi`, Web Streams, Web Crypto, `fetch`. No `node:*` imports (Biome `noNodejsModules` is an error there); tests may use Node (to drive native git, for example). On Node, get a `FilesApi` from `createNodeFilesApi` (`@statewalker/vcs-utils-node/files`). Every file operation goes through the `FilesApi`, symlinks included (`lstat`/`readlink`/`symlink` in its `PosixFilesApi` contract), so a composite or simulated FilesApi (`createSymlinkFilesApi`, `createMountedFilesApi`) works everywhere. The one exception to the no-`node:*` rule is the Node FilesApi itself in `packages/vcs-utils-node/src/files` (`posix-node-files-api.ts`, `replace-file.ts`), and the signer `node-signer.ts` (ssh-keygen's temporary files). `git-host-environment.ts` may import `node:os` but not `node:fs`: it reads files through a FilesApi. The Biome overrides in `biome.json` list exactly these files, so any other `node:fs` use fails lint.

## Code Quality / Post-Edit Checks

After any refactoring or multi-file edit, run `tsc --noEmit` and fix ALL TypeScript errors (unused imports, type mismatches, missing extends) before reporting completion.

## Testing

When editing existing test files, NEVER overwrite/replace the entire file. Always append or surgically insert new tests alongside existing ones.

A test ported from git's `t/` names its source as the script and the test's exact title, quoted, in the test name or a comment on the same line: `t0008-ignores.sh: "local ignore inside a sub-directory"` (several titles: `t7509 "--author", "--date"`). Native git still decides the expected result. `pnpm t-coverage` (`scripts/t-coverage.mjs`, git's `t/` at a pinned version) counts these citations per script and family, and lists the ones that name no title, several, or a script the pinned version lacks; paraphrased titles port nothing. CI's `git t/ coverage` workflow puts the report in the run's summary.

## Task Execution

When working from checklist/epic documents, complete ALL items listed — do not skip or forget items. Before reporting done, re-read the checklist and verify every item is addressed.

## Common Pitfalls

- **Import extensions**: Always use `.js` in imports, never `.ts` or extensionless
- **`git-cli-sandbox`**: `apps/demos/git-cli-sandbox/` is stale — ignore its test failures
- **`split()` limit**: `"a b".split(" ", 2)` gives `["a","b"]` not `["a","b c"]` — use `indexOf` + `slice`
- **Refs vs Checkout**: `CommitCommand` uses `history.refs`, not `checkout.head`
- **Apps are built without type checking**: vite builds `apps/*` even when they use removed APIs. After changing a package API, run `pnpm -r typecheck` (it covers the apps) and grep `apps/` for the old names.
- **Workspace cycles**: `vcs-core` depends on `vcs-utils-node`, and `vcs-testing` on `vcs-core`, so `vcs-utils`/`vcs-utils-node` must not depend on `vcs-testing` (not even as a devDependency): pnpm then builds in the wrong order and CI fails on missing declarations. Put such tests in a store package.
- **git's read-only files in tests**: git writes commit-graph files, packs and idx files mode 0444; tests run as root locally but CI does not, so a test that corrupts or rewrites one `chmodSync(path, 0o644)` first (else EACCES on CI). Check with `setpriv --reuid=65534 --regid=65534 --clear-groups env HOME=<tmp> TMPDIR=<tmp> node ../../node_modules/vitest/vitest.mjs run <test> --configLoader runner` (a world-writable temp dir, not the scratchpad)
- **`toEqual` on large byte arrays**: Vitest `toEqual` on `Uint8Array`s of hundreds of KB or more takes seconds and has caused CI timeouts; compare the bytes directly (length plus a loop, or `Buffer.equals` in tests)
- **Native git in tests**: CI has no `user.name`/`user.email`; pass `GIT_AUTHOR_*`/`GIT_COMMITTER_*` in the env of every git call, and fix both `GIT_AUTHOR_DATE` and `GIT_COMMITTER_DATE` when two repositories must produce the same commit ids
- **git versions differ**: CI runs a newer git (2.5x) than the sandbox (2.43); oracle tests that compare bytes with native git must pin config that changed defaults (e.g. `transfer.advertiseObjectInfo`) or normalise version-dependent lines
- **git 3.0 (`breakingChanges`)**: `GitHostEnvironment.breakingChanges` (`createNodeGitHostEnvironment({ breakingChanges: true })`) asks for a git built with `WITH_BREAKING_CHANGES` (`Documentation/BreakingChanges.adoc`); off, ours is git 2.5x. Its twins are `tests/*-git3-native.test.ts`, run against `$GIT3` (`tests/native-git3.ts`: `git3Binary()`, `nativeGit3Env()`; the `git3-oracle.yml` workflow builds git master with the flag) and skipped without it. Build one locally with `make WITH_BREAKING_CHANGES=YesPlease NO_GETTEXT=YesPlease NO_TCLTK=YesPlease NO_PERL=YesPlease NO_PYTHON=YesPlease NO_CURL=YesPlease prefix=<dir> install` and `GIT3=<dir>/bin/git`. Such a build creates reftable repositories on `main` but still SHA-1 objects (`read_repository_format` gives a new repository `GIT_HASH_SHA1_LEGACY`): follow the oracle, not BreakingChanges.adoc. What the switch changes: `init`'s initial branch (`defaultInitialBranch`: `init.defaultBranch` from the protected config, else `master`, `main` with the switch; `InitResult.hints` is git's advice), `safe.bareRepository`'s default (`explicit`), `core.commentChar=auto` refused in `checkConfigOnLoad` (`checkAutoCommentChar`, git's advice per config file). Grafts stay (the oracle still honours `info/grafts`). Legacy remotes: off, a remote the configuration gives no URL is read from `$GIT_COMMON_DIR/remotes/<name>` then `branches/<name>` (`loadLegacyRemote`, vcs-commands `legacy-remotes.ts`: remote.c's `read_remotes_file`/`read_branches_file`, `<url>[#<branch>]` fetching `refs/heads/<branch>:refs/heads/<name>`, pushing `HEAD:refs/heads/<branch>`, the branch `init.defaultBranch` else `master` with the hint, tags always followed: transport `TagMode` `auto-always`), its refspecs added after the configuration's; commands load it where git calls `remote_get` (fetch, pull, push, ls-remote, `@{upstream}`/`@{push}`, `remote rename`) and every `RemoteConfigStore` of the working copy then sees it (`isConfigured`, `legacyOrigin`; `configuredNames` stays config-only, as `for_each_remote`); 2.5x's deprecation warning goes to `FetchResult.messages`/`PushResult.warnings`/`RemoteRenameResult.warnings` (2.43 has none), `remote rename <n> <n>` migrates it (`migrate_file`) and another new name fails as `git_config_rename_section` (exit 1). With the switch on both files are never read (git 3.0); twins `tests/legacy-remotes-native.test.ts`
- **`GIT_CONFIG_GLOBAL=/dev/null` is read-only**: `nativeGitEnv` and most test environments point `GIT_CONFIG_GLOBAL` at `/dev/null`; a `git config --global` (or `git lfs install`, which writes global config) under it locks and renames a regular file over `/dev/null`, breaking every later process on the machine. A test that writes global config sets `GIT_CONFIG_GLOBAL` (or `HOME` with it unset) to a temp file; never run such a command by hand in that environment either. Check `ls -l /dev/null` still shows a character device
- **Background maintenance in native git**: git 2.5x runs `git maintenance run --auto --detach` after `commit` and similar commands; the detached process changes `.git/objects` while a test copies or reads the repository (CI fails with ENOENT). Set `maintenance.auto=false` and `gc.auto=0` (e.g. `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n`, as `nativeGitEnv` in vcs-commands tests does); a local `git push ../bare.git` starts receive-pack with `local_repo_env` cleared (`GIT_CONFIG_COUNT` too), so set them in the receiving repository's own config (`receive.autogc=false` as well) when a test copies it afterwards
- **Commit identities**: every commit/tag-creating command resolves its author and committer through `resolveAuthorIdent`/`resolveCommitterIdent` (vcs-commands `git-ident.ts`, git's `ident.c` order). Native-twin tests pass the same `GIT_AUTHOR_*`/`GIT_COMMITTER_*` to native git and, through `createNodeGitHostEnvironment({ env })`, to ours, instead of `setAuthor`/`setCommitter`
- **Signing**: requests to sign resolve through `signRequestOf` (`setSign`/`setSigningKey`, `commit.gpgSign`; tag `setSigned`/`setSigningKey`, `tag.gpgSign`, `tag.forceSignAnnotated`; push `setSigned`, `push.gpgSign`). `commit` (statewalker-root#288) and `tag` (statewalker-root#317) sign: `signCommit` → `signPayload` → `resolveSigning`/`signingConfigOf` (vcs-commands `signing.ts`, gpg-interface.c's `git_gpg_config`/`sign_buffer`: `gpg.format`, `gpg.program`/`gpg.<format>.program` in config order, `user.signingKey`, the committer's `Name <email>` as openpgp's default key, `gpg.ssh.defaultKeyCommand`, ssh without a key dies) hands a `SigningRequest` to `GitHostEnvironment.signer` and puts the signature, CRs before LFs stripped, in `gpgsig` (the store writes `gpgsig-sha256` in SHA-256 repositories); a tag appends it to its message (`TagCommand.signTag`, `do_sign`; `write_tag_body` drops it again through `signatureStart`). git 2.43's `sign_buffer_ssh` returns ssh-keygen's exit status, which its `do_sign` takes for success: under 2.43 compatibility a failing ssh-keygen leaves the tag unsigned, its error in `TagCreateResult.warnings` (`SigningOutcome.exitCode`). Signers: `createNodeSigner` (vcs-utils-node `files/node-signer.ts`, the one file there besides the hook runner allowed `node:child_process`, and allowed `node:fs` for ssh-keygen's temporary files) runs the program as git does and returns git's messages (`vfreportf`'s `?` for control characters is applied by `signPayload`); `createSshSigner` (vcs-commands `ssh-signer.ts`) signs Ed25519 in-process, ssh-keygen's bytes exactly. Commits the merge family leaves to `git commit` (`merge --continue`, an edited or resolved pick or revert) go through `CommitCommand` and sign too; the commits merge, the sequencer (pick, revert), rebase and am make themselves sign through `GitCommand.signedCommit` / `signCommit` (statewalker-root#319; a rebase step's `SigningFailedError` carries gpg's lines alone, each step adds what git says next; `merge --continue` signs by `commit.gpgSign` only, as git's plain `git commit`). With no signer, and for push certificates, every request to sign still fails where git's `commit_tree`/`build_tag_object`/`generate_push_cert` would sign, with git's lines for a gpg that fails without output (`refuseCommitSigning`, `SigningFailedError`), leaving the state git leaves (MERGE_HEAD, CHERRY_PICK_HEAD, a stopped or rescheduled rebase pick, `rebase-apply`). Twins: `tests/signing-native.test.ts`, `tests/tag-signing-native.test.ts` (a deterministic `gpg.program` script for byte equality, a throwaway GnuPG key in a temporary `GNUPGHOME`, an ssh-keygen Ed25519 key with `gpg.ssh.allowedSignersFile`; needs `gpg` and `ssh-keygen`, else skipped) and `tests/signing-refused-native.test.ts` (a `gpg.program` that exits 1); the rewrites' twins (`tests/rebase-gpg-sign-native.test.ts`, `tests/cherry-pick-revert-gpg-native.test.ts`, `tests/signed-merge-am-native.test.ts`, `signed-rewrites-native-support.ts`) run in ssh (byte for byte) and openpgp (gpg signatures carry their second, so commits are compared without `gpgsig` and parent ids, then verified)
- **Signature verification**: checks go through `GitHostEnvironment.verifier` (statewalker-root#318): vcs-commands `signature-check.ts` finds the signature (`parseBufferSignedByHeader` for a commit's `gpgsig`/`gpgsig-sha256`, `parseSignature` for a tag or mergetag), reads what `check_signature` reads (`signingConfigOf`: the program of the signature's format, `gpg.minTrustLevel`, `gpg.ssh.allowedSignersFile`/`revocationFile`; the committer's or tagger's date as ssh's verify time) and parses the verifier's raw output as `parse_gpg_output`/`parse_ssh_output`, so a verifier only runs programs (`createNodeVerifier` in `node-signer.ts`) or imitates ssh-keygen's lines (`createSshVerifier`, Ed25519 only; allowed-signers lines `sshsigopt_parse` refuses match nothing, never fail open; validity against now without a verify time; a blob with trailing bytes refused). No verifier: every check goes as git's when its program cannot run (`N` for openpgp, `B` for ssh). `Verifier.compatibility`: 2.43's `check_signature` takes only `G` as good, 2.5x also `Y` (expired key). Used by `verifyCommit`/`verifyTag` (no `verify-tag --format` yet), the `%G` placeholders (`PrettyFormatOptions.signature`; log passes it, rebase's instruction format still answers `N`/`E` unchecked), `log --show-signature` (`LogOutputOptions.showSignature`, `log.showSignature`, never in format-patch) and `merge`/`pull` `setVerifySignatures` (`verify_merge_signature`: reduced heads only, before ORIG_HEAD; a merge into an unborn branch with verification merges into the void; `gpg.minTrustLevel` set turns the marginal check off; `pull_into_void` checks for either `--[no-]verify-signatures`). Twins: `tests/verify-signatures-native.test.ts` (real throwaway GnuPG and ssh keys: good, bad, unknown, untrusted, expired, revoked, unsigned; run `gpg --check-trustdb` first or the first check prints the trustdb lines)
- **Merge-family twins**: `merge`/`cherry-pick`/`revert`/`rebase`/`pull` native tests build both twins with `buildHistory` (`tests/merge-native-scenarios.ts`) and compare `snapshot(..., normalizeState)` (`tests/merge-native-helpers.ts`); `normalizeState` evens out what 2.43 and 2.5x write differently in `rebase-merge/` (todo `# ` subjects, `message`). A refused `git merge` runs `restore_state` (reset --hard + `stash apply --index`), which leaves AUTO_MERGE and rewrites dirty files through smudge
- **`git merge-tree`**: `MergeTreeCommand` (vcs-commands `merge-tree-command.ts`, builtin/merge-tree.c) runs merge-ort through `mergeBaseTree`/`mergeStoredTrees` as `git merge` does, writing only objects (never refs, index or worktree); `--quiet` (2.5x) merges over `remergeObjectsView` so nothing is stored. Its messages come from `OrtMergeResult.details`: every `say(type, paths, text)` in `ort-merge.ts` gives merge-ort's `type_short_descriptions` type and the paths of its `path_msg` (primary first), which `-z` prints, and the omittable-hint flag (`--remerge-diff`) follows from the type: a new message must pass both. merge-tree's options are `init_basic_merge_options` (`merge.*`, `diff.renames`, the conflict style; no `diff.algorithm`); git 2.43's merge-ort detects renames whatever `diff.renames`/`merge.renames`/`-X no-renames` say, takes both branches as commits even with `--merge-base` (2.5x: tree-ishes), and splits `--stdin` lines otherwise (`setCompatibility`). The shared merge code reads a missing tree or blob as empty; merge-tree wraps its stores to die as 2.5x (`Could not read <tree>` + `collecting merge info failed`, `unable to read blob object`). Twins: `tests/merge-tree-native.test.ts` (t4301, t4300's trivial merge)
- **rerere**: `rr-cache/` and `MERGE_RR` are read and written only by vcs-commands `rerere.ts` (rerere.c: `runRerere`, `rerereClear`, `rerereForget`, `rerereStatus`/`Remaining`/`Diff`, `normalizeConflicts`; `git.rerere()` is builtin/rerere.c), byte for byte as git (conflict id: the repository's hash of each hunk's sides, the smaller first, NUL after each; replays are `ll_merge` with Myers, the preimage as base). Commands call `GitCommand.rerere()` where git calls `repo_rerere`: merge's `suggest_conflicts` (not an in-process merge; a rebase's octopus `git merge` does), a stopped pick of cherry-pick/revert/rebase (after the advice lines) and rebase's merges, am's three-way fallback and `--continue`, stash apply's conflict, and after every `CommitCommand` commit (so `--continue` commits record resolutions); `rerereClear()` on rebase `--skip`/`--abort` and am `--skip`/`--abort`/`--quit`. Results carry the lines as `rerereOutput` (am in `errors`). `--rerere-autoupdate` is kept as git keeps it: `sequencer/opts` `allow-rerere-auto`, `rebase-merge/allow_rerere_autoupdate`, `rebase-apply/rerere-autoupdate`. git before 2.45 segfaults in `rerere clear` (`rebase --abort`) when MERGE_RR names a conflict with no files left (read_rr's missing `fit_variant`): that twin compares with 2.45+ only. `GitResolutionStore` (vcs-store-files transformation API) writes rr-cache entries in a format of its own; no command uses it. Twins: `tests/rerere-native.test.ts` (t4200), `tests/rerere-merge-family-native.test.ts` (t3504, rebase, am, stash)
- **Merge messages**: every merge message comes from `FmtMergeMsgCommand` (fmt-merge-msg.c; `MergeCommand.mergeMessage`, pull through `setMergeNames` with its FETCH_HEAD line): never format `Merge branch ...` by hand. As git's `merge_msg` it has no final newline (MERGE_MSG gets one added on a stop, none before the hooks; `--cleanup=verbatim` commits it so), and `--signoff` is added only on the way to a commit (`prepare_to_commit`), never to a stopped merge's MERGE_MSG. git writes a merged annotated tag's object id to MERGE_HEAD, ours the commit (twins skip MERGE_HEAD there)
- **`connection: close` in test HTTP servers**: Node 22's undici 6 asserts (`Parser.finish`, `!this.paused`) when the server closes the socket while the body consumer pauses on the final chunk; test servers keep connections alive and end them in `close()` (`closeAllConnections`)
- **Gitea oracle**: `GITEA=1 pnpm --filter @statewalker/vcs-testing-gitea test` runs a real Gitea (test infra; Node APIs allowed in that package via a biome override)
- **Sorted directory listings**: Node `fs.readdir`, and so FilesApi `list`, returns names sorted, so git behaviour that depends on filesystem order (readdir order of loose objects, reflogs) cannot be reproduced; tests sort such output
- **`git fsck` in 2.5x**: it runs `git refs verify` unless given `--no-references` (`FsckCommand` matches `fsck --no-references`), and dies under `--connectivity-only` on a corrupt packed object
- **Missing files in memory**: `createInMemoryFilesApi().read()` of a missing path yields no bytes instead of failing with ENOENT, so `tryReadFile` returns an empty array there; check `stats(path)?.kind === "file"` first when a missing file must read as absent
- **Commit-graphs and replace refs**: `git commit-graph write` disables replace refs and writes a graph anyway; `git gc` (in-process, replace refs on) writes none, and readers ignore a graph while `refs/replace/` has refs (`commitGraphCompatible`)
- **Bloom statistics differ by version**: git 2.5x asks a root commit's changed-path filter (`rev_same_tree_as_empty`), 2.43 does not, so trace2 `bloom/statistics` of one `git log -- <path>` differ by one check per root reached (`log-path-native.test.ts` allows for it)
- **Benchmarking**: measure the built bundles (`dist/`), not sources through tsx: its `keepNames` wraps every function in `__name` and skews profiles of hot closures. `node scripts/bench-porcelain.mjs <work-dir>` builds a wide and a long-history repository with native git and times status, commit -a, log -p and log --stat against it (median of fresh processes)
- **Benchmark noise**: the sandbox VM varies by 10 to 15% between runs of the same build; compare two builds interleaved (A, B, B, A...) over 11 or more fresh processes, with the CPU time (`process.cpuUsage()`) beside the wall time, and keep a copy of the baseline's `packages/*/{dist,package.json,node_modules}` (relative pnpm links) to run it from. A change that does not beat that noise is dropped. A cold status's fixed cost is mostly the lstat syscalls (about 3 µs each in a fresh process, half that warm) and JIT warm-up: lstat without BigInt (`bigint: false`, exact seconds but not nanoseconds) and a directory cache in `lstatMany` measured no gain; git verifies the index trailer only in fsck (`verify_index_checksum`), so reads skip the hash, and nothing on a read-only path should call `crypto.getRandomValues` (its first call loads the runtime's crypto, several ms) Commit walks are bound by object reads (pack lookup, inflate, delta), not commit parsing: `commitFromBytes` (one native `TextDecoder` pass) costs about 1 µs per commit and a byte-by-byte JavaScript header parser is slower (`String.fromCharCode.apply` over subarrays)
- **Attribute lookups outside an operation**: a `Worktree.attributes`/conversion lookup made outside `Worktree.batch` opens a scope of its own, re-reading the configuration, `info/attributes` and every `.gitattributes` on the way, once per path. A command that prints or converts many paths runs inside one batch (`git log` and `DiffCommand.callBytes`/`callDiffstat` do); `git diff A B` of 200 files spent about a fifth of its time there
- **FilesApi Proxies inside `Worktree.batch`**: `FileWorktree.batch` runs over `files.withLstatCache()`, a new `PosixNodeFilesApi` of the same root, so a test Proxy around the FilesApi (one refusing `move`/`remove`, or counting `read`s) sees nothing a batched command does unless it wraps `withLstatCache` too. Attribute-read counting tests (`diff-one-operation`, `commands-one-operation`) therefore count only the reads made outside an operation; `mv` and `rm` stay unbatched (their failure-injection twins rely on the Proxy, and they hash only files whose stat changed)
- **FilesApi reads in hot paths**: every `read` call resolves and lstats its path; on Node a range of at most 64 KiB is read synchronously, a longer one through libuv's thread pool (several round trips, idle time in profiles). Per-entry pack reads go through cached windows of at most 64 KiB (`PackedEntry.data()`, index-pack's `WindowReader`), never `files.read` per entry. `node scripts/bench-clone.mjs <dir>` times a clone's stages (pack generation, index-pack, checkout, end to end) against native git without bitmaps
- **Small typed arrays in hot paths**: `new Uint8Array(n)`/`new Int32Array(n)` above 64 bytes gets a backing store outside the heap (1–3 µs each, more than a small diff's loops); per-object or per-diff buffers come from `allocBytes`/`allocInt32` (vcs-utils `streams/`, slab views) or a reused scratch buffer. On Node, `fs.promises.lstat` with any concurrency is about ten times slower than `lstatSync` in a loop, so stat passes stay synchronous
- **Type and size checks of packed objects**: `objectHeader`, `hasObjectOfType` (typed stores' `has`), `Blobs.size` and write-pack's planning read entry headers (`GitObjects.header`/`objectType`, git's `oid_object_info`) and fall back to `get` only when those answer undefined; never check a type or size through `get` in a loop (it applies the whole delta chain). A wrapper of `GitObjects` may pass `header`/`objectType` through only if they answer for nothing its `get` would not return. index-pack inflates a stream whole in one pass when it lies in the chunk at hand (`inflateWholeInChunk`); keep the streaming path as the fallback that reports errors. Benchmarks that build branches with native git under a fixed `GIT_COMMITTER_DATE` give them the oldest date, and date-ordered walks (merge bases, upload-pack's commit walk) then read the whole history, in native git too: date such commits after their parents
- **FIFO/LRU eviction with `Map`**: `map.keys().next()` skips every slot deleted since the table was rebuilt, so evicting one entry per insert costs microseconds; use `OrderedMap` (vcs-utils) for caches that evict
- **Commit filters (`--grep`, `--author`, `--committer`)**: the walk's show/hide stage is `LogCommand.addCommitFilter` (`CommitFilters` and/or/not, vcs-commands `rev-filter/`), applied in the walk's `shown()` (git's `get_commit_action`) so `-n`/`--skip` count shown commits and graph/topo output see it; filters keeping state per commit (`-L`) implement `CommitFilter` there, never in one command; pickaxe is not one (see Pickaxe). git's options compile to one `compileCommitGrep` (grep.c over the raw commit: header patterns only on `author `/`committer ` lines up to the last `>`, message patterns from the empty line on, the `--all-match`/`--invert-grep` hit-marker passes), not to and/or of separate filters. - **Reftable repositories**: `extensions.refStorage = reftable` opens; `createGitFilesBackend` gives it a `ReftableRefStore` (vcs-store-files `refs/reftable/`): a lazy reader as git's `reftable/reader.c`. `openReftable` checks only the header, footer CRC and section positions; `getRef` seeks through the ref index (its top level may span several blocks, walked linearly) or the blocks' first keys, then a block's restarts; `refs(prefix)`/`logs(refName)` are generators decoding one block at a time (log blocks inflated one at a time, exactly to their length), keys rebuilt in one scratch buffer; `verify()` walks every block (fsck). Every decoded block, restart and record is bounds-checked (`ReftableFormatError`). SHA-256 repositories use version 2 tables with hash id `s256` (28-byte header, 72-byte footer, 32-byte ids and obj keys; git's `writer_version`: SHA-1 stays version 1): the store, stack reader and writer are told the repository's `objectFormat` (`ReftableRefStoreOptions.objectFormat`, `createReftableStackReader(files, dir, { objectFormat })`, `ReftableWriteOptions.objectFormat`, `openReftable(bytes, name, { objectFormat })`) and refuse a table of another hash as git's merged table does (`ReftableFormatError`, "corrupt reftable file"; native reads then see no refs, writes die `reftable: transaction prepare: corrupt reftable file`); compaction's size overhead is the header less one (23, or 27). obj_id_len (common prefix + 1) has 5 bits: ids sharing 31 bytes would overflow it in git too, so tests use real hashes, never ids that differ only at the end. No budget is relative to the file (`reflog expire` writes tombstones deflated below a byte each): each call gets a `ReftableReadBudget` charging records visited, restart tables checked, names and values materialised and an eighth of inflated bytes against `REFTABLE_READ_CEILING` (256 MiB), and counting the inflated log blocks held at once (one per iterator) against `REFTABLE_HELD_CEILING` (128 MiB) (a log block may exceed the header's block size: JGit writes them twice its ref block size). `createReftableStackReader` re-reads `tables.list` each call (a listed table gone or read short, a concurrent compaction's, reloads the list while it changed, as `reftable_stack_reload_maybe_reuse`: back-off, 3 s once past 3 tries; unchanged, `ReftableFormatError`), refuses a name listed twice, update-index ranges that do not ascend (git's stack writer) and tables holding more than `REFTABLE_STACK_BYTES_CEILING` (512 MiB); its view merges lazily (lookups newest table first, listings and reflogs a binary heap as git's pq.c, `logHeads` decoding only the records no newer table hides); `getReflog` re-walks per call. Its own refs (HEAD, root refs, `refs/bisect/` ...) live in `<common>/worktrees/<id>/reftable` for a linked worktree (`GitLinkedWorktrees.refsOf`); `.git/HEAD` is a stub never read; FETCH_HEAD/MERGE_HEAD stay files. An index's lower levels come before its root (the footer's position), so sections are found by walking blocks, not from the footer alone. Writes (`ReftableRefStore` over `createReftableStackWriter`, `refs/reftable-backend.c`): one transaction per write, `tables.list.lock` taken (`reftable.lockTimeout`, 100 ms) before the plan is checked (`planRefBatch`; a root ref alone, no reflog), the hook told `preparing` (as asked) before the lock, `prepared` under it, `committed` after the list is renamed, `aborted` on a refusal (rolled back); one table per stack changed (a linked worktree's own refs go to its stack), refs at the next update index, reflog lines at it (own lines, `RefCommand.reflog`, at the indexes after it, git's `max_index`), a deleted ref's log one tombstone per entry; a no-op of HEAD's branch still logs HEAD (git does). `writeReftable` is `reftable/writer.c` byte for byte (padding dropped before the log section and at the end, an index from four blocks, obj blocks only with a ref index, every key without a shared prefix a restart) except the deflate of log blocks: pako (zlib 1.2.8) at level 9 picks other back references than the system's zlib 1.3, so twins compare log blocks inflated (`normalizedTable`). After each addition the stack compacts geometrically (`suggestCompactionSegment`, sizes less 23, `reftable.geometricFactor`; `$GIT_TEST_REFTABLE_AUTOCOMPACTION=false` off), table locks taken newest first, best effort, the merged table written as a `.temp.*` file and renamed to its `.ref` name only under the relocked list (a `.ref` file appears only while `tables.list.lock` is held, so no clean, ours or git's, can take it for stale); `packRefs`/`optimize`/gc compact all and remove unlisted tables (`clean`, under the lock). A transaction over two stacks commits them in git's order (the stack of the ref asked for first), rolls back the rest when one fails, and reports a partial apply (`ReftablePartialCommitError`). Reflog expiry and `deleteReflogEntry` go through `expireReflog` (one table rewriting the whole log, an existence marker when empty, `--updateref` peeled, no hook), so gc's `expireReflogs` uses it on reftable; reachability (gc, repack, prune), reflog expiry and fsck read reflogs and worktree refs through `reflogNames`/`worktreeRefs`/`getReflog`, never `logs/`, from `repositoryStore()` whichever worktree runs them (fsck reads a linked worktree's HEAD as `worktrees/<id>/HEAD` there, never its stub file) (a linked worktree's store would miss the main worktree's HEAD, `refs/bisect/` and HEAD reflog). Native git in a test that reads an object our in-process server must lazily send blocks the server under `spawnSync`: use `gitAsync`, or check our store's `has`. gc and repack exclude promisor objects (`promisorExclusions`: promisor-pack objects plus absent objects they name, `listObjects({ excludeObjects })` marking them as revision.c's `mark_uninteresting`), and `repack -a` writes the promisor packs' objects into a new promisor pack with an empty `.promisor` (both versions; `RepackResult.promisorPack`); `repack({ filter })` is `--filter` (the left-out objects in a pack beside it). fsck takes promisor objects as reachable without walking them and never missing (mark_object, check_reachable_object); a promisor pack object it cannot read is git's `fatal: packed object <id> (stored in <pack>) is corrupt`, exit 128 (`PromisorObjectReadError`, read in pack order: 2.5x asks at the walk's first object, 2.43 at its first missing one, else skips). `readRepositoryFormat` counts a remote with only `partialclonefilter` as a promisor remote (promisor_remote_config). Twins count `command=fetch` POSTs through one counting server (`tests/partial-clone-lazy-native.test.ts`)
- **Backfill, sparse-checkout clean, pulls into the void**: `git.backfill()` (`BackfillCommand`, 2.49+) is path-walk.c's walk with backfill's `fill_missing_blobs`: root trees of the walked commits (boundary commits' first, `--include-edges` default on), then paths from a priority queue (blob paths before tree paths, each in byte order, an object listed only at the first path met), each blob path's absent ids added to the batch and fetched (`ObjectPromisor.fetchObjects`, one promisor fetch) once it reaches `--min-batch-size` (default 50000), the rest at the end; `--sparse` (default `core.sparseCheckout`) skips paths outside the cone (non-cone patterns are matched with `includes`, broader than git's MATCHED-only blob check). Revisions go through `handle_commit`/`setup_pending_objects`: annotated tags peeled (`^v1`, `v1..main` exclude), a tree with a path (`HEAD:dir`) walked from `dir/`, a blob with a path fetched (a missing one first by a lazy fetch of its own, as `parse_object`), a blob by id or through a tag fetched (`/tagged-blobs`), a tree by id or through a tag not walked; `--all`/`--not` and `-- <path>` (history simplified as try_to_simplify_commit, exact pathspecs as path-walk compares them: `dir/` enters `dir` and fetches nothing below it, as git) are supported, other rev-list options and pathspec magic/wildcards refused (exit 128), never ignored. Twins record each request's wants behind http-backend. `sparse-checkout clean` (2.5x) removes, whole, every directory `sparseDirectoriesOf` collapses (convert_to_sparse in memory, whatever `index.sparse` says; unmerged entries, an empty index or non-cone patterns die; nothing at or below a directory holding an intent-to-add entry, whose cache-tree node `update_one` leaves invalid and `convert_to_sparse_rec` never enters, the root excepted; 2.43 lacks that check and collapses such directories, so twins with intent-to-add entries are 2.5x-only; a directory read sparse stays collapsed under such an entry, as git keeps a collapsed index), a sparse directory that is a symbolic link in the worktree passed over (git follows it and empties the directory it points to; ours keeps it, the safer choice), `Removing`/`Would remove` per directory or, with `-v`, per regular file in readdir order; it checks sparse and cone mode before parsing options, then `clean.requireForce`. `pull` on an unborn branch: with rebase and an index file (even one without entries) git dies `Updating an unborn branch with changes added to the index.` before fetching (`--autostash` too); otherwise `pull_into_void` (`MergeCommand.callIntoVoid`: a two-way switch from the empty tree, HEAD's branch created with reflog `initial pull`). `GcOrchestrator` takes `GcRoots.keep` (objects kept unwalked: `FileGcStrategy` passes a partial clone's `promisorExclusions().excluded`, and its `roots` as roots) and walks through `historyWithoutLazyFetch`, so it prunes partial clones as `git gc --prune=now` does for loose objects
- **`git pull`**: `PullCommand` is builtin/pull.c: one `git fetch [<remote> [<refspec>...]]` (configured refspecs when none is given; `setAll` runs `FetchMultipleCommand`; every connection through `GuardedTransportCommand`'s credential rule), then the FETCH_HEAD entries not `not-for-merge` are merged (`setMergeNames` with the whole file), rebased onto or pulled into the void; never resolve a tracking ref by hand.
