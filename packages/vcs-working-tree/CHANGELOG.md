# @statewalker/vcs-working-tree

## 0.6.0

### Minor Changes

- 09aa062: **Attributes and end-of-line conversion as git does them, and git's configuration chain.**
  
  - **vcs-working-tree:** `.gitattributes` are read as git's `attr.c` reads them (per-directory files, `$GIT_DIR/info/attributes`, `core.attributesFile` or `$XDG_CONFIG_HOME/git/attributes`, the system file; macros, the built-in `binary`, set / unset / `!attr` / values, no negative patterns), through `AttributesResolver`. `GitContentFilter` is git's `convert.c`: `text`, `text=auto`, `eol`, `crlf`, `-text`, `core.autocrlf`, `core.eol`, `core.safecrlf` (git's warnings and errors), the binary heuristics, the CRLF-in-index rule, renormalisation, `ident`, `working-tree-encoding` (UTF-16 / UTF-32 with git's BOM rules; other encodings fail as git's failed conversion does) and filter drivers registered by the host (`FilterDriver`; a missing required driver fails with git's message). A `Worktree` now has an optional content filter (`contentFilter`, `setContentFilter`): `computeHash` hashes a file as it is cleaned and `writeContent` smudges it (`raw: true` writes as is); `readContent` still gives the file as it is. `MemoryWorkingCopy` installs git's filter on its worktree (options `contentFilter`, `filterDrivers`, `environment`); `storeWorktreeFile` cleans (with `onWarning`, `renormalize`); `readCleanContent` reads a file as the repository would store it (`readConvertedContent` only when a conversion applies). `GitHostEnvironment` describes the user's global files for hosts that opt in.
  - **vcs-store-files:** `GitWorkingCopyConfig` reads git's chain: the system and global files (`$XDG_CONFIG_HOME/git/config`, `~/.gitconfig`) from an optional host `environment`, `include.path` and `includeIf` (`gitdir:`, `gitdir/i:`, `onbranch:`), and `config.worktree` with `extensions.worktreeConfig`; writes stay in the repository's file (`getLocal` reads only it). `FileWorktree` supports the content filter, `readGitDirFile` and a global excludes file read through the chain. `GitWorkingCopy` and the factory install git's filter.
  - **vcs-commands:** `add`, `commit -a`, `status`, `stash`, `checkout`, `reset --hard`, `clone` and `stash apply` clean and smudge content as git does. `AddCommand.setRenormalize` is `git add --renormalize`, `AddResult.warnings` holds git's line-ending warnings, and a tracked file whose stat still matches is no longer read again (as git's `add_to_index`).
  - **vcs-transport-lfs:** `createLfsFilterDriver` is git-lfs's clean / smudge as a filter driver (`filterDrivers: { lfs }`).
  - **vcs-utils-node:** `createNodeGitHostEnvironment` gives the user's environment (`HOME`, `XDG_CONFIG_HOME`) for hosts on Node.
  - **Which attributes a checkout reads:** a checkout of a tree (`checkout <branch>`, `reset --hard`, `stash`/`stash apply`, `clone`, `Worktree.checkoutTree`) smudges every file with the attributes of the index it leaves behind, as git's unpack-trees reads `o->result`: `.gitattributes` itself and files sorting before it get the target's rules. Writers pass it as `WorktreeWriteOptions.attributes` (`ContentAttributesContext`, built with `attributesIndexOf` / `attributesIndexOfTree`); a plain `writeContent` and `checkout -- <path>` read the worktree's `.gitattributes` first, as git does. `checkout -- <path>` now writes the file (and records the index). The filter no longer remembers what was written (`noteWritten` / `noteRemoved` are replaced by `noteChanged`, which only drops cached files).
  - **Speed:** the content filter reads its configuration and attributes files once per worktree batch (`WorktreeContentFilter.batch`, joined by `FileWorktree.batch` / `MemoryWorktree.batch`; `add` runs as one batch), keeps parsed files by blob id or stat, and skips a path at once when no attribute and no setting converts it.
  - **Fixes:** status rename detection reads a file cleaned once (its stat size when nothing converts it); `add --renormalize` fails on a deleted tracked file with git's message and renormalises without write flags (no `core.safecrlf`, a bad `working-tree-encoding` keeps the content); re-opening a working copy replaces git's filter installed by an earlier one. Linked worktrees read the repository's config plus their `config.worktree`; the factory passes the real git directory for `includeIf.gitdir:` (`rootPath`, default the FilesApi's `rootDirectory`); `GitWorkingCopyConfig.refresh()` re-evaluates `includeIf.onbranch:` after HEAD changes (the filter calls it per batch). `GitHostEnvironment.globalConfig` is `$GIT_CONFIG_GLOBAL`; `createNodeGitHostEnvironment` reads `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_NOSYSTEM`, `GIT_ATTR_NOSYSTEM` (option `env`) and defaults the system files to `/etc/gitconfig` and `/etc/gitattributes`.
- 8681320: **`diff.renames=copies` finds copies.** `git diff` and `git log` (`--stat`, `--name-status`, `--summary`, `-p`) detect copies as git's `diffcore_rename` does under DIFF_DETECT_COPY: modified paths are sources too, a source can be taken by several destinations (the last use of a deleted source is the rename, the others copies), no basename matches. `detectRenames` takes `copies` and sources marked `kept`, and its pairs say `copy`.
  
  **`git diff` of a conflict prints the combined diff first.** With several formats including the patch, the `diff --cc` of a conflicted path comes before the stat and summary of the other paths, as `run_diff_files` prints it.
  
  **`git bisect` checkouts.** The tracking report follows `status.compareBranches` (git 2.56: each of `@{upstream}` and `@{push}` compared once, a blank line between reports, `git pull <remote> <branch>` advice for a push ref behind), and `GIT_PRINT_SHA1_ELLIPSIS=yes` puts `...` after the ids of "HEAD is now at" and "Previous HEAD position was". `GitHostEnvironment` gains `printSha1Ellipsis`, which `createNodeGitHostEnvironment` reads from `GIT_PRINT_SHA1_ELLIPSIS`.
- 8a603c0: **Clean never removes what it has not walked: fake `.git` directories as git.**
  
  - **vcs-commands (data loss fix):** `clean -d`, `-dx` and `-X -d` no longer remove a directory holding a `.git` that is no repository whole and unwalked: like git's `remove_dirs`, they enter it (and the fake `.git`), skip the nested repositories in it ("Would skip repository", `-ff` removes them whole), remove the files one by one and the directories once empty. Recursive removal is used only for a nested repository under `-ff`. A directory whose listing failed is never removed. Plain `clean` now works on the same tree model as `-X`: a directory removed only in part reports its removed subdirectories without the trailing slash, as git.
  - **vcs-working-tree:** `WorktreeWalkOptions.enterNonRepositoryGitDirs` (list and enter a `.git` that names no repository) and `onUnreadable` (directories whose listing failed); `Worktree.remove` takes `WorktreeRemoveOptions` (`nonRepositoryGitDirs` accepts such `.git` components; a real repository's `.git` is still refused), `removeEmptyDirectory` too.
  - **vcs-store-files:** `FileWorktree` implements those options; a dangling `.git` link whose target lies inside the FilesApi is no repository (git removes its directory with `-d`).
- e306a5e: **Commit, tag and stash identities as native git resolves them.**
  
  - **vcs-commands:** one resolver for every commit and tag the porcelain makes: `resolveAuthorIdent(environment, config)` and `resolveCommitterIdent(environment, config)` follow git's `ident.c`. The name and email come from `GIT_AUTHOR_*` / `GIT_COMMITTER_*` (the host environment), then `author.name` / `author.email` or `committer.name` / `committer.email`, then `user.name` / `user.email`, then `$EMAIL` for the email, with git's crud trimmed. The date is `GIT_AUTHOR_DATE` / `GIT_COMMITTER_DATE`, else the clock in the local timezone offset. With `user.useConfigOnly`, a commit or annotated tag that the configuration names nobody for is refused with git's message (`IdentityUnknownError`). When nothing names anyone, the command's other, explicitly given identity is used, else `webrun-vcs <vcs@localhost>` (the ref stores' reflog identity). No commit is made by `Unknown` any more. `parseGitDate` reads every common form git's `parse_date` reads: raw `<seconds> <+-HHMM>`, `@<seconds>`, seconds alone (in the local offset of that time), RFC 2822, ISO 8601 (with an offset, `Z`, a zone name, or none, which means local time), git's own format, `YYYY.MM.DD`, `MM/DD/YYYY`. ISO and RFC dates keep their offset. An unreadable date is refused with `fatal: invalid date format: <date>` (`InvalidDateError`).
    - The per-command semantics follow git. **commit:** the author comes from `setAuthor` / `setAuthorIdent` or the resolver. `--amend`, and the commit that concludes a cherry-pick, keep the earlier author unless you call the new `setResetAuthor(true)`. `setAuthor(name, email)` replaces only the name and email (its date is the kept author's, else `GIT_AUTHOR_DATE` or now). The committer always comes from the resolver; before, it was the author. **merge (and the merge commit of `pull`):** the author and the committer each come from the resolver. **cherry-pick:** the picked commit's author is kept. **revert:** the resolver gives the author. **rebase picks:** the original author is kept, and the resolver gives the committer. `RebaseCommand.setCommitterDateIsAuthorDate` and `setIgnoreDate` give git's `--committer-date-is-author-date` and `--ignore-date`; both are kept in `rebase-merge/` across a stop and imply a forced rebase. **stash:** the author and the committer each come from the resolver, unless `setAuthor` is given. **tag -a:** the tagger comes from the committer resolver.
    - `GitCommand` gains `resolveAuthor`, `resolveCommitter`, `datedIdent` and `clock` for subclasses. `committerIdent` (reflog lines) now also reads `committer.*`.
  - **vcs-working-tree:** `GitHostEnvironment.author` carries git's author variables, and `defaultEmail` carries `$EMAIL`.
  - **vcs-utils-node:** `createNodeGitHostEnvironment` reads `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_AUTHOR_DATE` and `EMAIL`.
- 57846c3: **Faster fsck and commit-graph writing; the attribute source (`GIT_ATTR_SOURCE`, `git --attr-source`, `attr.tree`).**
  
  - **vcs-core:** `scanPackObjects` reads a pack once in pack order and unpacks only the objects of the types asked for (a delta takes its base's type, so blobs and their deltas are skipped unread; a REF_DELTA whose base is an earlier entry of the same pack is unpacked as an OFS_DELTA is; what it does not handle as it stands is left to the store, and a pack whose deltas mostly lack their base is not read further); `visit` returning false stops the read. With `packEntryOrder` (offsets sorted as numbers, no comparator), `parsePackEntryHead` and `packIdxLookups`. `writeCommitGraphFile` computing many changed-path filters (1024 or more) unpacks the trees of the newest packs that way first, newest first as the store orders packs, while the packs' objects fit in 32 per filter computed (a large pack a few new filters do not justify is skipped) and up to 256 MiB of trees (the read stops there), keyed by their id bytes (option `prefetch` tunes the three); the tree diff is synchronous while its trees are in memory (no generators), and commits are read without a promise when the store holds them. The files written are unchanged; `reads.treesScanned` counts the trees unpacked beforehand. `VerifyCommitSource` may answer without a promise.
  - **vcs-commands:** `fsck` keeps git's object hash with each id in its slot (one place in memory per probe) and every object's slot, so the lookups git makes again move an object without probing; a full run checks each pack with typed arrays in pack order and a FIFO cache of bases carved from slabs; a `--connectivity-only` run unpacks each pack's commits and trees in one read in pack order (`statistics.objectsScanned`, REF_DELTA packs included) and replays git's lookups on them in git's walk order, a commit-graph's parents and trees are looked up from its bytes, and the commit-graph verification takes the commits from those reads (the copy git's verification reads: the first pack of its most-recently-used pack list that has the commit, unchecked). What a run keeps from those reads is bounded (`setMemoryLimits`, `statistics.linksKept` and `graphCommitsKept`): past the bounds the objects are read from the store again. `fsck` now reports what native git reports where it missed it: `parse_object` checks the hash of what it reads (`hash mismatch <id>`) for the refs, the reflog entries a connectivity-only walk meets untyped, the cache-tree (trees read again, as git frees their buffers) and resolve-undo, reading the packed copy first as git does; the walk reads typed objects as git's `parse_tree`, `repo_parse_commit` and `parse_tag` (`Object <id> not a tree`); a grafts file prints git's `graftFileDeprecated` hint (as 2.43 or 2.56 words it). Every attribute consumer with a worktree (checkout and check-in conversion, diff and merge drivers) and `log -- :(attr)`, which also works in a bare repository, read the in-tree attributes of the attribute source when one is set: `$GIT_ATTR_SOURCE` over `attr.tree`, resolved with git's revision syntax; a bad `$GIT_ATTR_SOURCE` fails with git's `bad --attr-source or GIT_ATTR_SOURCE`, a bad `attr.tree` is ignored, an object that is no tree gives no in-tree attributes. `DiffCommand` still needs a worktree.
  - **vcs-working-tree:** `GitHostEnvironment.attrSource` (`$GIT_ATTR_SOURCE`); `GitContentFilter` reads in-tree attributes from the source's tree (options `trees`, `resolveAttributesSource`, method `setAttributesSourceResolver`); `attributesSourceSetting`, `resolveAttributesSource`, `readTreeAttributesFile` and `AttributesSourceError`.
  - **vcs-utils-node:** `createNodeGitHostEnvironment` reads `GIT_ATTR_SOURCE`.
- 5863bf1: **git hooks run through a portable host interface, and `git reset` refreshes the index as git does.**
  
  - `GitHostEnvironment.hookRunner` (optional) executes hooks; the commands find them as git's `find_hook` does (`core.hooksPath`, relative to the worktree top, else `$GIT_DIR/hooks` of the common git directory) through the repository's FilesApi (`Worktree.getFiles`), and a hook that is not executable gets the `advice.ignoredHook` hint (worded as the runner's `compatibility` says, 2.43 or 2.5x). Without a runner no hook runs, as before. On Node, `createNodeHookRunner` (vcs-utils-node) spawns the script, its stdout joined to its stderr where git joins them; pass it as `createNodeGitHostEnvironment({ hookRunner })`.
  - Hooks wired: commit (`pre-commit`, `prepare-commit-msg`, `commit-msg`, `post-commit`, `post-rewrite` for `--amend`; `setNoVerify`), merge (`pre-merge-commit`, `prepare-commit-msg`, `commit-msg`, `post-merge`; a refusal leaves the merge for `git commit`), checkout, switch, restore, clone and worktree add (`post-checkout`, its exit code in the result), rebase (`pre-rebase`, the post-checkout of onto, the picks' `prepare-commit-msg` and `post-commit`, `post-rewrite` "rebase"), cherry-pick and revert (the sequencer's `prepare-commit-msg` and `post-commit`), am (`applypatch-msg`, `pre-applypatch`, `post-applypatch`), push (`pre-push`, which can stop the push: `HookFailedError`), the receive side of a local push (`pre-receive`, `update`, `post-receive`, `post-update`, `push-to-checkout` for `updateInstead`, their output relayed as "remote: " lines), and the files ref store's batches (`reference-transaction`: `preparing` in 2.5x, `prepared`, `committed`, `aborted`; a refusal throws `RefTransactionAbortedError`). Commands expose what hooks wrote with `getHookOutput()` / `getHookStdout()`.
  - A commit with a hook runner updates HEAD in one transaction expecting its parent, as git's `update_head_with_reflog`.
  - vcs-transport: `PushClientOptions.prePush` (and `PushRefusedByHookError`), `relayPostReceive` for receive-pack (post-receive awaited before the side-band closes, as git), and the push client reads the side-band to its end so messages after the report reach `onProgress`.
  - `git reset` (mixed, and with paths) refreshes the index's stat data and reports "Unstaged changes after reset:" with `M`/`D`/`T`/`A`/`U` lines (`ResetCommand.getOutput()`), as `refresh_index` does; `setQuiet` and `setNoRefresh` as `-q` and `--no-refresh`, with the slow-refresh hint (`advice.resetNoRefresh`).
  - What a hook changes is taken as git takes it: `commit -a` reads the index lock back after `pre-commit` (`StagingIndexLock.reread`, `IndexFileLock.reread`); a partial commit (`setOnly`) gives its hooks git's temporary index (`$GIT_DIR/next-index-<n>.lock`: HEAD with the named paths), reads it back after `pre-commit` and removes it once the commit is made or given up. A hook that is a symbolic link counts only when its target is executable (followed through the FilesApi, else the host's `statFile`), and the Node runner reports a spawn failure (EACCES) as git's "cannot run".
  - reference-transaction: `committed` and `aborted` run once the ref locks are released; a deletion runs git's nested transaction on the packed store, and `Refs.remove(name, { deleteRefs })` runs the hook for refs under `refs/` (branch -d and tag -d pass `deleteRefs`, git's `delete_refs`); the hook context says which git version makes a call (`RefTransactionContext`). The receive side of a local push runs the remote's hook (a refusal makes receive-pack die, as git: the push fails with git's "fatal:" line and no ref moves); a command puts back the store's previous hook when it ends, and a command without a hook runner leaves a hook someone else set (`FileRefStore.setTransactionHook`) in place. A deletion that finds a ref lock or `packed-refs.lock` held tells the hook what git does (`aborted` only for the packed store's transaction, packed-refs.lock being taken before `prepared`). vcs-transport: `batchNonAtomic` (2.5x's two batches, each phase's update hooks run before its transaction, the deletions' committed before the rest's update hooks), `interleaveUpdateHook` (2.43's update hook then ref per command), `publishBeforeUpdate` (objects migrated after pre-receive, as git) and `BatchOptions.emptyTransaction`; the push client sends its commands in git's order (the remote's refs as advertised, then new ones).
  - rebase -i: `reword` runs `git commit --amend -e`'s hooks (pre-commit, prepare-commit-msg `commit HEAD`, commit-msg, post-commit, post-rewrite `amend`); `--continue` with staged changes those of `git commit -n -e` (prepare-commit-msg, post-commit, post-rewrite `amend` for an amend), with `GIT_REFLOG_ACTION` as git sets it.

- bbf5ca1: **`git hook run` and `git hook list`, configured receive hooks, and the reference-transaction hook of pack-refs.**

### Patch Changes

- e509d97: **Lock files use `FilesApi.createExclusive` when the FilesApi has it.** `atomicFilesOver(files, root).createExclusive` now delegates to the FilesApi's own exclusive create (webrun-files: `open "wx"` on Node, Web Locks in the browser, a transaction in sqlite) when it is present, detected at run time. Every git lock goes through it (`<ref>.lock` and `packed-refs.lock` in ref batches, `index.lock`, `gc.pid` and `gc.pid.takeover`), so the exclusion becomes cross-process: native git, other tabs and other FilesApi instances over the same directory are excluded. A delegated create that fails with ENOENT (another process, such as native git, pruned the empty directory between webrun-files-node's `mkdir` and its `open`) is retried, as git's `raceproof_create_file` does. Without it, locks behave as before: check-then-write, exclusive only among writers sharing one FilesApi instance.
  
  **webrun-files 0.11.** The catalog moves `@statewalker/webrun-files`, `-node`, `-mem` and `-browser` to `^0.11.0`. Every one of them now has `createExclusive`, so on Node locks hold across processes: two processes with their own `createNodeFilesApi` over one repository never both take `<ref>.lock` or `index.lock`, and native `git` sees our locks (and we see its). `createNodeFilesApi().write` streams to a temporary file and renames it over the target, and a `createNodeFilesApi({ rootDir: "/" })` accepts absolute paths. The vcs `FilesApi` interface declares the optional `createExclusive`, as webrun-files does.
