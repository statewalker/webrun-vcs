# @statewalker/vcs-commands

## 0.5.0

### Minor Changes

- 7d77bf8: **`git.clean()` as `git clean`; the index refresh is compare-and-set; submodule gitfiles.**
  
  - **vcs-commands (data loss fix):** `clean().setCleanDirectories(true)` no longer removes tracked directories, staged new files, nested repositories or ignored files. As `git clean -fd`: untracked files are removed one at a time; an untracked directory (no tracked or staged path in it) is entered only with `-d` or a path filter and removed once empty, deepest first, never recursively; nested repositories are skipped unless the new `setForceNestedRepositories(true)` (`-ff`); ignored files only with `setIgnore(false)` (`-x`); the index decides what is tracked (not HEAD). `cleaned` lists what `git clean -n` prints ("Would remove", a wholly removed directory as `dir/`), the new `skipped` the "Would skip repository" lines.
  - **vcs-working-tree / vcs-store-files (index refresh):** status and stash refresh entries compare-and-set (`applyStatUpdate`): only a stage-0 entry still holding the compared id, mode, size and mtime changes, the rest of it (flags such as assume-unchanged) kept; an add made meanwhile is never undone. An index file is refreshed by the new optional `Staging.refreshStats` (`GitStaging`, `FileStagingStore`): read afresh, written under `index.lock` only while it is the index this instance read or wrote, without writing other in-memory edits, and memory changed only once the write succeeded. `isOutdated()` compares the index's checksum, not its mtime. Index entries keep nanoseconds, uid and gid (`StagingEntry.mtimeNs`/`ctimeNs`/`uid`/`gid`), and refreshed entries record the file's exact stat (`LinkStats`/`WorktreeEntry` gain `mtimeNs`, `ctimeNs`, `dev`, `ino`, `uid`, `gid`; the Node FilesApi reads them with a bigint `lstat`), so native git trusts them.
  - **vcs-store-files:** `readGitlinkHead` resolves `gitdir: ../.git/modules/sub` (as `git submodule add` writes it) against the submodule's directory, refusing a path above the FilesApi's root, and reads only regular files (never a FIFO).
  - **vcs-utils / vcs-utils-node:** new optional `PosixFilesApi.rmdir` (an empty directory only, never recursive), implemented by the Node, simulated-links and mounted FilesApis; `FileWorktree.removeEmptyDirectory` uses it, and no directory pruning falls back to a recursive removal.
- 7d77bf8: **Clean never enters tracked paths; git's racy smudging on every index write; exact nanoseconds.**
  
  - **vcs-commands (data loss fix):** `clean()` never enters a directory standing where the index has a file, link or submodule (a file replaced by a directory, a deinitialised submodule's directory), as git; a path filter removes the untracked directory it names as `git clean -f -- u` does (`u/`), globs (`*.txt`) match as git's pathspecs, a nested repository named by a path filter is passed over silently, and a directory whose `.git` is no repository (an empty `.git`) is removed with `-d`, as git (new optional `Worktree.isRepository`).
  - **vcs-working-tree / vcs-store-files (racy git):** every index write of `GitStaging` / `FileStagingStore` applies git's `ce_smudge_racily_clean_entry`: an entry as read whose mtime second is not older than the index file's, and whose content changed behind a matching stat, is written with size 0 (new `Staging.setRacyCheck`, installed by every command from the worktree; `smudgeRacilyClean`). The index time is the index file's own mtime after every read and write (0, every entry racy, when unknown; never "now"). Entries a refresh proved clean are recorded as they are, not smudged.
  - **vcs-utils-node:** `lstat` builds millisecond times from the nanosecond parts exactly (a ~1.8e18 nanosecond time no longer drifts below its millisecond), so the index records the file's nanoseconds exactly.
  - **vcs-store-files:** a submodule `gitdir:` file pointing where there is no repository, or beyond the FilesApi's root, makes status fail with git's message ("fatal: gitfile does not point to a valid repository: sub/.git") instead of reporting the submodule clean.
  - **vcs-working-tree:** stash push keeps the index's commit for a submodule (as git stash), even when the submodule checked out another one.
  
  **Exact index times.** The index writer records the exact nanoseconds a file's stat carried, and takes the seconds from them: a time in milliseconds (a double) cannot hold nanoseconds at today's dates and can round across a millisecond or a second. Status takes whole seconds the same way.
- 875db86: **Clone and fetch leave what git leaves: remote and upstream configuration, `refs/remotes/<name>/HEAD`, `FETCH_HEAD`; shallow clones on the KV store. Breaking: `CloneCommand.setBranch` no longer implies `--single-branch`.**
  
  - **vcs-commands, `CloneCommand`:** writes the configuration `git clone` writes: `remote.<name>.url`, `remote.<name>.tagOpt = --no-tags` for `setNoTags()` and for a mirror (as git 2.49+, whose `--mirror` implies `--no-tags`), the `remote.<name>.fetch` refspec of the clone (`+refs/heads/*:refs/remotes/<name>/*`; one branch or tag for a single-branch clone; none for a bare clone; `+refs/*:refs/*` with `remote.<name>.mirror = true` for a mirror), and `branch.<b>.remote` / `branch.<b>.merge` for the checked-out branch (an empty remote's unborn branch included). `refs/remotes/<name>/HEAD` becomes a symbolic ref to the tracking ref of the remote's default branch when the clone took it. `setRemote(name)` (`--origin`) names the remote in all of it. The configuration is saved through the working copy's config (`.git/config` for the files backend), and native git reads it: `git status` shows the upstream and `git pull` works in our clone.
  - **vcs-commands, breaking:** `CloneCommand.setBranch(b)` is git's `--branch`: every branch is still cloned and `b` (or a tag `b`, checked out detached) is set up. New `setSingleBranch(true)` (`--single-branch`) restricts the clone to it, as before; a shallow clone and `setBranchesToClone` (with `setCloneAllBranches(false)`) stay single-branch unless `setSingleBranch(false)`.
  - **vcs-commands, `FetchCommand`:** writes `FETCH_HEAD` in git's format through the checkout (`<oid>\t[not-for-merge]\t<description>`, `branch 'main' of <url>`, `tag 'v1' of <url>`, the URL without credentials or `.git`), the refs to merge first: every ref of explicit refspecs, or with configured refspecs the current branch's `branch.<b>.merge` refs (fetched for this alone when no refspec takes them), or, when the current branch has no upstream at all, the first ref of an exact first refspec; a ref named twice without destination is listed twice; tags (auto-followed ones by name) and the rest are `not-for-merge`. Byte-identical to native `git fetch` for the same fetch. New `setAppend(true)` (`--append`) and `setWriteFetchHead(false)` (`--no-write-fetch-head`); FETCH_HEAD is truncated when the fetch starts (a failed fetch leaves it empty); a dry run writes nothing. Without `setTagOpt`, a configured remote's `remote.<name>.tagOpt` decides; a configured remote without `fetch` lines fetches the current branch's merge refs when it is that branch's upstream, else its HEAD only, as git (the default refspec is no longer filled in).
  - **vcs-commands:** new `git.remoteSetHead()` (`RemoteSetHeadCommand`, `git remote set-head <name> <branch>` / `-d`). `fetch --prune` keeps `refs/remotes/<name>/HEAD` (a symbolic ref), as git.
  - **vcs-transport:** `FetchClientResult.fetched` lists every remote ref a fetch took, with or without a local ref, in git's FETCH_HEAD order (refspec matches, then auto-followed tags: those of fetched or present objects first, then those found in the fetched history), each with the index of the refspec that selected it (`PlannedRef.refspec`). New `formatFetchHead`, `parseFetchHead`, `fetchHeadUrl` and `anonymizeUrl` (git's transport_anonymize_url).
  - **vcs-working-tree:** `Checkout` has optional `readFetchHead()` / `writeFetchHead(content, { append })`; `MemoryCheckout` keeps it in memory.
  - **vcs-store-files:** `GitCheckout` reads and writes `.git/FETCH_HEAD`.
  - **vcs-store-kv:** `KVRefStore.getShallow()` / `setShallow(commits, expected)`, with the `expected` check of the other stores (one compare-and-swap of a `shallow:root` key), so shallow fetches and clones work on the KV store.
- d45dfb0: **A non-bare clone checks out its files, as `git clone` does.**
  
  - **vcs-commands:** `CloneCommand` writes the files of the checked-out commit into the worktree, not only the index: contents, the executable bit and symbolic links where the worktree can represent them, an empty directory for each submodule (gitlink), and the index with the size and mtime of every file written, so native `git status` reports a clean tree right after the clone. The tree is planned (every blob checked) before the first file is written. A symlink becomes a plain file holding its target where the worktree cannot make links or `core.symlinks` is false; the index keeps mode 120000.   - **vcs-working-tree:** `Worktree` gains the optional `capabilities` (`WorktreeCapabilities`: `executable`, `symlinks`); undefined means both. `WorktreeWriteOptions.mode` documents that mode `0o120000` makes the content the link target.
  - **vcs-store-files:** `FileWorktree` writes mode `0o120000` as a link where its FilesApi can make one (else as a plain file holding the target), chmods regular and executable files with their permission bits (`0o644`/`0o755`, was the whole git mode), and reports `capabilities` (see the changeset on symbolic links for what it requires of the FilesApi).

- 01d2219: **Every ref and reflog write goes through git's locks; the unlocked writers are gone (breaking).** `vcs-store-files` no longer exports `writeRef`, `writeObjectRef`, `writeSymbolicRef`, `deleteRef`, `updateRef` (`refs/ref-writer.ts`) or `appendReflog`, `deleteReflog` (`refs/reflog-writer.ts`, removed; `hasReflog` moved to `reflog-reader.ts`). They wrote loose refs and reflogs with plain writes. Use `FileRefStore` instead: `set`, `setSymbolic`, `remove`, `batch`, `compareAndSwap` and the new `deleteReflogEntry` all take `<ref>.lock` (and `packed-refs.lock` where git does), and a reflog line is appended while the ref's lock is held, as git does. A batch now also locks every symbolic ref that logs the update (not only HEAD), the updated ref first. As in git, a reflog line that cannot be written now fails the update before its commit (the ref keeps its value) instead of being skipped.
  
  **Stash as git keeps it.** `GitStashStore` (the files `WorkingCopy.stash`) writes `refs/stash` through the history's ref store: a push is a one-ref batch under `refs/stash.lock` that creates the reflog (git's REF_FORCE_CREATE_REFLOG) with the stash commit's message, a drop is `git reflog delete --rewrite --updateref refs/stash@{n}` under `refs/stash.lock` and `logs/refs/stash.lock`, and the last drop deletes the ref and its log. Messages follow git ("WIP on main: abc1234 subject", "On main: message", "index on main: …"), commit timestamps are seconds (they were milliseconds), and `list()` returns the reflog message. Native `git stash list` / `show` / `drop` work on our stashes and we read and drop git's. `GitStashStoreOptions` loses `files` and `gitDir` (and `StashFilesApi` is gone): the store needs only `history`. In `vcs-commands`, `stashCreate` logs every stash (a custom message becomes "On <branch>: <message>", a detached HEAD "(no branch)", as in git), `stashList` lists every `stash@{n}` from the reflog, `stashApply` resolves `stash@{n}`, and `stashDrop` drops any `stash@{n}` (stores without reflogs keep the old `stash@{0}`-only behaviour).
  
  **Pseudo refs and HEAD.** ORIG_HEAD, MERGE_HEAD, CHERRY_PICK_HEAD and REVERT_HEAD are written and removed through the ref store (under `<name>.lock` on git files) by the merge, cherry-pick and revert state stores and by `GitCheckout`, which also reads them from its `refs`. `createGitFilesBackend({ create: true })` writes HEAD with `setSymbolic` (under `HEAD.lock`).
  
  **New core API.** `BatchOptions.createReflog` creates the updated refs' reflogs whatever their names. `Refs.deleteReflogEntry(name, index, { rewrite, updateRef })` (optional) deletes `name@{index}`; it is implemented by the memory, KV, SQL and git-files stores. `deleteReflogLine` and `ReflogEntryNotFoundError` are exported from `vcs-core`.

- 3292f46: **upload-pack honours `include-tag` and negotiates over v0 as git does, both servers hide refs as git's `hideRefs`, upload-pack gets hooks, and the fetch client gzips large requests.**
  
  - **vcs-transport, v0 negotiation (fix):** upload-pack answers haves exactly as git's `get_common_commits`: `ACK <oid> common` / `continue` / `ready` while a batch is read (`ready` also without no-done, once every want reaches a common commit), NAK at the end of every batch in the multi_ack modes, the final `ACK <oid>` on `done`, and with no-done after `ready` NAK and the final ACK before the pack. - 658066d: **Breaking: one fetch client, as git's fetch-pack and remote-curl.**

It now returns `{ id, entry }`, the stat that matched the stored content, which the add commands record in the index.
  - **vcs-testing:** `createRawStorageTests` covers chunked values, failed writes, `move` (`supportsMove`) and streaming writes (`persistedBytes`); `createGitObjectsTests` covers `putUnsized` and, with `persistedBytes`, a 50 MiB blob written and read back with the producer never more than a few MiB ahead of the store.
  - **vcs-utils:** `randomHexId`, `timestampedId` and `timestampOfId` build ids from `crypto.getRandomValues`; no package source uses `crypto.randomUUID` any more (missing on non-secure browser origins).
- 7392d8e: **Breaking: worktree hashing and checkout writes stream.** No worktree file or blob is read whole just to hash it or to write it.
  
  - **vcs-working-tree:** new `hashWorktreeFile(path, { size, read }, newHasher?)` hashes a file as it streams, with its size from stat. When the file changes size while it is read it re-stats and retries once, then returns `unknownContentId()`, a non-hex value unique to each call that never equals an index id, so it compares as modified (`isUnknownContentId` recognises it). `add -N` now records the empty blob's id flagged `intentToAdd`, as git does, instead of an empty id. Checkout writes are as atomic as `FilesApi.write`. `MemoryWorktree` uses it. The `hashFunction` option is removed; pass `newHasher` (an incremental `Hasher` factory, default `createSha1`). New type `NewHasher`.
  - **vcs-store-files:** `FileWorktree.computeHash` and `FileTreeIterator.computeHash` stream through `hashWorktreeFile`; their `hashFunction` option is replaced by `newHasher`. `FileWorktree.checkoutTree` streams each blob into `FilesApi.write`. `GitResolutionStore` streams blobs into the worktree (`acceptOurs`, `acceptTheirs`), stores resolved files as streams of known size (`markAllResolved`), and scans for conflict markers chunk by chunk.
  - **vcs-commands:** the core `CheckoutCommand`, `Git.checkout()`, `reset --hard` and `stash apply` hand the blob stream to the worktree instead of collecting it.
  - **vcs-utils:** `computeObjectIdFromStream(type, size, content, newHasher?)` takes an optional hasher factory.
- c767140: **Checkout never writes into the repository's own `.git`** (git's `verify_path`, CVE-2014-9390). Tree and index paths come from other people's repositories, and a crafted tree with an entry named `.git` used to write its files into the worktree's `.git` (config, hooks, refs).
  
  - **vcs-core:** new `isValidWorktreePath(path)` and `assertValidWorktreePath(path)`. They refuse empty, `.` and `..` components, and `.git` under any spelling a filesystem folds to it: any letter case; NTFS trailing dots and spaces, the 8.3 name `git~1`, alternate data streams (`.git::$INDEX_ALLOCATION`) and `\` as a separator; and HFS+-ignored code points (`‌.git`). `.gitignore`, `.github/` and other dotfiles stay valid.
  - **vcs-store-files:** `FileWorktree.writeContent`, `mkdir`, `remove` and `rename` refuse such paths. `checkoutTree` and `checkoutPaths` report them under `failed` and check out the rest. `GitResolutionStore` refuses them when it writes conflict resolutions to the worktree.
  - **vcs-commands:** the core `CheckoutCommand` refuses such paths when it writes or removes worktree files, and reports them as conflicts. `clean` leaves an untracked file with such a name (`git~1`, `.GIT/`) in place rather than aborting on it.
