# @statewalker/vcs-utils

## 0.7.0

### Minor Changes

- a8726f7: git's date parsing (`approxidateCareful`, `parseGitDate`, ...) moves to vcs-utils (vcs-commands
  re-exports it), and gc's expiry settings (`gc.reflogExpire*`, `gc.pruneExpire`) are read as git's
  `parse_expiry_date`: `2 weeks`, `90.days`, `yesterday`, `two.weeks.ago` and absolute dates work.
- f91199d: **SHA-256 repositories open: their loose objects, trees, commits, tags and refs read and write with 64-hex ids.**
  
  - **vcs-utils:** `ObjectFormat` (git's `struct git_hash_algo`): `SHA1_OBJECT_FORMAT` and `SHA256_OBJECT_FORMAT` with their raw and hex lengths, null id, empty tree and blob ids, signature header and hashers; `objectFormatByName`, `isHexObjectId`, `isNullObjectId`, `nullObjectIdLike`. `sha256()` is a one-shot SHA-256 on Web Crypto (the portable incremental hasher where there is none); `computeObjectId(type, content, format?)` hashes in the given format. `UnsupportedObjectFormatError` and `assertSha1ObjectFormat` refuse what has no SHA-256 path yet.
  - **Worktrees:** `FileWorktree` and `MemoryWorktree` hash files in the repository's format by default (`Blobs.objectFormat`), so status, diff and checkout agree with the stored blobs in a SHA-256 repository.
  - **vcs-core:** a store carries its format (`GitObjects.objectFormat`, `createGitObjects(store, { objectFormat })`, `History.objectFormat`, `objectFormatOf()`); trees are encoded and decoded with the format's id length (`decodeTreeBytes(…, { idLength })`, `TreeEntryCursor(bytes, idLength)`), commits sign with `gpgsig-sha256` in SHA-256 (`CommitSignatureHeader`), the empty tree is the format's, abbreviations reach 64 digits (`parseCoreAbbrev(value, hexLength)`), refs check direct values against the format (`isRefObjectId(value, format)`, `RefBatchView.objectFormat`, `createMemoryRefs({ objectFormat })`, `createMemoryHistory({ objectFormat })`), and reflogs write 64-zero null ids.
  - **vcs-store-files:** `extensions.objectFormat = sha256` is no longer refused (`RepositoryFormat.objectFormat`); `createGitFilesBackend({ create: true, objectFormat })` writes `core.repositoryformatversion = 1` and `extensions.objectformat`. Refused with `UnsupportedObjectFormatError` until their tickets land: a SHA-256 repository holding packs (or a multi-pack-index) and every pack write into one, its index file (`FileStagingStore`, through `GitStagingOptions.objectFormat`), gc, repack and prune, and writing its commit-graph (which is not read either).
  - **vcs-transport:** fetch, push and serving refuse a SHA-256 repository (`createRepositoryFacade`) until the protocols' `object-format` capability is implemented.
  - **vcs-commands:** `init().setObjectFormat("sha256")`, `$GIT_DEFAULT_HASH` (`GitHostEnvironment.defaultHash`) and `init.defaultObjectFormat` choose a new repository's format; re-initialising with another one throws `ReinitializeHashError` ("attempt to reinitialize repository with different hash"), an unknown name `UnknownHashAlgorithmError`. `rev-parse --show-object-format` (`addArgument`, `showObjectFormat()`), full and abbreviated 64-hex revisions, `log`, `diff` (`--full-index` too), `fsck` and `notes` (fanned-out trees too) work in SHA-256 repositories; `gc` refuses them. Patch-ids, `format-patch`'s zero commit, porcelain v2 status, rebase's ref updates, `worktree list`, `apply` and submodule summaries use the repository's null and empty ids.

## 0.6.0

### Minor Changes

- d5158af: **Faster `git blame`, with the same output.**
  
  - **vcs-commands:** `BlameCommand` splits, hashes and numbers the lines of each version of the file once, through one `LineInterner` for the whole walk, instead of again in every diff; lines in the tail a diff trims (`trim_common_tail`) are not read at all, and a blob read as one chunk is not copied. The algorithm, its blame entries and tie-breaks are git's as before. On a 1000-commit history of a 3000-line file blame takes about 40% of the time it took (about 1.6× native git, from 3.7×). The interner's memory is bounded: past 64 MiB of distinct lines (`BlameCommand.setInternerByteLimit`) blame starts a new interner, and a version from the old one is interned again when compared with one from the new.
  - **vcs-utils:** `LineInterner` numbers distinct lines (under xdiff's whitespace flags) across diffs (`byteSize` tells how many bytes of lines it holds), and `InternedText` reads a file's lines on demand; `XdiffOptions.interner` lets xdiff classify lines by those numbers (the same classes, numbered alike), and `xdiffHunks` takes either side as a `LineSource` (`ByteLines` or `InternedText`). `ByteLines.prefix` gives the lines of a prefix sharing the line table and hashes. xdiff's line classification uses a typed hash table, and `trimCommonTail` compares four bytes at a time. The pooled inflater resets a state without allocating new code tables (pako's reset allocated two per object), which makes reading small objects such as commits and trees about 20% faster.
- 457680a: **Diff and blame output byte for byte as git's, on the xdiff port.**
  
  `@statewalker/vcs-utils`: the xdiff port takes git's whitespace flags (`ignoreWhitespace` `-w`, `ignoreWhitespaceChange` `-b`, `ignoreWhitespaceAtEol`, `ignoreCrAtEol`), and gains xdiff's emitter: `unifiedDiff`/`unifiedDiffHunks` print the hunks of `git diff` (context, inter-hunk context, `-W`, `--ignore-blank-lines`, function lines in hunk headers cut at 80 bytes and at broken UTF-8 as git does, `\ No newline at end of file`), `diffLineCounts` counts as the diffstat does, and `xdiffHunks` gives the changes `git blame` uses (common tail trimmed). `userdiffFindFunction` and `BUILTIN_FUNCNAME_PATTERNS` port git's diff drivers (builtin `cpp`, `python`, `java`, ... patterns of git 2.56, and `diff.<driver>.xfuncname`/`funcname`), matched as glibc matches them: `compilePosixRegex` (new, `@statewalker/vcs-utils`) is a POSIX regular expression engine over bytes, extended and basic syntax with the GNU extensions, leftmost-longest matches and subexpressions placed as glibc places them, back-references, `REG_ICASE` folding ASCII only, the patterns glibc refuses refused (git then dies with "Invalid regexp to look for hunk header"), and time linear in the line for patterns without back-references (JavaScript's backtracking took seconds on the `csharp` pattern). `BUILTIN_FUNCNAME_PATTERNS_2_43` holds the drivers of git 2.43 and 2.44 (`userdiffFindFunction`'s third argument). `legacyMinimal` reproduces git before 2.5x, whose `minimal` still set aside many-matched lines. Breaking: the JGit-style `HistogramDiff`, `HistogramDiffIndex`, `MergeAlgorithm`/`merge3Way`, `getAlgorithm`, `DiffAlgorithm` and `DEFAULT_ALGORITHM` are removed (nothing used them; diffs and merges run on `xdiff` and `mergeLines`); `SupportedAlgorithm`, `MyersDiff`, `RawText` and `RawTextComparator` stay.
  
  `@statewalker/vcs-commands`: `DiffCommand.callText(format)`/`callBytes(format)` print `git diff` as git does: the patch (`diff --git`, `old mode`/`new mode`, `new file mode`, `deleted file mode`, `similarity index`/`rename from`/`rename to`, `index` lines with abbreviated ids, `Binary files ... differ`, quoted paths, a file turned into a symbolic link as a deletion and an addition), `stat` (git's widths; `setOptions({ stat: { width } })` for `COLUMNS`), `numstat`, `shortstat`, `name-only` and `name-status`, with `setOptions` for `-U`, `--inter-hunk-context`, `-W`, `--diff-algorithm`, `--[no-]indent-heuristic`, the whitespace options and `--ignore-blank-lines`, and the configuration (`diff.algorithm`, `diff.indentHeuristic` default on, `diff.context`, `diff.interHunkContext`, `diff.renames` default on, `diff.renameLimit`, `core.quotePath`, `diff.statNameWidth`, `diff.statGraphWidth`, `diff=<driver>` attributes with `diff.<driver>.binary`/`.algorithm`/`.xfuncname`). `git diff` without trees now compares the index with the worktree (it compared HEAD with itself), `setOldTree(a)` alone compares `a` with the worktree (it compared `a` with HEAD), and paths sort in git's byte order; `setRenames(true)` detects renames in `call()`. `formatNoIndexDiff` prints `git diff --no-index` for two files. `DiffFormatter` now prints exactly git's text: `toString` ends lines with LF, `formatAll` concatenates, `formatBytes` keeps non-UTF-8 content, hunks start at 0 for an empty side (`@@ -0,0 +1,3 @@`), hunk lines include the `\ No newline at end of file` marker, and the default algorithm is myers as git's. `BlameCommand` is a port of git's blame (`blame.c`): commits by committer date, whole-file renames followed by default (git's default; `setFollowRenames(false)` is `--no-follow`), the xdiff diff with `diff.algorithm` and the indent heuristic, root commits as boundaries (`setShowRoot`, `blame.showRoot`), `setIgnoreWhitespace` (`-w`), `setLineRanges` (`-L`); lines are split at LF only (a CR-only file is one line, as in git). `BlameEntry` gains `previous` and `boundary`, `BlameResult` gains `content`, and `formatBlamePorcelain` (`--porcelain`, `--line-porcelain`) and `formatBlame` (default output, `-n`, `-f`, `-e`, `-s`, `-l`, `-t`, `-b`) print them as git does. Options for older git: `histogramRediff`, `legacyMinimal`, `renameCountLastSpan`, `namesFromContents` (diff) and `setCompatibility` (blame), `alwaysWidenAbbrev` (blame output).
  
  A conflicted path shows as git shows it: in `git diff`, the combined diff of stages 2 and 3 against the worktree file (`diff --cc`, `index a,b..0000000`, `@@@` hunks, dense as git's `combine-diff.c`; `writeCombinedDiff`), printed before the other files, and in the other formats as an unmerged entry followed by stage 2 against the worktree; in `git diff A`, the worktree file against `A`. A submodule with changes of its own shows as `Subproject commit <id>-dirty` in the worktree modes (untracked files in it count only with `diff.ignoreSubmodules=none`, as git's default ignores them; `diff.ignoreSubmodules` is read). `setOldTree`/`setNewTree` with a revision that names nothing throws (`RefNotFoundError`, "bad revision"), as git exits 128, instead of diffing against an empty tree. Abbreviated ids follow git: `core.abbrev` (auto, a number, `no`), 7 digits up to 16383 packed objects and more beyond (`findAbbrevLengths` in `@statewalker/vcs-core`, from the new optional `GitObjects.approximateCount`, which the files backend answers from its packs only, as git counts), and longer where another object shares the prefix; in `index` lines (`DiffOutputOptions.abbrevLengths`) and in blame's default output (`BlameResult.autoAbbrev()`, `formatBlame`'s `autoAbbrev`, then the boundary marks of git 2.5x or one more digit for older git).
  
  Remaining differences from git's diff: paths that are not valid UTF-8 (core and the stores keep paths as strings); `diff.noprefix`, `diff.mnemonicPrefix`, `diff.orderFile`, textconv drivers (`diff.<driver>.textconv`) and `submodule.<name>.ignore` are not read; glibc itself mishandles a few contrived patterns with word anchors after a repetition (it finds `b*\B` in "Ab" at 2), which the matcher does not copy.
- a8df903: **`git.fsck()` and `git.verifyPack()` read each pack once, and SHA-1 is two to three times as fast.**
  
  On a repacked 5000-commit repository (39.7k objects in one pack), over the built packages, a full `fsck` takes 1.0 s instead of 2.3 s, `--connectivity-only` 0.6 s instead of 0.9 s, and `verify-pack -s` 0.7 s instead of 1.7 s. Output, exit status and verdicts are unchanged; the native comparison tests pass on git 2.43 and 2.56.
  
  - **vcs-commands (fsck, verify-pack):** a pack is checked in one sequential read: each entry's bytes feed the pack's SHA-1 and the entry's CRC-32 and are inflated there, once; a delta is applied to its base from a 16 MiB cache of the objects unpacked just before it (in pack order a base precedes its deltas), and each object is hashed in one call. Whatever that path does not handle as it stands (REF_DELTA, a base not cached, an object over 1 MiB, an entry reached through a corrupt part of the idx, any failure) goes through the pack's own reader, so error messages and verdicts are those of before. The pack checksum errors are still printed before the entries' output. The ids are read straight from the idx and the object table is probed with their bytes, the commit parser hands back where its ids are instead of decoding them, and the object hash keeps each slot's key next to its object number. A tree checked in full is remembered as the object numbers of its entries, so the connectivity walk does not unpack it again (not with `--name-objects`, nor for an object with a copy that failed a check); the walk reads through the store's synchronous path (`getNow`) and runs without awaiting when nothing needs I/O. `--connectivity-only` inflates no blob: a dangling object's type comes from its pack entry's header, following delta bases, as git's `packed_object_info`. `verify-pack` takes each entry's header from the same read instead of reading it again.
  - **vcs-commands (`fsck-object-checks`):** new `scanTree` (a tree's entries as a table, without an object per entry), `parseCommitLinks` (`parseCommitBuffer` with the ids left in place), `hexIdAt` and `rawIdAt`; `fsckTree` takes a tree's `scanTree` table when the caller has one.
  - **vcs-utils:** SHA-1 is this package's own instead of `@noble/hashes`': a fully unrolled JavaScript block function, and a WebAssembly one assembled at load time (no binary shipped) wherever the runtime compiles WebAssembly from bytes; elsewhere (workerd, a CSP without `wasm-unsafe-eval`) the JavaScript one runs. `createSha1()` uses it, so every caller gets the speed. New exports: `Sha1` (the incremental hasher without the `Hasher` wrapper), `sha1Of(head, body)` (a header and a body hashed as one message in a single WebAssembly run, padding included) and `sha1Wasm()`. CRC-32 is computed slicing by 8 (eight bytes per step, about twice as fast).

- 2d0759a: **Writing objects costs what it costs git: an object already stored is only freshened, and a new loose object takes six system calls and no thread-pool round trip.** Storing 20,000 small blobs in a files repository went from 15.0 s to 2.7 s (native `git hash-object -w --stdin-paths`: 3.3 s), 20,000 trees of which 90% exist from 2.8 s to 0.5 s (native `git mktree --batch`: 0.4 s), and a 3,000-commit loop through `history.blobs/trees/commits.store` from 8.8 s to 2.4 s.
  
  - **vcs-core:** the object kernel hashes content it holds first and skips the write of an object the store already has (git's `odb_freshen_object` before `write_loose_object`), for `putRaw` too, whose id is known up front: an unpacked object the repository has is not read, deflated nor staged. The write that follows reuses that id (the content is hashed once) and tells the store with the new `PutStagedOptions.notFresh` that it need not look again. - e509d97: **Lock files use `FilesApi.createExclusive` when the FilesApi has it.** `atomicFilesOver(files, root).createExclusive` now delegates to the FilesApi's own exclusive create (webrun-files: `open "wx"` on Node, Web Locks in the browser, a transaction in sqlite) when it is present, detected at run time. Every git lock goes through it (`<ref>.lock` and `packed-refs.lock` in ref batches, `index.lock`, `gc.pid` and `gc.pid.takeover`), so the exclusion becomes cross-process: native git, other tabs and other FilesApi instances over the same directory are excluded. A delegated create that fails with ENOENT (another process, such as native git, pruned the empty directory between webrun-files-node's `mkdir` and its `open`) is retried, as git's `raceproof_create_file` does. Without it, locks behave as before: check-then-write, exclusive only among writers sharing one FilesApi instance.
  
  **webrun-files 0.11.** The catalog moves `@statewalker/webrun-files`, `-node`, `-mem` and `-browser` to `^0.11.0`. Every one of them now has `createExclusive`, so on Node locks hold across processes: two processes with their own `createNodeFilesApi` over one repository never both take `<ref>.lock` or `index.lock`, and native `git` sees our locks (and we see its). `createNodeFilesApi().write` streams to a temporary file and renames it over the target, and a `createNodeFilesApi({ rootDir: "/" })` accepts absolute paths. The vcs `FilesApi` interface declares the optional `createExclusive`, as webrun-files does.
- b6a5d9c: **The object kernel, `createGitObjects`.** Git objects stored as zlib loose objects over a `StagingBlobStore`, written in one pass (`put(type, size, content)`), received with their id (`putRaw`), and read back checked (`get`, `getRaw`, `has`, `list`, `remove`). New in vcs-core: `GitObjects`, `GitObject`, `CorruptObjectError`, `ObjectIdMismatchError`, `InvalidObjectIdError`, `StagingBlobStore`, `rawStorageStaging`, and a re-export of `SizeMismatchError`. New in vcs-store-files: `filesStagingStore` and `FilesStagingStore` (git's `objects/` layout, `sweepStaged`). New in vcs-testing: `createGitObjectsTests` and `gitObjectSamples` (objects written by git). Additive: the typed stores move to it in a later change.
  
  `deflate` (Web streams): input is pulled with backpressure, a consumer that stops early closes the source without waiting for a stalled one, the source's own errors come out unchanged and compressor errors as `CompressionError`.
- ee92812: **Breaking: only portable APIs in the packages.** Files go through `FilesApi` alone; no package source imports a `node:*` module, and a lint rule (`noNodejsModules`, error for `packages/*/src`) keeps it so.
  
  `@statewalker/vcs-utils-node` now only provides the Node `FilesApi` (`createNodeFilesApi`, returning `NodeFilesApi` from `@statewalker/webrun-files-node`). Removed: the `node:zlib` compression (`@statewalker/vcs-utils-node/compression`, `createNodeCompression`, `deflateNode`, `inflateNode`, `compressBlockNode`, `decompressBlockNode`; the Web `CompressionStream` default is used everywhere), `StreamingNodeFilesApi`, and `createNodeAtomicFiles` (ref batches use `atomicFilesOver(files, gitDir)`, which excludes writers sharing one `FilesApi`, not other processes such as a running `git`).
  
  `createNodeFilesApi().write` is `NodeFilesApi`'s, which streams from `@statewalker/webrun-files-node` 0.11 (a temporary file, then a rename, as the removed `StreamingNodeFilesApi` did), and lock files use its `createExclusive` (`open "wx"`), so they exclude other processes. `atomicFilesOver` now runs its exclusive creates and empty-directory removals one at a time per FilesApi, and a ref commit blocked by another writer's lock directory waits, then reports `df-conflict` instead of throwing.
