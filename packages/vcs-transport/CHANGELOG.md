# @statewalker/vcs-transport

## 0.6.0

### Minor Changes

- 7f697fd: **The served HTTP handler serves the dumb protocol as `git http-backend` does, checks the request's content type, and appends to the alternates a quarantined pre-receive is given.**
  
  - **Security note (default change):** `createServedHttpHandler` / `createServedFetchHandler` now answer the dumb protocol by default (`http.getanyfile`, as http-backend), where they refused it before. The object files are not filtered by hidden refs, so they fail closed: while any hidden-ref pattern applies (the operator's `settings.hideRefs` / `uploadPackHideRefs`, the repository's `transfer.hideRefs` / `uploadpack.hideRefs`, the resolver's settings), every `objects/...` path is refused (403) unless the operator passes `getAnyFile: true`, or the repository sets `http.getanyfile=true` explicitly while only its own config hides refs (a repository's opt-in never re-opens what the operator's `settings` or the resolver's settings hide); `HEAD` and `info/refs` (which leave hidden refs out) are still served. A server that relies on `uploadpack.allowAnySHA1InWant` staying off without hiding refs should pass `getAnyFile: false`.
  - The dumb protocol (`getAnyFile: false` or the repository's `http.getanyfile=false` turns it off): `objects/info/packs` generated from the repository's own packs (youngest first, no `update-server-info` needed), `objects/info/alternates`, `objects/info/http-alternates`, loose objects, packs and indexes, with http-backend's content types and caching (`no-cache`, or a year for objects and packs), `Content-Length` and `Last-Modified`; a missing file is a 404. A native client with `GIT_SMART_HTTP=0` clones and fetches from it. The dumb protocol is still served only where upload-pack is, and `info/refs` still leaves out hidden refs. A `HEAD` request for a file returns its headers without opening it, and a `GET` opens the file at the first read of its body.
  - The files come from the new `ServedRepository.files` (`servedGitFilesOf(files, gitDir)`; `servedRepositoryOf` sets it from the new `OpenedRepository.files`, which `Worktree.openRepository` fills). Only files of the object directory are served: a file whose links lead outside `<git dir>/objects` (an alternates file linked to `../config`) is not; an absolute link is followed only below the FilesApi's `rootDirectory`. A repository without files (key-value, SQL, memory stores) answers `HEAD` and `info/refs` only and every `objects/...` path 404.
  - A POST to `git-upload-pack` / `git-receive-pack` whose `Content-Type` is not exactly `application/x-git-<service>-request` is answered 415 with http-backend's message.
  - A quarantined pre-receive's `GIT_ALTERNATE_OBJECT_DIRECTORIES` is the host's (new `GitHostEnvironment.alternateObjectDirectories`, read from `GIT_ALTERNATE_OBJECT_DIRECTORIES` by `createNodeGitHostEnvironment`) with the repository's objects appended, as tmp-objdir.c's `env_append`.
  - A local push (`git push <path>`) runs the receiving repository's hooks without the pushing side's repository variables (git's `local_repo_env`: `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_OBJECT_DIRECTORY`, `GIT_DIR`, `GIT_INDEX_FILE`, `GIT_CONFIG_COUNT`, ...; new `LOCAL_REPO_ENV`, `remoteHookSession(..., { localPush: true })`, `HookHost.unsetEnv`), as connect.c starts receive-pack; the host's alternates are appended for served HTTP and git:// pushes only.
- 4e839be: **git's native protocol over MessagePorts, WebSockets and libp2p streams, with backpressure.**
  
  - MessagePort: `messagePortDuplex(port)` and `serveGitOverPort(port, options)` run one git session per port on webrun-rpc's stream tier (`duplexOverPort` / `serveDuplexOverPort`): one chunk in flight per direction, the end of the client's input a half-close. `serveGitOverPortMux` / `connectGitOverPortMux` carry many sessions over one port (webrun-rpc's `overPipe` multiplexer, a 1 MiB window per session); `createMessagePortConnector` registers the first with a `GitTransportRegistry`, `createWebrunConnector` the second. The sentinel-based `createMessagePortDuplex`, `messagePortFetch` and `messagePortServe` are deprecated; the unused, unexported socket handler (`createGitSocketClient`, `handleGitSocketConnection`) is removed.
  - WebSocket: `webSocketDuplex(socket)` (binary frames, one session per socket; an empty binary frame ends its sender's direction; writes wait while `bufferedAmount` is high; a `ws` socket pauses while its reader lags; writes leave in frames of at most 64 KiB, a received frame over `maxFrameSize` (1 MiB) closes the socket; an error or an abnormal close fails the read side instead of looking like the end, and writes to a socket that is not open fail), `serveGitOverWebSocket(socket, options)` and `createWebSocketConnector({ createWebSocket?, connectTimeout? })` for `ws://` / `wss://` URLs, git-daemon's request line first.
  - libp2p: `libp2pStreamDuplex(stream)` over libp2p 3's message streams (`send` / `onDrain`, `close`, `abort`) and libp2p 1/2's `{ source, sink, closeWrite?, close? }` streams (`end` ends the write side; `close` aborts a stream whose peer stopped reading after `closeTimeout`; a failing sink fails the writes), `serveGitOverLibp2pStream(stream, options)` for a `GIT_LIBP2P_PROTOCOL` (`/git/1.0.0`) handler and `createLibp2pConnector({ dial, connectTimeout? })` for `libp2p://<peer>/<path>` URLs. No libp2p dependency.
  - `webrunClientDuplex` no longer queues without bound: writes go through `createByteQueue` (1 MiB high water mark, small chunks coalesced to 64 KiB) and return a promise while it is full (a push after the end, or once the reader stopped, rejects); it gains `end` (a half-close). `webrunServerDuplex(run)` and `serveGitOverWebrun(options)` serve `serveGitConnection` on any webrun-streams `serve`.
  - `createDuplexConnector({ name, schemes, open, connectTimeout? })` turns any byte stream the host opens into a connector.
  - `serveGitOverPortMux` serves at most `DEFAULT_GIT_MAX_PORTS` (64) sessions at once unless `maxPorts` says otherwise.
- de6af72: **Fetch and clone check what they received, as git does.**
  
  - **vcs-transport:** `fetchFromConnection` runs git's `check_connected` before it writes any ref: every new ref tip must reach only objects that are here, down to the existing refs and the alternates' refs (`connectivityErrors`, receive-pack's walk, so a fetch on top of a branch reads only what it brought). A deepening fetch is checked against its new shallow commits before the shallow file changes; a clone checks the refs it writes, except those in a pack index-pack found self-contained. A failure throws `FetchCheckError` with rev-list's lines (`fatal: bad object`, `error: Could not read`, `fatal: bad tree object`, `fatal: missing blob object`). `FetchClientOptions.fsckObjects` runs index-pack's `--strict` over each received pack (imported into a quarantine, so a refused pack leaves nothing behind): fsck of every object and every named object received or present (`fatal: did not receive expected object`), as a clone's `--check-self-contained-and-connected` also does. `RepositoryFacade.loadObject` reads an object's content, `PackImportOptions.onObject` reports each received object, and commits and tags the typed stores refuse are walked as git parses them (`lenientCommitHeader`, `lenientTagTarget`).
  - **vcs-core:** pack imports report every received object with its place in the pack (`onObject` of `importPack`, `installPack` and `SerializationApi.importPack`: whole entries first, then deltas).
  - **vcs-commands:** `git fetch` fails with git's `error: <url> did not send all necessary objects` (exit 1) and `git clone` with `fatal: remote did not send all necessary objects` when a server leaves history out, writing no ref. `fetch.fsckObjects` / `transfer.fsckObjects` (or `FetchCommand.setCheckFetchedObjects`) check received objects with `fetch.fsck.<msg-id>` severities and `fetch.fsck.skipList` (`fetchFsckOf`), in git's words (`error: object <id>: <msg-id>: <message>`, `fatal: fsck error in packed object`, `fatal: index-pack failed`). `FetchCommand.setCompatibility` picks 2.43's or 2.5x's output.
  - **Received links read in memory:** pack imports report the content of every received commit, tree and tag while they hold it (`onContent` of `importPack`, `installPack`, `unpackObjects`, `SerializationApi.importPack` and `PackImportOptions`), and the fetch client checks index-pack's links from it (`ReceivedLinks`) instead of reading every object back: a clone's self-contained check of 219k objects takes 30 ms instead of 4 s. An import into a quarantine opens none for an empty stream, and a fetch discards its quarantine on any failure before the commit (a response error after the pack included). fsck reads only the blobs it checks (`ReceivedObjectsFsck.wantsBlob`). Lenient commit/tag reads ask the object's type first (`storedObjectType`) and are used by `VcsRepositoryFacade.getCommitInfo` with a commit-graph too; `VcsRepositoryFacade.getObjectType` reads the object header. `fetch.fsck.*` is read in config order where the config lists its variables (`RemoteConfigStore.entriesWithPrefix`): unknown ids give git's `warning: Skipping unknown msg id '<id>'`, the first demoted fatal id dies, and a `fetch.fsckObjects`/`transfer.fsckObjects` that is no boolean dies with `fatal: bad boolean config value`.
- 5863bf1: **git hooks run through a portable host interface, and `git reset` refreshes the index as git does.**
  
  - `GitHostEnvironment.hookRunner` (optional) executes hooks; the commands find them as git's `find_hook` does (`core.hooksPath`, relative to the worktree top, else `$GIT_DIR/hooks` of the common git directory) through the repository's FilesApi (`Worktree.getFiles`), and a hook that is not executable gets the `advice.ignoredHook` hint (worded as the runner's `compatibility` says, 2.43 or 2.5x). Without a runner no hook runs, as before. On Node, `createNodeHookRunner` (vcs-utils-node) spawns the script, its stdout joined to its stderr where git joins them; pass it as `createNodeGitHostEnvironment({ hookRunner })`.
  - Hooks wired: commit (`pre-commit`, `prepare-commit-msg`, `commit-msg`, `post-commit`, `post-rewrite` for `--amend`; `setNoVerify`), merge (`pre-merge-commit`, `prepare-commit-msg`, `commit-msg`, `post-merge`; a refusal leaves the merge for `git commit`), checkout, switch, restore, clone and worktree add (`post-checkout`, its exit code in the result), rebase (`pre-rebase`, the post-checkout of onto, the picks' `prepare-commit-msg` and `post-commit`, `post-rewrite` "rebase"), cherry-pick and revert (the sequencer's `prepare-commit-msg` and `post-commit`), am (`applypatch-msg`, `pre-applypatch`, `post-applypatch`), push (`pre-push`, which can stop the push: `HookFailedError`), the receive side of a local push (`pre-receive`, `update`, `post-receive`, `post-update`, `push-to-checkout` for `updateInstead`, their output relayed as "remote: " lines), and the files ref store's batches (`reference-transaction`: `preparing` in 2.5x, `prepared`, `committed`, `aborted`; a refusal throws `RefTransactionAbortedError`). Commands expose what hooks wrote with `getHookOutput()` / `getHookStdout()`.
  - A commit with a hook runner updates HEAD in one transaction expecting its parent, as git's `update_head_with_reflog`.
  - vcs-transport: `PushClientOptions.prePush` (and `PushRefusedByHookError`), `relayPostReceive` for receive-pack (post-receive awaited before the side-band closes, as git), and the push client reads the side-band to its end so messages after the report reach `onProgress`.
  - `git reset` (mixed, and with paths) refreshes the index's stat data and reports "Unstaged changes after reset:" with `M`/`D`/`T`/`A`/`U` lines (`ResetCommand.getOutput()`), as `refresh_index` does; `setQuiet` and `setNoRefresh` as `-q` and `--no-refresh`, with the slow-refresh hint (`advice.resetNoRefresh`).
  - What a hook changes is taken as git takes it: `commit -a` reads the index lock back after `pre-commit` (`StagingIndexLock.reread`, `IndexFileLock.reread`); a partial commit (`setOnly`) gives its hooks git's temporary index (`$GIT_DIR/next-index-<n>.lock`: HEAD with the named paths), reads it back after `pre-commit` and removes it once the commit is made or given up. A hook that is a symbolic link counts only when its target is executable (followed through the FilesApi, else the host's `statFile`), and the Node runner reports a spawn failure (EACCES) as git's "cannot run".
  - reference-transaction: `committed` and `aborted` run once the ref locks are released; a deletion runs git's nested transaction on the packed store, and `Refs.remove(name, { deleteRefs })` runs the hook for refs under `refs/` (branch -d and tag -d pass `deleteRefs`, git's `delete_refs`); the hook context says which git version makes a call (`RefTransactionContext`). The receive side of a local push runs the remote's hook (a refusal makes receive-pack die, as git: the push fails with git's "fatal:" line and no ref moves); a command puts back the store's previous hook when it ends, and a command without a hook runner leaves a hook someone else set (`FileRefStore.setTransactionHook`) in place. A deletion that finds a ref lock or `packed-refs.lock` held tells the hook what git does (`aborted` only for the packed store's transaction, packed-refs.lock being taken before `prepared`). vcs-transport: `batchNonAtomic` (2.5x's two batches, each phase's update hooks run before its transaction, the deletions' committed before the rest's update hooks), `interleaveUpdateHook` (2.43's update hook then ref per command), `publishBeforeUpdate` (objects migrated after pre-receive, as git) and `BatchOptions.emptyTransaction`; the push client sends its commands in git's order (the remote's refs as advertised, then new ones).
  - rebase -i: `reword` runs `git commit --amend -e`'s hooks (pre-commit, prepare-commit-msg `commit HEAD`, commit-msg, post-commit, post-rewrite `amend`); `--continue` with staged changes those of `git commit -n -e` (prepare-commit-msg, post-commit, post-rewrite `amend` for an amend), with `GIT_REFLOG_ACTION` as git sets it.
- 53ecad0: **`GIT_GRAFT_FILE` everywhere grafts count, git's diffstat widths, log decoration filters, `fetch -v` / `--porcelain`.**
  
  - **Grafts file:** `commitGraphCompatible` takes `readGraftFile` (the file `GIT_GRAFT_FILE` names, read in place of `info/grafts`); the files commit-graph provider and `writeCommitGraph` pass the environment's, so a graph is neither read nor written while that file has grafts. `git fsck` reads the grafts file the environment names too (its walk, its deprecation hint, its commit-graph checks). `fsck`'s `git commit-graph verify` now reads grafted commits as git does once the grafts file is read: the grafted parents from the object database, no parents from the graph (`VerifyGraphOptions.ungraphedParents`), and the grafts file's `bad graft data` errors repeated by that second process. A relative `GIT_GRAFT_FILE` is read from the worktree top (the git directory when bare), where git's setup has changed to before opening it, not from the process's current directory: `graftFileReader` takes a `GraftFileBase` (the repository's FilesApi and directory, or a host directory), and `graftFileBaseDir` gives that directory for a git directory.
  - **`diff --stat` widths:** names are measured with git 2.56's character widths (`gitStrWidth`, git's `utf8_strwidth`: byte count for invalid UTF-8) and shortened behind `...` as git 2.55+ does (`gitCharWidthAt`, diff.c's `utf8_ish_width`: whole characters, invalid bytes one column, control characters none). `blame`'s author column uses the same widths.
  - **Decorations:** `createRefDecorationFilter` is `git log`'s decoration filter (`--decorate-refs`, `--decorate-refs-exclude`, `--clear-decorations`, `log.excludeDecoration`, `log.initialDecorationSet=all`, the default set), and `loadRefDecorations` takes it as `logOptions` (with `decorate` / `log.decorate=full` for full ref names in `%d`, `%D`).
  - **Fetch:** `FetchCommand.setVerbose` (`-v`: ` = [up to date]` lines, the remote column measured over them) and `setPorcelain` (`--porcelain`: `<flag> <old> <new> <ref>` lines in `display`); `fetch.output=compact` is honoured. As in git, a refused ref update stops the fetch before tag backfill (no second round trip is made) and before the remote HEAD is followed. With `--atomic`, the stale refs of `--prune` are deleted in the fetch's one ref transaction (git's prune_refs queues them there): a refused update writes no ref, deletes no stale ref and writes no `FETCH_HEAD` line; a transaction the ref store refuses (a D/F conflict) leaves everything as it was, skips the remote HEAD, and is reported as git reports it: the lines the updates were accepted with, then git 2.5x's error (`FetchResult.errors`, `FetchClientResult.refTransactionError`; `FetchRefUpdate.accepted` and `aborted`). Without `--atomic` the prune stays a step of its own, first. The tags of objects already here are fetched with the tips (git's find_non_local_tags), not in a second round.
- bbf5ca1: **`git hook run` and `git hook list`, configured receive hooks, and the reference-transaction hook of pack-refs.**
  
  - `git.hookRun(name)` (`HookRunCommand`) is `git hook run`: the arguments after `--` (`setArgs`), `--to-stdin` (`setToStdin`, read only when a hook runs; "could not open" is fatal, exit 128), `--ignore-missing`, git's "cannot find a hook named" error (exit 1), git 2.5x's refusal of unknown hook names (`setAllowUnknownHookName`; 2.43 runs any name), the configured hooks before the hooks directory's script and their exit codes or'ed together. The result carries git's exit status and stderr; `getHookOutput()` gathers the same.
  - `git.hookList(name)` (`HookListCommand`) is git 2.5x's `git hook list` with `-z` and `--show-scope`: configured hooks by friendly name (`disabled` / `event-disabled` marked), the script as `hook from hookdir`, "no hooks found" (exit 1). git 2.43 has none: the command throws its usage error there.
  - The receive side of local and served pushes runs git 2.5x's configured hooks (`hook.<name>.*` of the receiving repository) for pre-receive, update, post-receive, post-update, push-to-checkout and reference-transaction, as receive-pack runs them through the hook API (`OpenedRepositoryConfig.listWithOrigin`).
  - `pack-refs` and `gc` run the reference-transaction hook as git's `files_optimize`: the packed store's transaction (`<zero> <id> <ref>` for each loose ref packed, also when there is none), then one transaction per pruned ref in reverse name order; a refusal throws `RefTransactionAbortedError` with nothing packed or the rest left loose. `pack-refs` without `--all` or refs packs the loose tags as git does (`Refs.packRefs` takes `prefixes`), and per-worktree refs (`refs/bisect/` ...) stay loose.
  - Config values carry their scope (`ConfigValueOrigin.scope`: system, global, local, worktree; an included file's is the including file's).
  - `Refs.packRefs` returns how many refs it packed (`PackRefsResult.refsPacked` counts those) and takes `auto` (git 2.5x's `pack-refs --auto`, `should_pack_refs`: nothing locked and no hook unless `max(16, log2(packed-refs size / 100) * 5)` loose refs wait; `PackRefsCommand.setAuto`, and 2.5x's `gc --auto`) and `onError`. A loose ref whose object is missing stays loose (`error: <ref> does not point to a valid object!`, `FilesRefBatchOptions.hasObject`), as does a loose name failing check_refname_format; a ref changed between its packing and its prune keeps its loose file (`error: cannot lock ref '<ref>': is at X but expected Y`, its transaction ending after `preparing`). The error lines go to the hook output and `errors` of `PackRefsResult` / `GCCommandResult`.
  - `git hook run --to-stdin=<path>`: a relative path climbing above the repository's files is read from the host (never the worktree's file of the clamped name); one that cannot be read is git's fatal "could not open".
  - A broken `hook.<name>.*` configuration of the receiving repository makes receive-pack die (`ReceivePackDiedError` from a receive hook): a local push fails with git's fatal line and "the remote end hung up unexpectedly", a served HTTP push's answer ends without a report; no ref moves.
  - Config include paths resolve `.` and `..` (`include.path=../inc` of a repository's config, read by `FileWorktree.openRepositoryAt` and the working copy alike); one above the repository's files is read from the host where the files have a root directory.
- c72622c: **httpeers connectors, a server side for `messagePortDuplex`, and a transports guide.**
  
  - `@statewalker/vcs-transport-httpeers`: `createHttpeersConnector(options)` registers mesh peers with a `GitTransportRegistry`, so vcs-commands' clone, fetch, pull, push and ls-remote reach them. `httpeers://<peer>/<repo>` (default `mode: "http"`) is smart HTTP over the mesh through `meshRemoteFetch`: a webrun caller to the peer (`call(peer)`, with the membership token, sent only to that peer's origin) or a `fetchImpl` that already reaches peers (`peerUrl`). `httpeers+git://<peer>/<repo>` (`mode: "native"`) is git's native protocol on a stream the host opens (`openStream`, e.g. httpeers-libp2p's `openDuplex`), the token in the stream's open frame. `meshGitDuplexHandler(options)` serves that side, mounted at `HTTPEERS_GIT_DUPLEX_PATH` (`/git`) of httpeers-libp2p's duplex mounts: the token is verified as `meshGitHandler` verifies a request's (a refusal is git's `ERR access denied: …`), then `serveGitConnection` serves the repository the request line names with the same capability rules (`git:read` to fetch; `git:write`, or `git:write-own` inside `refs/peers/<peerId>/*`, to push; receive-pack only with `enableReceivePack`; `daemon.*` never overrides). The stream's proven peer is its only identity (an `access.provenPeer` is ignored). Its `guard(serve, caller, context)` option wraps each authorized stream, e.g. with httpeers-access's `guardStream` to end a revoked member's stream; `MeshCaller.issuedAt` (the token's `iat`) lets a member re-admitted with a newer token through. The peer of an httpeers URL must be letters, digits, `-` or `_` (no `user@`, no `:port`); a `fetchImpl` needs `peerUrl`, which carries the case-sensitive peer id in the path, and a `call` connector addresses its requests to `HTTPEERS_CALL_ORIGIN`. `withMeshToken`/`meshRemoteFetch` take a `scope`: the token goes only to that base URL and below it, and a redirect out of it is refused; the connector pins the token to the repository's URL, as every peer behind one edge shares an origin.
  - `@statewalker/vcs-transport`: `serveOverPort(port, run, options?)` runs any server (`serveOverDuplex` for a fixed service, `serveGitService`) on one end of a port whose other end is `messagePortDuplex`: the non-deprecated replacement for the server side of `createMessagePortDuplex`. `serveOverPort` and `serveGitOverPort` close their port once the session is over (right away when the client took the whole answer, else `lingerTimeout`, default `DEFAULT_PORT_LINGER_TIMEOUT` = 1 s, after the server settled), which closes the other end of a `MessageChannel` too, so a session nobody closes keeps no worker or Node process alive; their teardown closes the port as well. `messagePortDuplex`'s `close` closes its port (idempotent), and a real `MessagePort`'s `close` event fails a session whose other end went away instead of leaving it waiting. `webrunServerDuplex` takes `onDrained` (the run settled and every byte it wrote was handed on). `createDuplexConnector` aborts a pending `open` when the request's `signal` aborts, as when `connectTimeout` passes. A user guide, `docs/transports.md`, covers choosing a transport, registering connectors with `Git.fromWorkingCopy(workingCopy, { transports })`, client and server examples for HTTP, git://, ssh, MessagePort, WebSocket, libp2p and HTTPeers, and the security notes for serving. `createMessagePortDuplex`, `messagePortFetch` and `messagePortServe` stay deprecated (the integration tests still use them).
  - `@statewalker/vcs-workspace`: the `duplexRemote` example uses `messagePortDuplex` / `serveOverPort`.
- bd31e0f: **git's native protocol over any byte stream: `git://` and ssh connectors on host hooks, and a git-daemon server.**
  
  - `Duplex.end?()` half-closes a stream's write side. The native clients end it where git closes its end (after a push's request, after the final flush of a fetch); a transport without it is left as it is. Node sockets that carry it need `allowHalfOpen: true` on both ends.
  - `serveGitConnection({ duplex, resolveRepository, enableReceivePack, ... })` serves a connection as git-daemon does: it reads the request line (`readGitDaemonRequest`, without losing the bytes after it), refuses as daemon.c does (`ERR access denied or repository not exported: <path>`, or the informative reasons; aliases such as `/../`, receive-pack unless enabled, a repository's `daemon.uploadpack` / `daemon.receivepack` override, upload-archive), and runs upload-pack (v0, v1, v2) or receive-pack with the repository's settings. `serveGitService` serves a session whose service, path and `GIT_PROTOCOL` arrived out of band (an ssh channel; `parseGitServiceCommand` reads `git-upload-pack '<path>'`).
  - `createGitDaemonConnector({ openSocket })` (`git://`, port 9418) and `createSshConnector({ exec })` (`ssh://`, `git+ssh://`, `ssh+git://`, `host:path`: git's `git-upload-pack '<path>'` with `sq_quote`, `GIT_PROTOCOL=version=<n>`), registered by `createDefaultTransports({ openSocket, exec })` only when the host gives the hook. `GitConnectRequest.program` carries `--upload-pack` / `--receive-pack` and `remote.<name>.uploadpack` / `receivepack`.
  - Served paths are client input: both modes refuse git-daemon's aliases (`daemon_avoid_alias`: `..`, `//`, `/./`, a trailing `/.` or `/..`), a NUL and a backslash before `resolveRepository` sees them (`isUnsafeServicePath`; an implicit session's relative and `~/` paths checked as if below `/`). `createBasePathResolver({ files, basePath, openRepository, exportAll, userPath, strictPaths, whitelist })` maps a path as git-daemon does: base-path join, `~user` only through `userPath` (an empty user, `~` or `~/x`, refused), an empty path refused, enter_repo's `.git` suffixes, the directory list, `git-daemon-export-ok` unless `exportAll`, and nothing outside the base (symbolic links followed where the FilesApi reads them).
  - Served settings layer as git's config files do: git's defaults, the operator's `settings`, what the repository's config sets explicitly (`explicitServerSettingsFromConfig`; `serverSettingsFromConfig` still gives every key), then the resolver's `settings`; hidden ref lists concatenate in layer order across `hideRefs` and the service lists (`layerServeSettings`), so a repository's `!pattern` never unhides a ref the resolver hides. An implicit session ignores `daemon.*` unless `allowOverride`, and refuses with one text unless `informativeErrors`. `serveGitConnection` takes `initTimeout` and `timeout` (git-daemon's `--init-timeout` / `--timeout`; `timeout` bounds reads and writes alike, so a client that stops reading is cut off).
  - ssh: a host or user starting with `-` is refused ("strange hostname '<user@host>' blocked"), and `sshArgs(target)` gives an ssh client's arguments with `--` before one `user@host` argument and a checked port. `parseGitServiceCommand` reads the command as git-shell's `sq_dequote` (nothing after the quoted argument, no `-` argument).
  - Smart-HTTP `info/refs` failures use git's words: "fatal: repository '<url>/' not found", "fatal: Authentication failed for '<url>/'", "fatal: unable to access '<url>/': The requested URL returned error: <code>", a `text/plain` body first as `remote:` lines.
  - `ls-remote` keeps the v2 symref and peeled data (`RemoteRef.symbolic`, `target`, `peeledObjectId`), takes the default branch from HEAD's symref, sends `ref-prefix` for `--heads` / `--tags` over v2 (with `ref-prefix HEAD`, so the default branch is still known), shows both kinds with both flags, and passes `setUploadPack` (else `remote.<name>.uploadpack`) to the connector. `fetch().setUploadPack()` and `clone().setUploadPack()` (git's `--upload-pack` / `-u`) too.
  - vcs-commands: `servedRepositoryOf(openedRepository, { hooks })` gives `serveGitConnection` a repository with the settings git's receive-pack reads from it (the `receive.*` and hidden ref ones through its `config`, so only what that sets overrides the operator's).
  - `IdleTimer` and `abortErrorOf` are no longer exported from the package root.

  - **vcs-utils:** new `createSha256()`, an incremental `Hasher` like `createSha1()` (on `@noble/hashes`). The streaming request body helpers (`requestBody`, `fetchWithRequestBody`, `shouldStreamRequestBody`, `supportsRequestStreams`, `isBrowserContext`, `toReadableStream`) moved here from vcs-transport and are exported from `@statewalker/vcs-utils/streams`.
  - **vcs-transport:** re-exports those helpers from vcs-utils; its public API is unchanged.
  - **vcs-transport-lfs (breaking):** `lfsUpload` sends a streaming body (`duplex: "half"`, with `content-length` from the local object's manifest; browsers collect unless the new sixth argument `{ streamRequestBody: true }` is passed, and drop `content-length` from a streamed body). An object whose local size disagrees with the pointer or the batch response is reported as `size mismatch` and skipped, and any per-object failure, a rejected `fetch` included, is that object's `error` event instead of aborting the rest. `lfsDownload` and the server's `PUT` store the body as it arrives, hashing it on the way, and record no mapping when its SHA-256 does not match. A refused object is not removed (store ids come from content, so removing it could delete a concurrent honest upload of the same bytes); the store's `gc`, with the resolver's values as live roots, reclaims it. `lfsDownload` also checks the pointer size and reports the new reason `size mismatch`, and the server caps a `PUT` at its `content-length` (`422`); a body that runs past either is cut off and its stream cancelled. Unread responses (upload replies, failed downloads) are cancelled. The server's `GET` streams with `content-length`. `sha256Hex` now takes a buffer or a stream (`ByteSource`) and no longer uses Web Crypto. New: `createLfsPointer` (streamed oid and size, the hashing half of a clean filter), `formatLfsPointer`, `parseLfsPointer` (strict: `version` first, other keys in alphabetical order, size a safe integer), `LFS_POINTER_VERSION`, `storeVerified`, and the types `LfsTransferOptions`, `LfsStoreResult`, `ByteSource`.
  - **vcs-transport-xet (breaking):** a webrun-chunks download (then named `xet`; see the `hf-xet-read` changeset for the rename) verifies the assembled object by streaming it through SHA-256 and also checks its size (`size mismatch`). The server now verifies an uploaded object's whole-file SHA-256 against the oid while assembling it, and refuses it on a mismatch (`webrun-chunks upload refused: sha256 mismatch`). As with LFS, a refused object on either side is left for the store's `gc`, never removed. New `WebrunChunksOptions.streamRequestBody` for the basic fallback.
