# @statewalker/vcs-core

## 0.6.0

### Minor Changes

- d84c354: **Tree entry modes read as git reads them (`canon_mode`), everywhere.**
  
  A tree that stores a blob as 100664 (older git wrote it) now reads as 100644, as git's `decode_tree_entry` reads it, so a repository with such trees behaves as with native git: `status` is clean after `reset --hard`, and `merge`, `checkout`, `cherry-pick`, `revert`, `rebase` (patch-ids), `stash`, `reset`, `diff` and `log` no longer see a mode change between 100664 and 100644, or refuse with "local changes would be overwritten".
  
  - **vcs-core:** the tree store's `load`, `entries` and `getEntry` give canonical modes (`canonTreeMode`: a regular file 100644 or 100755 by its owner's execute bit, a symlink 120000, a directory 40000, anything else a gitlink); `raw` still gives the stored bytes, and serializing a stored tree (`SerializationApi`) copies them. `decodeTreeBytes(bytes, { canonicalModes: true })` reads canonical modes (without the option, modes as stored), and `treeModesRewritten(entries)` says whether such a list came from a tree written with other modes (encoding it again makes another tree). fsck keeps reading the modes as stored (`badFilemode` for 100664 under `--strict`).
  - **vcs-working-tree:** the files and git stagings' `writeTree` reuses the directories the index's cache-tree has valid, as git's write-tree does (a tree primed by a reset keeps its stored 100664 modes). `updateCacheTree` computes a directory as the canonical tree its entries make: where the stored tree holds other modes, that tree is valid only if stored (git's `WRITE_TREE_REPAIR`), else invalid.
  - **vcs-commands:** `reset --hard` primes the cache-tree with the target tree (`prime_cache_tree`) and `reset --mixed` keeps it with the changed paths invalid; `stash apply` invalidates the paths it merges. A combined diff's `-U0` hunk header prints a count below zero as git's `%lu` does (`+1,18446744073709551615`), in `diff` and `log --cc`.
  - **vcs-store-sql**, **vcs-transport-adapters:** syncing a tree to the SQL store and an object's size read the stored bytes; the native SQL tree store reads canonical modes.
- 1777896: **Commit-graphs: read, written and verified as git does, and used by history walks.**
  
  On a 5000-commit repository with a graph, a walk of every commit takes 3.5 ms instead of 49 ms, a merge base of distant commits 3 to 5 ms instead of 41 to 48 ms, and an ancestor check about 2 ms instead of 40 ms, level with `git rev-list` and `git merge-base` over the same graph.
  
  - **vcs-core (`history/commit-graph`):** `readCommitGraph` loads `objects/info/commit-graph` or the split chain in `info/commit-graphs/` as git's `commit-graph.c` does (header, chunk table, OIDF, OIDL, CDAT, EDGE, GDA2/GDO2, BIDX/BDAT, BASE; git's checks and messages on load; a broken chain kept up to its last good layer). `CommitGraph` gives each commit's parents, tree, date, topological level and generation (corrected commit date with GDA2) without reading the commit; `bloomMayContainPath` queries its changed-path filters. `writeCommitGraphFile` writes files byte-identical to `git commit-graph write` (`--append`, `--split[=no-merge|replace]`, `--size-multiple`, `--max-commits`, `--expire-time`, `--[no-]changed-paths` with murmur3 hash versions 1 and 2, `--max-new-filters`; GDA2 unless `commitGraph.generationVersion=1`; the filters of an existing graph kept). `verifyCommitGraph` is `git commit-graph verify`. `loadRepositoryCommitGraph` and `commitGraphCompatible` follow git's `prepare_commit_graph`: no graph with `core.commitGraph=false`, replace refs, grafts or a shallow repository.
  - **vcs-core (commits):** `createCommits(objects, { commitGraph })`; `Commits.getHeader` (tree, parents, commit time, generation) and `getParents`, `getTree` and `walkAncestry` read the graph for the commits it has and parse the others (a stale graph is fine). `findMergeBase` is now git 2.56's merge-base (`paint_down_to_common` over a queue ordered by generation then date, with its side-exhaustion exit in the graph; redundant bases removed), returning every merge base, best first, as `git merge-base --all` (it returned the first common ancestor of a depth-first walk). `isAncestor` and the redundancy check skip commits whose generation shows they cannot reach the commit sought. `getMergeBases` and `isAncestorOf` (`commit-reach.ts`) are exported. `History.commitGraph` is the provider; `listObjects` takes a `commitHeader` lookup.
  - **vcs-store-files:** the files backend reads the repository's graph on first use. `writeCommitGraph` is `git commit-graph write --reachable` (or from given commits) in a repository; `readCommitGraphSettings` reads the config. `gc` writes the graph at the end when `gc.writeCommitGraph` is true (the default), as `git gc`, and its reachability walk reads commits from the graph.
  - **vcs-commands:** `fsck` verifies the commit-graph as git's fsck runs `git commit-graph verify` (exit bit 16, `FSCK_ERROR_COMMIT_GRAPH`). merge, rebase, pull, octopus and merge-ort's virtual bases use the store's walks and the graph's generations (the merge-base queue ordered by generation when the graph has corrected dates, as git orders it).
  - **vcs-transport-adapters:** upload-pack and receive-pack walks read commits from the graph.
- 21d6866: **Delta base cache and idx open as git does them: faster packed reads, rev-walks and repository opens.**
  
  On a repacked 5000-commit repository (depth 50, files backend), reading 2000 packed blobs takes about two thirds of the time it took, a rev-walk about 90%, and opening a repository about half. Object bytes, read errors and the streaming of large objects are unchanged.
  
  - **Delta base cache (vcs-core):** as git's `unpack_entry`, the bases a read resolves on its way up a delta chain are cached and the object asked for is not: it is handed to the caller without a copy (a cached object asked for is still copied, so callers never hold a buffer the cache holds). Small bases are carved from 64 KiB slabs owned by the cache instead of each getting its own `Uint8Array`; a slab is never reused, and the budget counts a whole slab while any entry lives in it. The LRU is an intrusive list. As git's `add_delta_base_cache`, a new entry evicts the least recently used others until the cache is within its budget and is always admitted, even alone over it: a budget of 0 keeps the most recent base (reading a chain upwards costs one or two delta steps per object), and the base of the object asked for is always among the bases a read caches. The default budget is git's `core.deltaBaseCacheLimit` default, 96 MiB (was 16 MiB, which made a random read workload evict bases it needed again). `DeltaBaseCache` gains `alloc`, `hits`, `ownAllocations`, `slabsCreated` and `size`; `DEFAULT_DELTA_BASE_CACHE_LIMIT` is exported. Reading the same delta twice now costs one delta step instead of a copy.
  - **idx open (vcs-core):** `openPack` checks what git's `check_packed_git_idx` checks (header, monotonic fan-out, a length that fits the tables) and no longer hashes the whole idx or walks every entry. A fan-out bucket's ids are checked (sorted, inside the bucket) the first time a lookup searches it, and a 64-bit offset index when it is read, so a corrupt idx fails with `PackError` when used, never with another object's bytes. `openPack(..., { verifyIndex: true })` and `PackFile.verifyIndex()` run git's `verify_pack_index` (the SHA-1 and every entry); `PackSet.install` uses it for the idx it just wrote, also when it shares the open of a scan running at the same time; an installed pack whose idx fails it is refused as a scan refuses a corrupt pack (recorded in `skipped`, left out of the set, not opened again until its files change). Behaviour change: an idx whose only fault is its own checksum, or whose ids are out of order, now opens as git opens it (the pack is no longer skipped); a `PackFile` lookup into a broken bucket raises `PackError` and `has` answers false for it, and a `PackSet` treats such a bucket as holding nothing (a miss, which rescans, as git's). `PackStats` gains `idxBucketsChecked` and `idxVerified`.
  - **Commit reads (vcs-core):** `GitObjects.getNow` (optional) returns an object without a promise when it is in memory; the commit store uses it. Returning the cached commit without a copy was measured and left out: the copy is under the noise of a rev-walk.
  - **vcs-store-files:** the backend honours `core.deltaBaseCacheLimit` (`readDeltaBaseCacheLimit`, git's size syntax: `96m`, `512k`, hex, octal), and `withPacks` implements `getNow`.
- 457680a: **Diff and blame output byte for byte as git's, on the xdiff port.**
  
  `@statewalker/vcs-utils`: the xdiff port takes git's whitespace flags (`ignoreWhitespace` `-w`, `ignoreWhitespaceChange` `-b`, `ignoreWhitespaceAtEol`, `ignoreCrAtEol`), and gains xdiff's emitter: `unifiedDiff`/`unifiedDiffHunks` print the hunks of `git diff` (context, inter-hunk context, `-W`, `--ignore-blank-lines`, function lines in hunk headers cut at 80 bytes and at broken UTF-8 as git does, `\ No newline at end of file`), `diffLineCounts` counts as the diffstat does, and `xdiffHunks` gives the changes `git blame` uses (common tail trimmed). `userdiffFindFunction` and `BUILTIN_FUNCNAME_PATTERNS` port git's diff drivers (builtin `cpp`, `python`, `java`, ... patterns of git 2.56, and `diff.<driver>.xfuncname`/`funcname`), matched as glibc matches them: `compilePosixRegex` (new, `@statewalker/vcs-utils`) is a POSIX regular expression engine over bytes, extended and basic syntax with the GNU extensions, leftmost-longest matches and subexpressions placed as glibc places them, back-references, `REG_ICASE` folding ASCII only, the patterns glibc refuses refused (git then dies with "Invalid regexp to look for hunk header"), and time linear in the line for patterns without back-references (JavaScript's backtracking took seconds on the `csharp` pattern). `BUILTIN_FUNCNAME_PATTERNS_2_43` holds the drivers of git 2.43 and 2.44 (`userdiffFindFunction`'s third argument). `legacyMinimal` reproduces git before 2.5x, whose `minimal` still set aside many-matched lines. Breaking: the JGit-style `HistogramDiff`, `HistogramDiffIndex`, `MergeAlgorithm`/`merge3Way`, `getAlgorithm`, `DiffAlgorithm` and `DEFAULT_ALGORITHM` are removed (nothing used them; diffs and merges run on `xdiff` and `mergeLines`); `SupportedAlgorithm`, `MyersDiff`, `RawText` and `RawTextComparator` stay.
  
  `@statewalker/vcs-commands`: `DiffCommand.callText(format)`/`callBytes(format)` print `git diff` as git does: the patch (`diff --git`, `old mode`/`new mode`, `new file mode`, `deleted file mode`, `similarity index`/`rename from`/`rename to`, `index` lines with abbreviated ids, `Binary files ... differ`, quoted paths, a file turned into a symbolic link as a deletion and an addition), `stat` (git's widths; `setOptions({ stat: { width } })` for `COLUMNS`), `numstat`, `shortstat`, `name-only` and `name-status`, with `setOptions` for `-U`, `--inter-hunk-context`, `-W`, `--diff-algorithm`, `--[no-]indent-heuristic`, the whitespace options and `--ignore-blank-lines`, and the configuration (`diff.algorithm`, `diff.indentHeuristic` default on, `diff.context`, `diff.interHunkContext`, `diff.renames` default on, `diff.renameLimit`, `core.quotePath`, `diff.statNameWidth`, `diff.statGraphWidth`, `diff=<driver>` attributes with `diff.<driver>.binary`/`.algorithm`/`.xfuncname`). `git diff` without trees now compares the index with the worktree (it compared HEAD with itself), `setOldTree(a)` alone compares `a` with the worktree (it compared `a` with HEAD), and paths sort in git's byte order; `setRenames(true)` detects renames in `call()`. `formatNoIndexDiff` prints `git diff --no-index` for two files. `DiffFormatter` now prints exactly git's text: `toString` ends lines with LF, `formatAll` concatenates, `formatBytes` keeps non-UTF-8 content, hunks start at 0 for an empty side (`@@ -0,0 +1,3 @@`), hunk lines include the `\ No newline at end of file` marker, and the default algorithm is myers as git's. `BlameCommand` is a port of git's blame (`blame.c`): commits by committer date, whole-file renames followed by default (git's default; `setFollowRenames(false)` is `--no-follow`), the xdiff diff with `diff.algorithm` and the indent heuristic, root commits as boundaries (`setShowRoot`, `blame.showRoot`), `setIgnoreWhitespace` (`-w`), `setLineRanges` (`-L`); lines are split at LF only (a CR-only file is one line, as in git). `BlameEntry` gains `previous` and `boundary`, `BlameResult` gains `content`, and `formatBlamePorcelain` (`--porcelain`, `--line-porcelain`) and `formatBlame` (default output, `-n`, `-f`, `-e`, `-s`, `-l`, `-t`, `-b`) print them as git does. Options for older git: `histogramRediff`, `legacyMinimal`, `renameCountLastSpan`, `namesFromContents` (diff) and `setCompatibility` (blame), `alwaysWidenAbbrev` (blame output).
  
  A conflicted path shows as git shows it: in `git diff`, the combined diff of stages 2 and 3 against the worktree file (`diff --cc`, `index a,b..0000000`, `@@@` hunks, dense as git's `combine-diff.c`; `writeCombinedDiff`), printed before the other files, and in the other formats as an unmerged entry followed by stage 2 against the worktree; in `git diff A`, the worktree file against `A`. A submodule with changes of its own shows as `Subproject commit <id>-dirty` in the worktree modes (untracked files in it count only with `diff.ignoreSubmodules=none`, as git's default ignores them; `diff.ignoreSubmodules` is read). `setOldTree`/`setNewTree` with a revision that names nothing throws (`RefNotFoundError`, "bad revision"), as git exits 128, instead of diffing against an empty tree. Abbreviated ids follow git: `core.abbrev` (auto, a number, `no`), 7 digits up to 16383 packed objects and more beyond (`findAbbrevLengths` in `@statewalker/vcs-core`, from the new optional `GitObjects.approximateCount`, which the files backend answers from its packs only, as git counts), and longer where another object shares the prefix; in `index` lines (`DiffOutputOptions.abbrevLengths`) and in blame's default output (`BlameResult.autoAbbrev()`, `formatBlame`'s `autoAbbrev`, then the boundary marks of git 2.5x or one more digit for older git).
  
  Remaining differences from git's diff: paths that are not valid UTF-8 (core and the stores keep paths as strings); `diff.noprefix`, `diff.mnemonicPrefix`, `diff.orderFile`, textconv drivers (`diff.<driver>.textconv`) and `submodule.<name>.ignore` are not read; glibc itself mishandles a few contrived patterns with word anchors after a repetition (it finds `b*\B` in "Ab" at 2), which the matcher does not copy.
- de6af72: **Fetch and clone check what they received, as git does.**
  
  - **vcs-transport:** `fetchFromConnection` runs git's `check_connected` before it writes any ref: every new ref tip must reach only objects that are here, down to the existing refs and the alternates' refs (`connectivityErrors`, receive-pack's walk, so a fetch on top of a branch reads only what it brought). A deepening fetch is checked against its new shallow commits before the shallow file changes; a clone checks the refs it writes, except those in a pack index-pack found self-contained. A failure throws `FetchCheckError` with rev-list's lines (`fatal: bad object`, `error: Could not read`, `fatal: bad tree object`, `fatal: missing blob object`). `FetchClientOptions.fsckObjects` runs index-pack's `--strict` over each received pack (imported into a quarantine, so a refused pack leaves nothing behind): fsck of every object and every named object received or present (`fatal: did not receive expected object`), as a clone's `--check-self-contained-and-connected` also does. `RepositoryFacade.loadObject` reads an object's content, `PackImportOptions.onObject` reports each received object, and commits and tags the typed stores refuse are walked as git parses them (`lenientCommitHeader`, `lenientTagTarget`).
  - **vcs-core:** pack imports report every received object with its place in the pack (`onObject` of `importPack`, `installPack` and `SerializationApi.importPack`: whole entries first, then deltas).
  - **vcs-commands:** `git fetch` fails with git's `error: <url> did not send all necessary objects` (exit 1) and `git clone` with `fatal: remote did not send all necessary objects` when a server leaves history out, writing no ref. `fetch.fsckObjects` / `transfer.fsckObjects` (or `FetchCommand.setCheckFetchedObjects`) check received objects with `fetch.fsck.<msg-id>` severities and `fetch.fsck.skipList` (`fetchFsckOf`), in git's words (`error: object <id>: <msg-id>: <message>`, `fatal: fsck error in packed object`, `fatal: index-pack failed`). `FetchCommand.setCompatibility` picks 2.43's or 2.5x's output.
  - **Received links read in memory:** pack imports report the content of every received commit, tree and tag while they hold it (`onContent` of `importPack`, `installPack`, `unpackObjects`, `SerializationApi.importPack` and `PackImportOptions`), and the fetch client checks index-pack's links from it (`ReceivedLinks`) instead of reading every object back: a clone's self-contained check of 219k objects takes 30 ms instead of 4 s. An import into a quarantine opens none for an empty stream, and a fetch discards its quarantine on any failure before the commit (a response error after the pack included). fsck reads only the blobs it checks (`ReceivedObjectsFsck.wantsBlob`). Lenient commit/tag reads ask the object's type first (`storedObjectType`) and are used by `VcsRepositoryFacade.getCommitInfo` with a commit-graph too; `VcsRepositoryFacade.getObjectType` reads the object header. `fetch.fsck.*` is read in config order where the config lists its variables (`RemoteConfigStore.entriesWithPrefix`): unknown ids give git's `warning: Skipping unknown msg id '<id>'`, the first demoted fatal id dies, and a `fetch.fsckObjects`/`transfer.fsckObjects` that is no boolean dies with `fatal: bad boolean config value`.
- 0a39cdc: **New `git.fsck()` and `git.verifyPack()` porcelain, with git's checks, messages, output order and exit status.**
  
  - **vcs-commands (`FsckCommand`):** `git fsck` after git's `builtin/fsck.c` and `fsck.c`. Every stored object is read and checked with git's message ids, severities and texts (`error in tree <id>: duplicateEntries: contains duplicate file entries`): trees (modes, zero-padded modes, order, duplicates, `.`, `..`, `.git` under its HFS+/NTFS spellings, full and empty names, null ids, symlinked `.gitmodules`/`.gitattributes`/`.gitignore`/`.mailmap`), commits (header order, tree and parent ids, author and committer lines, dates, time zones, NUL bytes), tags (object, type, tag name, tagger, gpgsig, extra headers) and `.gitmodules`/`.gitattributes` blobs. `fsck.<msg-id>` config, `setMessageType` and `setStrict` (`--strict`) set severities. Then everything reachable from the refs, the reflogs, the index (entries, cache-tree, resolve-undo), linked worktrees' HEADs and indexes, and the stash is walked; `missing`, `dangling` (default) and `unreachable` (`setUnreachable`) objects and `broken link`s are printed in git's order (the layout of git's object hash table). Options: `setConnectivityOnly`, `setDangling`, `setReflogs`, `setNameObjects`, `setRoot`, `setTags`, `setLostFound`, and `setCompatibility("2.43" | "2.56")` for the output differences between git versions: the default, `2.56`, is `git fsck --no-references` of git 2.45+ (HEAD's own checks moved to `git refs verify`, not implemented); `2.43` checks HEAD and linked worktrees' HEADs, following symbolic ref chains as git's `resolve_ref_unsafe` does (5 reads at most, HEAD's own included; past them `invalid HEAD`, and `bad ref for <reflog>`). The result has the structured findings, git's stdout and stderr text, and git's exit bits (`FSCK_ERROR_OBJECT`, `FSCK_ERROR_REACHABLE`, `FSCK_ERROR_PACK`, `FSCK_ERROR_REFS`). Symbolic refs that resolve to nothing, or need more than 5 reads, are `invalid sha1 pointer 0000…`. An invalid `core.bigFileThreshold` rejects the call with `FsckConfigError` and git's `bad numeric config value` message, as git dies on it. Over a files repository (`setRepositoryFiles`) loose objects are read from their files (zlib errors, headers, `hash-path mismatch`, stray files; blobs above `core.bigFileThreshold` streamed and hashed as git's `check_stream_oid` does; a buffer that grows to at most the declared size or what the file can inflate to; a stream that fit whole in git's 32-byte header read is cut to its declared size, as git's `unpack_loose_rest` cuts it) and packs are verified as git's `verify_pack` does (idx and pack checksums, per-entry CRC-32 and hash); over the memory, KV and SQL stores the objects of `history.objects` are checked and walked. Contents are read one object at a time.
  - **vcs-commands (`VerifyPackCommand`):** `git verify-pack` with `-v` (`<id> <type> <size> <size-in-pack> <offset> [<depth> <base>]`, the `non delta:` and `chain length = N:` histogram, `<pack>: ok`) and `-s`; a bad pack is reported with its checks' own messages and `<pack>: bad`.
  - **vcs-core:** `isDotGitComponent` (git's `is_hfs_dotgit` / `is_ntfs_dotgit`) and `isNtfsGitWorktreeFile` (git's `is_ntfs_dot*`) are exported; `openPack` takes the idx bytes (`idxBytes`) when the caller has read them.
  - **vcs-utils:** `inflateWhole` with `partial` now fills the output: the part of a stored block or a match that fits is written before it stops, as zlib does, so a header probe reads the start of an incompressible (stored) stream instead of nothing; input that runs out once the output is full stops it too, as zlib returns the full buffer then.
- 57846c3: **Faster fsck and commit-graph writing; the attribute source (`GIT_ATTR_SOURCE`, `git --attr-source`, `attr.tree`).**
  
  - **vcs-core:** `scanPackObjects` reads a pack once in pack order and unpacks only the objects of the types asked for (a delta takes its base's type, so blobs and their deltas are skipped unread; a REF_DELTA whose base is an earlier entry of the same pack is unpacked as an OFS_DELTA is; what it does not handle as it stands is left to the store, and a pack whose deltas mostly lack their base is not read further); `visit` returning false stops the read. With `packEntryOrder` (offsets sorted as numbers, no comparator), `parsePackEntryHead` and `packIdxLookups`. `writeCommitGraphFile` computing many changed-path filters (1024 or more) unpacks the trees of the newest packs that way first, newest first as the store orders packs, while the packs' objects fit in 32 per filter computed (a large pack a few new filters do not justify is skipped) and up to 256 MiB of trees (the read stops there), keyed by their id bytes (option `prefetch` tunes the three); the tree diff is synchronous while its trees are in memory (no generators), and commits are read without a promise when the store holds them. The files written are unchanged; `reads.treesScanned` counts the trees unpacked beforehand. `VerifyCommitSource` may answer without a promise.
  - **vcs-commands:** `fsck` keeps git's object hash with each id in its slot (one place in memory per probe) and every object's slot, so the lookups git makes again move an object without probing; a full run checks each pack with typed arrays in pack order and a FIFO cache of bases carved from slabs; a `--connectivity-only` run unpacks each pack's commits and trees in one read in pack order (`statistics.objectsScanned`, REF_DELTA packs included) and replays git's lookups on them in git's walk order, a commit-graph's parents and trees are looked up from its bytes, and the commit-graph verification takes the commits from those reads (the copy git's verification reads: the first pack of its most-recently-used pack list that has the commit, unchecked). What a run keeps from those reads is bounded (`setMemoryLimits`, `statistics.linksKept` and `graphCommitsKept`): past the bounds the objects are read from the store again. `fsck` now reports what native git reports where it missed it: `parse_object` checks the hash of what it reads (`hash mismatch <id>`) for the refs, the reflog entries a connectivity-only walk meets untyped, the cache-tree (trees read again, as git frees their buffers) and resolve-undo, reading the packed copy first as git does; the walk reads typed objects as git's `parse_tree`, `repo_parse_commit` and `parse_tag` (`Object <id> not a tree`); a grafts file prints git's `graftFileDeprecated` hint (as 2.43 or 2.56 words it). Every attribute consumer with a worktree (checkout and check-in conversion, diff and merge drivers) and `log -- :(attr)`, which also works in a bare repository, read the in-tree attributes of the attribute source when one is set: `$GIT_ATTR_SOURCE` over `attr.tree`, resolved with git's revision syntax; a bad `$GIT_ATTR_SOURCE` fails with git's `bad --attr-source or GIT_ATTR_SOURCE`, a bad `attr.tree` is ignored, an object that is no tree gives no in-tree attributes. `DiffCommand` still needs a worktree.
  - **vcs-working-tree:** `GitHostEnvironment.attrSource` (`$GIT_ATTR_SOURCE`); `GitContentFilter` reads in-tree attributes from the source's tree (options `trees`, `resolveAttributesSource`, method `setAttributesSourceResolver`); `attributesSourceSetting`, `resolveAttributesSource`, `readTreeAttributesFile` and `AttributesSourceError`.
  - **vcs-utils-node:** `createNodeGitHostEnvironment` reads `GIT_ATTR_SOURCE`.
- f078ebd: **`GcOrchestrator` no longer deletes reachable history: a corrupt or missing reachable object aborts the run, and it keeps what git keeps (HEAD, the index, reflogs, linked worktrees, recent objects).**
  
  - **vcs-core (data loss fix):** `collectReachableObjects` throws `CorruptObjectError` for a reachable object that is stored but cannot be read or decoded, on the object kernel and on the typed-store fallback, instead of treating it as absent (which cut the walk and let gc prune everything behind it). The typed stores' `has()` throws `CorruptObjectError` for such an object instead of returning false. A new third argument (`CollectReachableOptions`) makes an absent reachable object throw `MissingObjectError` (`missing: "throw"`) and names the shallow commits, whose parents may be absent. Commits are walked by their tree and parent lines only, and gitlinks are not followed.
  - **vcs-core (gc roots):** `GcOrchestrator` walks strictly from every ref, HEAD, the old and new ids of the refs' reflogs, and the roots a strategy adds (`GcStrategy.collectRoots`); unreachable objects the strategy reports as recent (`GcStrategy.recentObjects`, new `GcRunOptions.pruneExpireMs`, default two weeks as git's `gc.pruneExpire`) are kept with everything they reach. `GcRunResult.keptRecentObjects` counts them.
  - **vcs-store-files:** `FileGcStrategy` gives the orchestrator the roots `gc()` uses (`collectReachabilityRoots`) and the ages of loose objects, so unreachable loose objects younger than `pruneExpireMs` survive (pass `pruneExpireMs: 0` for `--prune=now`). `collectReachabilityRoots` now also keeps the trees of the index's cache-tree, the blobs of its resolve-undo, and the commits pseudo-refs name (`MERGE_HEAD`, `ORIG_HEAD`, `FETCH_HEAD`, ...), in the repository and in each linked worktree. `gc()` and `repack()` stop at the shallow boundary instead of failing on a shallow clone's absent parents.
- 5863bf1: **git hooks run through a portable host interface, and `git reset` refreshes the index as git does.**
  
  - `GitHostEnvironment.hookRunner` (optional) executes hooks; the commands find them as git's `find_hook` does (`core.hooksPath`, relative to the worktree top, else `$GIT_DIR/hooks` of the common git directory) through the repository's FilesApi (`Worktree.getFiles`), and a hook that is not executable gets the `advice.ignoredHook` hint (worded as the runner's `compatibility` says, 2.43 or 2.5x).   - Every ref lives in one root value (`ref:root`, JSON in git's name order).
  - Every write, whole batches included, is one `compareAndSwap` of that value. A lost race re-reads and re-checks; after 100 lost races a batch reports `locked`, and `set` / `setSymbolic` / `remove` throw.
