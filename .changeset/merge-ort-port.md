**Merges as git's merge-ort makes them: virtual merge bases, directory renames, octopus merges, merge drivers, renormalization, patch-id skips and resolve-undo, byte for byte with native git.**

The merge machinery (`ortMerge`, internal) is now a port of merge-ort's own structure: every path of the three trees gets an entry with its three versions, renames are detected per side for the paths the merge needs (exact, by basename with git's directory guess, then by similarity, in the order git reads the trees, unchanged directories deferred as git defers them), and entries are resolved children first, so a file meeting a directory moves aside only when the directory stays.

- **Several merge bases.** `merge` (and `pull`) merges the merge bases pairwise, oldest first, as `merge_ort_internal` does: "Temporary merge branch 1/2" markers two characters longer, binary files, links and modify/delete resolved to the base, the result named "merged common ancestors". The virtual commits and trees stay in memory; only content-merged blobs are stored, as git stores them. The merge bases come in git's order (a port of `paint_down_to_common`).
- **Directory renames** (`merge.directoryRenames`: `conflict`, the default, `true`, `false`): what one side adds in a directory the other side moved goes along, with git's "CONFLICT (file location)" / "Path updated" messages, the split, collision and in-the-way conflicts, the "Avoiding applying" warning, and their interplay with rename/rename and rename/delete. A merge that only has directory rename trouble is unclean, as in git.
- **Octopus merges**: `git.merge().include("a").include("b").include("c")` runs git-merge-octopus (trivial merges against each head's bases, then git-merge-one-file), with its messages, MERGE_HEAD listing every head, the refusal when an earlier head conflicts ("Should not be doing an octopus.") and the reduced head list in the message.
- **Merge drivers and renormalization**: the `merge` attribute (`text`, `binary`, `union`, a name), `merge.default`, `merge.<driver>.recursive`, `conflict-marker-size`; drivers of the host are callbacks (`installMergeDrivers(workingCopy, { name: createMergeDriver(fn) })`), since git's shell commands are not portable. `merge.renormalize` and `MergeCommand.setRenormalize` (`-X renormalize`) merge content as checked in afresh and drop a modify/delete whose change is only one of line endings or filters. `merge.renames`, `merge.renameLimit` are read too.
- **Rebase drops commits upstream already has**, by git's patch-id over the diff, with the "skipped previously applied commit" warnings and hint; `RebaseCommand.setReapplyCherryPicks` picks them anyway. A rebase whose commits are all upstream moves the branch to upstream. The sequencer's merge messages of a clean rebase pick are no longer reported (git shows them only for a conflicted pick).
- **Resolve-undo (`REUC`)** follows git: kept by `commit`, `reset --soft`, `reset --mixed` (which records the conflict stages it removes) and an up-to-date merge; dropped when the index is written anew (merge, cherry-pick, revert, rebase, branch checkout, `reset --hard`, stash). `Staging.clearResolveUndo` and `ReadTreeOptions.keepResolveUndo` are new; `GitContentFilter.renormalize` takes an attributes context.
