**Faster commit-graph writing, fsck and path-limited log; `fetch.writeCommitGraph`; `git log -- <path>` as git walks it, with changed-path Bloom filters.**

- **vcs-core:** `writeCommitGraphFile` computes changed-path filters over the trees' raw bytes (entries the same on both sides skipped after one byte comparison, no entry decoded, only differing subtrees read), keeps the trees it read lately, takes a parent's tree from the commits it parsed instead of reading the parent again, reads in-memory objects without a promise, and sorts ids as strings; commit headers parse their ids and dates without allocating. The bytes written are unchanged. `WriteCommitGraphFileResult.reads` counts the commits and trees read.
- **vcs-commands:** `LogCommand` with paths walks as `git log -- <path>` does (revision.c): newest commit first by date (ties in queue order), TREESAME commits hidden, a merge followed only to the first parent it matches, a root shown when it has the paths, `--first-parent` comparing the first parent only; before comparing trees it asks the commit-graph's changed-path filter of the commit (git's `check_maybe_different_in_bloom_filter`, all of a path's leading directories), and it compares only the entries on the paths' way, from the trees' raw bytes. `setUseBloomFilters(false)` turns the filters off; `getStatistics()` gives git's trace2 `bloom/statistics` counts and the tree work. `FetchCommand.setWriteCommitGraph()` (`--[no-]write-commit-graph`) and `fetch.writeCommitGraph` write a split commit-graph of what the refs reach after the fetch, as git's fetch does, given the repository's files (`setRepositoryFiles`, also on `PullCommand`); `FetchResult.commitGraph` lists the chain's layers. `FsckCommand --connectivity-only` takes the commits it reaches through parents from the commit-graph (git's `parse_commit_in_graph`) and walks a tree it just parsed from those bytes instead of reading it twice; `FsckResult.statistics` counts the objects read and the commits taken from the graph.
- **vcs-commands, ranges and pathspecs:** with excluded commits (`not`, `addRange`) a path-limited `LogCommand` limits the walk as git's `limit_list` does: one date-ordered queue of included and excluded commits, UNINTERESTING spread to parents as commits are taken, a merge's parents judged relevant (not UNINTERESTING, or an excluded commit given) with what is marked so far, so a merge TREESAME only to an uninteresting side stays shown and one TREESAME to its relevant parent is hidden, `--since` turned into UNINTERESTING, the early stop of `still_interesting`, and the output filtered by the final marks. Paths are git pathspecs: wildcards and `:(glob)`/`:(literal)`/`:(icase)`/`:(exclude)` magic match as `tree_entry_interesting` does in a pruned tree diff, `excludePath` is an `:(exclude)` element folded into TREESAME, and exclusions, icase and pathspecs without a literal leading directory leave the Bloom filters out as git does. A filter of another hash version than `commitGraph.changedPathsVersion` counts as not present (git's `get_bloom_filter`); a missing tree or parent fails with git's `unable to read tree (<id>)` / `cannot simplify commit <id> (because of <id>)`.
- **vcs-core:** the commit-graph writer reads a streamed tree (a loose tree over 64 KB) once, to the end of its content, instead of reading it again and leaving the first read open; its tree cache (and `LogCommand`'s) is bounded by bytes as well as by count.
