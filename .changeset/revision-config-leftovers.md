**Unique abbreviations everywhere, revision-or-path arguments, config load checks and git's config parser.**

- **vcs-commands, abbreviations:** what the sequencer, rebase and merge write abbreviates ids as git's `find_unique_abbrev` (`core.abbrev`, lengthened until unique) instead of 7 digits: cherry-pick / revert / rebase conflict labels (`<abbrev> (<subject>)`, `parent of ...`), `sequencer/todo`, `could not apply <abbrev>...`, merge-ort's single merge base label, the `Merge:` lines of `SQUASH_MSG` and checkout -m's autostash base. The sync `abbrev()` of merge-support is gone; `squashMessage` takes an abbreviator and `VirtualBaseContext` an `abbreviate`. Rebase writes its todo as git 2.5x does (`pick <id> # <subject>`) and says `Could not apply <abbrev>... # <subject>`.
- **vcs-commands, revision or path:** `RevParseCommand.addArgument` reads arguments as `git rev-parse` does: `--` and what follows printed as given (`bad revision` before it), the first argument that is no revision printed as a path that must exist, diagnosed as git's `verify_filename` / `maybe_die_on_misspelt_object_name` do (`path 'x' does not exist in 'HEAD'`, `path 'x' exists on disk, but not in 'HEAD'`, `path 'd/x' exists, but not 'x'` with its hint, the `:path` index variants, `invalid object name 'x'.`, `x: no such path in the working tree.`). `RevListCommand.addArgument` is `git log <args>` without `--`: revisions that also name a file die with `ambiguous argument 'x': both revision and filename`, the paths go to the walk. `'x' is outside repository at '<worktree>'` names the worktree's host path. New `revision-filenames.ts` (`checkFilename`, `looksLikePathspec`, `verifyFilename`, `verifyNonFilename`, `parseRevisionAndPathArgs`), `RevisionResolver.dieOnMisspeltObjectName`, `ResolveOptions.onlyToDie`, `RevisionSources.fileExists` / `worktreeHostPath`.
- **vcs-commands, config load:** every command checks `core.disambiguate` in `checkCallable()`, before it reads or writes anything (`InvalidConfigError` with git's `error:` / `fatal: bad config variable ... at line <n>`), as git dies on any command, `status` included (`configLoadError`): a commit, tag, merge, rebase, cherry-pick, stash, branch, reset or checkout refused this way changes no ref, index or file. Setters, which call `checkCallable()` too, throw it as well.
- **vcs-commands, paths as git's lstat:** `check_filename` and the `<rev>:<path>` diagnoses look a path up as git's `lstat` does, through the worktree (`lstatExists`, `WorktreeLookup`): a trailing slash asks for a directory (`a.txt/` is no path, `HEAD:a.txt/` does not exist in 'HEAD'), each leading component must be a directory, a link to a directory is followed (`lnk/c.txt`), `..` steps up from where the components led (`nope/../a.txt` and `lnk/../a.txt` are read as the kernel reads them), and a path may leave the worktree and come back through its own name (`../repo/a.txt`).
- **vcs-commands, remote names:** `RemoteAddCommand` and `CloneCommand.setRemote` refuse a name git's `valid_remote_name` refuses (`'<name>' is not a valid remote name`) before writing anything; `isValidRemoteName` is exported.
- **vcs-store-files, config parser:** `GitWorkingCopyConfig` parses as git's `config.c`: backslash line continuations inside and outside quotes, quoted values, the escapes `\n` `\t` `\b` `\"` `\\`, comments after values, blanks kept as written (git 2.5x), several headers or a header and a variable on one line; a file git refuses fails to load with `ConfigParseError` (`bad config line <n> in file <file>`: an unknown escape, a quote open at the end of a line, a bad header such as `[ sec]` or `[sec "x" ]`, a bad variable name, `name ; comment` without `=`). Line numbers (origins, errors) follow git's count past continuation lines; a variable spanning lines is rewritten whole and every other byte is kept. New `listWithOrigin()` (`git config --list --show-origin`). Blanks are git's (space, tab, newline, carriage return; `\v` and `\f` are kept in values and refused where only a blank may stand), a value ends at a NUL as git's C string does, and a variable written before any section header is listed under its bare name (as git 2.5x lists it) while no key reaches it. `set`, `add` and `unset` validate keys as git's `git_config_parse_key` (`key does not contain a section: <key>`, `invalid key: <key>`, `invalid key (newline): <key>`, ...; a value holding NUL is refused), `renameSection` / `copySection` the new name as `section_name_is_ok` (`invalid section name: <name>`, also for a newline in the subsection), and `save()` refuses to write a file its own parser would refuse. `remote..url` is `[remote ""]`, no longer `remote.url`. `get` / `getAll` read a key through an index instead of scanning the chain. `GitStashStore` abbreviates its messages' `<abbrev>` uniquely (option `coreAbbrev`, which takes the config's value as read: `12` or `false` count as their text).
