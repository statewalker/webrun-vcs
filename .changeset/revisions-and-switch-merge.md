**git's revision syntax, `switch -m`/`checkout -m`, `checkout -b` refusing an existing branch, several `-m`, `merge --no-commit -m`.**

- One resolver (`RevisionResolver`, used through `resolveRef` by checkout, switch, reset, merge, rebase, branch, diff, cherry-pick, revert and worktree add) reads git's revision syntax as `get_oid` does: `@`, `@{-N}`, `[<branch>]@{upstream}`/`@{u}` (`branch.<b>.remote`/`.merge`, the remote's fetch refspecs, `remote = .`), `[<branch>]@{push}` (`push.default`, `remote.pushDefault`, `branch.<b>.pushRemote`, push refspecs, mirror), `[<ref>]@{<n>}` and `[<ref>]@{<date>}` (git's `read_ref_at`, with its "only goes back to" warning and "only has N entries" refusal), `~`/`^`, `^{commit|tree|blob|tag|object|}`, `^{/<regex>}` and `:/<regex>` (POSIX extended, youngest reachable match first, `!-` and `!!`), `<rev>:<path>`, `:<path>` and `:<n>:<path>`. New `RevParseCommand` (`git.revParse()`, `rev-parse --verify`), `RevisionError` for git's `fatal:` lines (`no upstream configured for branch 'x'`, `HEAD does not point to a branch`), and `approxidateCareful` (git's approxidate) in the date module.
- `switch().setMerge(true)` and `checkout().setMerge(true)`: git 2.55+'s `-m`, local changes the switch would lose are stashed, the switch made and the stash applied with the labels `<target>` / `local` / the branch left; a conflict keeps the stash entry (`autostash while switching to '<target>'`). `stashApply().setLabels({ ours, theirs, base })` is `stash apply --label-ours/--label-theirs/--label-base`.
- `addMessage()` on `commit()`, `merge()` and `tag()`: several `-m` joined by a blank line.
- `merge().setCommit(false)` with a message writes `MERGE_MSG` as git does (the message plus a newline).
- Switch and checkout read a name's branch syntax as git does (`loc@{u}` is the local branch `main` when `loc` tracks it with `remote = .`; `switch @{u}` is refused as `a branch is expected, got remote branch 'origin/main'`).
- **Behaviour change:** `checkout().setCreateBranch(true)` on an existing branch is refused as `git checkout -b` refuses it (`RefAlreadyExistsError`, `fatal: a branch named 'x' already exists`); the new `setForceCreateBranch(true)` is `checkout -B` (create, or reset the branch to the start point), which `setCreateBranch` used to do.
- Commands that need a commit refuse a revision that names a tree, a blob or a missing object as git does (`NotACommitError`): reset (`error: object <id> is a tree, not a commit` / `fatal: Could not parse object '<rev>'.`), branch (`fatal: not a valid branch point: '<rev>'`), rebase (`fatal: invalid upstream '<rev>'`), merge (`merge: <rev> - not something we can merge`), cherry-pick and revert (`error: <rev>: can't cherry-pick a tree`), checkout and switch (`fatal: Cannot switch branch to a non-commit '<rev>'`; git 2.5x's `fatal: unable to read tree (<id>)` for a blob). They used to move the branch to the tree or blob. Reset with paths, diff and path checkout take any tree-ish.
- `checkout -m`/`switch -m` never lose the autostash: once the changes are stashed the index and worktree are reset as `reset --hard` resets them, and whatever happens to the switch the stash is applied or stored (`Applied autostash.`, git's conflict advice, or `error: could not apply autostash; your changes are safe in the stash`). Untracked files in the way take git 2.55+'s path (stash, refuse, apply back). `checkout().setForced(true).setMerge(true)` is refused (`fatal: '-f' cannot be used with '-m'`); the base label and stash messages abbreviate as `core.abbrev` and uniqueness ask.
- `checkout -b <branch> <start>`: a start point that names nothing is refused first (`fatal: 'nope' is not a commit and a branch 'feat' cannot be created from it`).
- Revisions: a full 40-hex id resolves whether the object exists or not (as `rev-parse --verify`); `<rev>:<path>` matches components as git's `get_tree_entry` (`HEAD:a.txt/`, `HEAD:d//b.txt` name nothing); warnings as git 2.56 prints them: `refname 'x' is ambiguous.` (also for 40-hex refnames, with git's advice unless `advice.objectNameWarning=false`; `core.warnAmbiguousRefs`), `ignoring dangling symref <ref>`, `log for ref <ref> has gap after <date>`, `log for ref <ref> unexpectedly ended on <date>`. Names that are no valid ref names are not looked up as refs.
- `approxidateCareful` keeps now's summer-time flag as git's `mktime` does (dates across a change differ by an hour, as in git), and dates written with numbers refuse the future relative to the given now.
- Several `-m`: an empty one adds no blank line (`-m "" -m b` is `b`).
