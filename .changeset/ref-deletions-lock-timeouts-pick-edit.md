**Several refs deleted in one transaction, the ref lock timeouts from the config, `cherry-pick -e` / `revert -e`, and the root refs in the reference-transaction hook.**

- New optional `Refs.removeAll(names, { legacy, message })` (`RefRemoveAllOptions`), git's `delete_refs`: `FileRefStore.removeAll` deletes all the refs in one transaction as git 2.5x does (none deleted when one cannot be), or with `legacy` as git 2.43's files backend (the refs dropped from `packed-refs` in a transaction of the packed store first, `packed-refs` rewritten even when absent, then each ref in a transaction of its own, going on past a failure). `branch -d/-D`, `tag -d`, `remote remove` and `fetch --prune` use it (legacy when the hook runner follows 2.43); `branch -d` and `tag -d` check every name first and still delete the others when some are refused, as git does; they throw the first refusal (its class as before), carrying every refusal in the new `GitApiError.refusals` and git's stderr for each in `GitApiError.messages` (`error: the branch 'x' is not fully merged` with its hint as each git version prints it, `error: branch 'x' not found`, `error: tag 'x' not found.`). The reflog of a deleted ref always goes with it.
- The files ref store locks the refs a multi-ref batch updates in name order (then the refs that only log the update, HEAD, as a single update locks them after its ref), so two batches naming the same refs in opposite orders cannot deadlock under a negative `core.filesRefLockTimeout`; the hook still hears the batch's order, and a lock it cannot take tells it `aborted` for the packed store's transaction of the deletions git would have locked before that ref. A batch of deletions only is committed as git commits it (packed-refs rewritten only when it names one of them, then the loose files removed). A batch without deletions no longer needs `packed-refs.lock`: when another writer holds it, the batch commits its loose refs as git does instead of failing.
- `createGitFilesBackend` reads `core.packedRefsTimeout` (default 1000 ms) and `core.filesRefLockTimeout` (default 100 ms) from the repository's config when the options are not given; a negative timeout waits forever, 0 tries once.
- `CherryPickCommand.setEdit` / `RevertCommand.setEdit` (`-e`, `--no-edit`) with `setEditor`: each pick that applies cleanly is committed by `git commit -n -e`, as git's sequencer runs it: the message in git commit's template through the editor, `prepare-commit-msg` told `merge`, `post-commit`, no `pre-commit` or `commit-msg`, `GIT_REFLOG_ACTION` set for the hooks. Either setting is saved in `sequencer/opts` (`edit = true` / `edit = false`, as git's `save_opts`) for a run of several commits and read back by `--continue` and `--skip`. `--continue` commits a resolved conflict as git's `continue_single_pick` does, through `git commit` (its `pre-commit`, `prepare-commit-msg` told `merge`, `commit-msg` and `post-commit` hooks): with the editor under `--edit`, else `--no-edit --cleanup=strip`. A cherry-pick records `CHERRY_PICK_HEAD` before it commits a clean pick, as git does. `GitCommand.shareHooksOf(source, env)` takes the variables such a child run exports.
- The files store tells its reference-transaction hook about the root refs git updates in transactions (`isRootRefName`: `ORIG_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `REBASE_HEAD`, ...; `AUTO_MERGE` for git 2.5x only), written with `set` (or a one-command `batch` with an old value) and deleted with `remove`. Commands delete them as git does: a commit, a reset and a branch switch delete `AUTO_MERGE` whether it exists or not, a cherry-pick's commit `CHERRY_PICK_HEAD`; a reset (and a sequencer's `--abort` / `--skip`) writes `ORIG_HEAD` given the value it read (`reset: updating ORIG_HEAD`; through a symbolic `ORIG_HEAD` to the ref it names, the old value read through it, an `ORIG_HEAD` naming `HEAD` writing HEAD's branch, one naming a missing ref with git's `warning: ignoring dangling symref ORIG_HEAD`; the hook's update lines carry the new `RefTransactionUpdate.through` for the symbolic refs on the way, and `viaHead` for a ref HEAD names reached through another symbolic ref) and moves HEAD expecting the commit it left, reporting an `ORIG_HEAD` it cannot write (`error: update_ref failed for ref 'ORIG_HEAD': ...` in `ResetCommand.getWarnings`) and moving HEAD all the same, as git; the sequencer's commits move HEAD in one transaction expecting its parent (a clean pick writes `MERGE_MSG` with `CHERRY_PICK_HEAD` before its commit, and a commit whose ref lock another process holds throws a `GitApiError` with git's `error: cannot lock ref 'HEAD': ...` and its exit status, both left as git leaves them); merge's hooks all see its `GIT_REFLOG_ACTION`.
- Deleting a root ref (`AUTO_MERGE`, `CHERRY_PICK_HEAD`, ...) with no reference-transaction hook installed unlinks it under its own lock, without taking `packed-refs.lock`, reading `packed-refs` only when its size or modification time changed (the new optional `AtomicFiles.stats`); a root ref `packed-refs` lists is deleted from it as git does; with a hook, git's nested packed-refs transaction is still emulated for the hook's lines.
