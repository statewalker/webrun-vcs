**Command-line config (`git -c`) on every config read; discovery's ceiling and file system boundary.**

- **vcs-store-files:** `GitWorkingCopyConfig` reads `GitHostEnvironment.commandLineConfig` last, after `config.worktree`, in scope `command` (git's `do_git_config_sequence`): the working copy's config, submodules' and repositories opened for serving all see it, so `-c` overrides the repository's own settings for every command. Its `include.path` / `includeIf.*.path` are followed (scope `command`, `file:<path>`); a relative include is git's fatal `relative config includes must come from files`; a `gitdir:./` condition prints git's `error: relative config include conditionals must come from files` (`loadErrors`, `GitConfigOptions.onError`, once per read) and holds in 2.5x but not under `GitConfigOptions.compatibility: "2.43"`; a directory named by a command-line include is git's `warning: unable to access '<dir>': Is a directory` plus the fatal line, and an include loop throws `ConfigIncludeDepthError` (git's `fatal: exceeded maximum include depth` text, exit 128). `includeIf.hasconfig:remote.*.url:` now holds in a repository's chain too, matched against the URLs of the whole sequence (system, global, the repository's file, `config.worktree`, the command line with what its includes bring in), as git's `populate_remote_urls`; the protected config sees command-line includes' URLs. `commandLineConfigError` (and that include error) make `load()` throw `CommandLineConfigError` (exit 128) once the files are read, as git dies at its first config read. `GitConfigOptions.commandLine: false` leaves it out. `listWithOrigin()` gives command-line values without a file; `showOrigin(entry)` prints `--show-origin`'s `file:<file>` / `command line:`. `readProtectedConfig` takes the command line from the chain, so its includes count for `safe.directory` too.
- **vcs-store-files:** `discoverRepository` honours `$GIT_CEILING_DIRECTORIES` (setup.c's `canonicalize_ceiling_entry` and `longest_ancestor_length`: relative entries ignored, `realPath` until an empty entry) and stops at a file system boundary where the FilesApi's `lstat` reports another `dev` unless `$GIT_DISCOVERY_ACROSS_FILESYSTEM` (`FilesystemBoundaryError`, git's two lines, exit 128).
- **vcs-working-tree:** `GitHostEnvironment.ceilingDirectories` / `discoveryAcrossFilesystem`; `withoutCommandLineConfig(environment)` (git's `local_repo_env`); `OpenRepositoryOptions.commandLineConfig` (default true, a server's own `-c`; false for the remote side of a local transport).
- **vcs-utils-node:** `createNodeGitHostEnvironment` fills `ceilingDirectories` and `discoveryAcrossFilesystem` from `$GIT_CEILING_DIRECTORIES` and `$GIT_DISCOVERY_ACROSS_FILESYSTEM`.
- **vcs-commands:** local fetch, push, ls-remote and clone open the remote with `commandLineConfig: false`: its upload-pack / receive-pack never see the client's `-c`, as connect.c clears `local_repo_env`; clone's ownership check of the source's objects (in the cloning process) still does.
- **vcs-store-files:** with an `environment`, `createGitFilesBackend` reads its own settings through git's whole sequence, the command line last: `core.logAllRefUpdates` / `core.bare` / the lock timeouts (ref store), `core.multiPackIndex` / `core.deltaBaseCacheLimit` (pack set), the alternates' config; so do the linked worktrees' reflog settings and `multiPackIndexWrite`/`Verify`'s `midx.version` and bitmap settings (`MultiPackIndexOptions.environment`, passed on by `repack`). The repository format stays the file alone. `discoverRepository` climbs the physical directory (`realPath` of `cwd`, mapped back into the FilesApi), so a symlinked `cwd` no longer bypasses `$GIT_CEILING_DIRECTORIES`.
- **vcs-transport:** `createServedFetchHandler` answers 500 when the resolver throws `CommandLineConfigError` or `ConfigIncludeDepthError`, as http-backend dies.
