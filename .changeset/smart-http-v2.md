**Smart-HTTP server speaks protocol v2.** `createFetchHandler`, `createHttpHandler` and `createGitHttpServer` answer `Git-Protocol: version=2` as git's http-backend does: `GET /info/refs?service=git-upload-pack` sends the v2 capability advertisement (`version 2` and the capabilities, without the `# service=` preamble git writes only for v0), and each `POST /git-upload-pack` runs one stateless v2 command (`ls-refs`, `fetch`, `object-info`) with the v2 server state machine, streaming the pack. gzip request bodies and `maxRequestBodyBytes` apply as in v0. Requests without the header, and receive-pack, stay v0. The `Git-Protocol` entries are split on `:` exactly, as git (no trimming: `foo : version=2` stays v0). New exports: `handleInfoRefsV2`, `handleUploadPackV2`, `requestsProtocolV2`, `isProtocolV2Request`, `NO_CACHE_HEADERS`, `SIDEBAND_64K_MAX_PAYLOAD`, `SIDEBAND_MAX_PAYLOAD`; new options `protocolV2` and `v2Capabilities`.

The v2 server matches git (checked against `git http-backend`): it advertises `ls-refs=unborn` and lists an unborn HEAD as `unborn HEAD symref-target:<ref>` (with `symrefs` and `unborn`), so cloning an empty repository checks out the server's branch; `object-info` sends the `size` line and sizes only when the `size` attribute is requested, a line per requested oid in order (`<oid> ` for a missing object), written without newlines as git, and an `ERR` line for an argument that is not an oid; a request is parsed as git's `serve.c`: `command=` must name an advertised command exactly (`invalid command '…'`), capability lines may precede it, a command may have no arguments (flush right after it), an `object-format=` other than the server's is refused (`mismatched object format: server sha1; client sha256`, `unknown object format '…'`), capabilities without a command are refused (`no command requested`), and only the first command of a stateless (HTTP) request runs. Errors before the first byte stay a 500 with git's message (http-backend answers an empty 200).

All info/refs and rpc responses, v0 and v2, upload-pack and receive-pack, carry git's no-cache headers (`Expires: Fri, 01 Jan 1980 00:00:00 GMT`, `Pragma: no-cache`, `Cache-Control: no-cache, max-age=0, must-revalidate`). A streamed upload-pack response never ends as a clean truncated 200: a failure after the first byte that the state machine did not report in band (an `ls-refs` or `object-info` failing half way) is written as an `ERR <message>` pkt-line, and the stream is aborted where no pkt-line can come (raw pack bytes out) or on a thrown error (`HandlerOutput.errorReported` tells which failures were already reported). In v0 over HTTP, a request that ends after a have batch is complete (git's `--stateless-rpc`), not an error. The pack is sent in full side-band frames (65515 payload bytes with side-band-64k, 995 with side-band), whatever the chunking of `exportPack`, holding at most one frame; a partial frame goes out when `exportPack` stalls for `keepAliveMs`.

Also: the v0 HTTP handler advertises what upload-pack implements for the repository (`deepen-since`, `deepen-not`, `deepen-relative` with a commit graph); v0 upload-pack honours the `deepen-relative` capability (`git fetch --deepen`), which it ignored before; `object-info` reports the size of any object type, not only blobs. Real `git clone`/`fetch`/`ls-remote` over HTTP is tested with protocol v2 and v0 (shallow, deepen, unshallow, multi-round negotiation, an empty repository), and the v2 answers against `git http-backend`.
