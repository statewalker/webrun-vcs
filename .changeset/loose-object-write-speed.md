**Writing objects costs what it costs git: an object already stored is only freshened, and a new loose object takes six system calls and no thread-pool round trip.** Storing 20,000 small blobs in a files repository went from 15.0 s to 2.7 s (native `git hash-object -w --stdin-paths`: 3.3 s), 20,000 trees of which 90% exist from 2.8 s to 0.5 s (native `git mktree --batch`: 0.4 s), and a 3,000-commit loop through `history.blobs/trees/commits.store` from 8.8 s to 2.4 s.

- **vcs-core:** the object kernel hashes content it holds first and skips the write of an object the store already has (git's `odb_freshen_object` before `write_loose_object`), for `putRaw` too, whose id is known up front: an unpacked object the repository has is not read, deflated nor staged. The write that follows reuses that id (the content is hashed once) and tells the store with the new `PutStagedOptions.notFresh` that it need not look again. Small objects (up to 64 KiB) are compressed with one synchronous call at git's loose-object level, `Z_BEST_SPEED` (`core.looseCompression` unset), so their files are byte for byte the ones native git writes; larger ones stream as before. `StagingBlobStore.isFresh` may now renew an old copy (git's `utime`) and answer true. `rawStorageStaging` (memory, KV and SQL backends) implements `isFresh`, so a duplicate write there costs one lookup and no deflate. `PackSet.freshen` renews an old pack's mtime (`touch`, git's `freshen_packed_object`) instead of having the object written loose again, where the FilesApi can set times; a cruft pack (one with a `.mtimes` file) never counts, as git's `is_cruft` check, so an object only it holds is written loose and outlives `gc --cruft --prune`. `putRaw` of an id already stored freshens it without reading its bytes (callers that take objects from elsewhere check them, as unpack-objects and index-pack do).
- **vcs-utils:** `FilesApi.touch(path, mtimeMs?)`, optional: sets a file's modification time without rewriting it, never through a link; the in-memory FilesApi, `createMountedFilesApi` and `createSymlinkFilesApi` implement it (the composites pass it on, false where the storage behind them has none). `deflateSync(chunks, { level })` compresses bytes in memory on a pooled pako state, as zlib's `compress2` does, and `LOOSE_OBJECT_COMPRESSION_LEVEL` is git's loose-object level.
- **vcs-utils-node:** `PosixNodeFilesApi.touch` (`lutimes`); `createExclusive` opens, writes the last (for a small file the only) batch and closes with synchronous calls, as small reads already were, and `move` renames synchronously; a batch view (`withLstatCache`) takes `maxAgeMs`, after which what it verified is checked again, and keeps its verified directories across file moves (it forgot them on every move) and checks a path whose parent it verified with no further `lstat`.
- **vcs-store-files:** `filesStagingStore` touches a loose object on every write of it, as git does, rather than rewriting it (an old one is rewritten only where the FilesApi cannot set times), names its temporaries from a counter instead of random bytes per object, and with the new `cacheDirectoryChecks` option (on in `createGitFilesBackend`) keeps one lstat-cache view for its life, so `objects/` and its fan-out directories are checked for links at most once a second, as git makes a fan-out directory once; a fan-out directory removed behind its back is made again. The files quarantine touches an old target instead of moving its copy over it.
