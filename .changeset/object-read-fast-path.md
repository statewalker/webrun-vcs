**Faster object reads: small objects are read, inflated and parsed in one pass.**

Reading one small object (a commit, a tree) went through the streaming inflater and several layers of async iterators. Small objects now take a short path, with the same results, errors and streaming of large objects. On a repacked 5000-commit repository (Node, files backend) a rev-walk that parses every commit takes about 40% of the time it took, reading every tree of HEAD about 22%, and reading 2000 blobs about 57% (packed) and 28% (loose).

- **vcs-utils:** `inflateWhole` inflates a zlib stream held in memory in one call, straight into its result (`into`, a known `size`, or a buffer that grows up to `maxSize`; `partial` stops at a full output, to read a header). It decodes what zlib decodes and fails where zlib fails (code sets, distances, stored lengths, the header and the Adler-32 trailer are checked): `InflateError`, `TruncatedStreamError`, or `InflateOverflowError` for output past the expected size. For small objects it is about twice as fast as the pooled pako inflater. `allocBytes` carves small buffers from shared slabs (a `new Uint8Array` costs more than inflating a commit). `applyGitDelta` takes an `allocate` function for its result and checks a result over 64 KiB before allocating it (smaller ones while writing them), in one pass without closures.
- **vcs-core:** `GitObject.bytes` holds the whole content when the store already has it in memory (never a cached buffer, absent for streamed and verified reads); the commit and tree stores parse it directly (`commitFromBytes` gives what the streaming decoder gives). A pack entry of at most 64 KiB is read from its pack window without the reverse index (the inflater finds where its zlib stream ends, as git's unpack_entry does; an entry crossing the window is read from the window's tail and the next window), windows are found synchronously per pack, a whole object of at most 1 MiB is inflated in one pass and handed out whole, delta chains write their intermediate results into two buffers of the read, and the delta base cache is reached through a per-pack `scope()` keyed by offset. Id lookups parse the hex id into bytes without regular expressions or allocation; the idx checksum is computed with Web Crypto where there is one. A loose object file of at most 64 KiB is read whole: its header first (a partial inflate), then the object in one pass; a file that is not plainly sound goes through the streaming read, which reports it as before.
- **vcs-utils-node:** `PosixNodeFilesApi.read` reads a file or range of at most 64 KiB synchronously (as it already did `lstat`): four async calls through libuv's thread pool cost far more than reading a loose object or a pack window from the page cache. The open flags and the regular-file check on the descriptor are unchanged.
